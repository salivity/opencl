How POCL Implements OpenCL Across CPUs and GPUs

The Portable Computing Language (POCL) is an open-source implementation of the OpenCL standard that allows parallel computing programs to execute seamlessly across diverse hardware architectures. By decoupling OpenCL from vendor-specific proprietary drivers, POCL enables developers to target multi-core CPUs, GPUs, DSPs, and custom hardware accelerators using a single runtime and compiler infrastructure. This article explains how POCL leverages the LLVM compiler framework, dynamic work-group transformations, and modular device drivers to deliver an open-source OpenCL implementation across modern CPUs and GPUs.

The LLVM-Based Compilation Pipeline

At the core of POCL's architecture is its deep integration with the LLVM compiler infrastructure and Clang. When an OpenCL C kernel is submitted for compilation, POCL processes the source through Clang to generate LLVM Intermediate Representation (IR).

Operating at the IR level allows POCL to perform hardware-agnostic optimizations, such as constant propagation and inlining, before handing the code off to device-specific targets. LLVM’s modular backend design allows POCL to translate OpenCL C into the native machine code of any target supported by LLVM, including x86-64, ARM, RISC-V, and specific GPU instruction sets.

CPU Implementation: Work-Item Vectorization and Multithreading

The OpenCL execution model defines fine-grained parallel units called work-items, which are grouped into work-groups. Because standard CPU architectures feature wide SIMD (Single Instruction, Multiple Data) execution units rather than millions of lightweight hardware threads like GPUs, directly mapping individual work-items to CPU threads results in massive scheduling overhead.

POCL solves this through a process known as work-group generation:

  1. Kernel Transformation: POCL transforms the kernel function by wrapping the work-item execution in loops that iterate through the local dimensions of a work-group.
  2. Loop Vectorization: Through LLVM's auto-vectorization passes, POCL vectorizes these loops across SIMD lanes (such as AVX-512, AVX2, or ARM NEON), executing multiple work-items in parallel per CPU core.
  3. Thread Pool Execution: The entire work-group is mapped to standard OS threads (typically via POSIX threads). POCL maintains a lightweight thread pool where each CPU core pulls and processes entire work-groups independently, minimizing context switching and ensuring high CPU cache locality.

GPU Implementation: Modular Device Drivers and Target Backends

For GPU execution, POCL utilizes a modular device layer that abstracts physical hardware interfaces into standard driver hooks for device discovery, memory allocation, and command execution.

Rather than managing hardware-level GPU registers directly, POCL integrates with existing low-level GPU compilation pathways:

  • NVIDIA GPUs (CUDA Backend): POCL maps OpenCL API calls to the CUDA Driver API. The LLVM NVPTX target compiles the OpenCL C kernel IR into PTX (Parallel Thread Execution) code, which the proprietary or open-source CUDA driver then assembles and launches on NVIDIA hardware.
  • Open-Source GPU Backends (SPIR-V, Vulkan, and Level Zero): For Intel and AMD GPUs, POCL can generate standard SPIR-V intermediate binaries. These are dispatched through modern vendor-neutral low-level APIs such as Vulkan (via compute shaders) or Intel Level Zero, enabling compute execution without requiring full proprietary OpenCL driver stacks.

Runtime Memory Management and Kernel Dispatch

POCL provides a fully compliant OpenCL host runtime library (libOpenCL.so). This runtime manages the lifecycle of OpenCL contexts, command queues, memory buffers, and synchronization primitives (events).

When host memory must be shared with a compute device, POCL determines whether the memory can be shared directly (zero-copy on unified memory architectures such as CPUs or integrated GPUs) or requires explicit DMA transfers over PCIe (discrete GPUs). POCL also implements an on-disk compilation cache, storing compiled device binaries to eliminate the latency of repeated Just-In-Time (JIT) compilation cycles across application runs.
