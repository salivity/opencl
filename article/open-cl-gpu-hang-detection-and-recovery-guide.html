OpenCL GPU Hang Detection and Recovery Guide

When a GPU experiences a hardware freeze or triggers an operating system Timeout Detection and Recovery (TDR) event, active OpenCL workloads fail abruptly, leaving the host application in an inconsistent state. Detecting these events requires monitoring OpenCL API return codes, inspecting asynchronous execution event statuses, and utilizing context error callbacks. Complete recovery involves tearing down the invalidated context, waiting for the underlying driver to stabilize the GPU, and reinitializing the OpenCL resources from a known clean state while breaking long-running workloads into smaller dispatches to prevent recurring crashes.

Detecting a GPU Hang

OpenCL provides both synchronous and asynchronous mechanisms to alert the host application when a hardware failure or driver reset occurs.

1. Context Error Notification Callback

When creating a context using clCreateContext, the host application can supply a pfn_notify callback function along with user data:

cl_context clCreateContext(
    const cl_context_properties *properties,
    cl_uint num_devices,
    const cl_device_id *devices,
    void (CL_CALLBACK *pfn_notify)(const char *errinfo, const void *private_info, size_t cb, void *user_data),
    void *user_data,
    cl_int *errcode_ret);

If the GPU encounters a hardware hang or the operating system resets the device, the OpenCL runtime invokes this callback asynchronously. The errinfo string typically contains driver-specific error strings identifying a device reset, lost hardware, or TDR event.

2. Synchronous API Error Codes

During a hang, executing blocking commands or querying the execution status of a submitted command will return severe error codes rather than standard runtime errors:

  • CL_OUT_OF_RESOURCES: Often returned when the device has hung, memory has faulted, or the driver failed to allocate execution slots during a reset.
  • CL_DEVICE_NOT_AVAILABLE: Returned if the OS has temporarily or permanently detached the device from the OpenCL platform during or after a driver reset.

3. Command Execution Status

If an application uses non-blocking enqueue operations, it must query the associated cl_event objects:

cl_int status;
clGetEventInfo(event, CL_EVENT_COMMAND_EXECUTION_STATUS, sizeof(cl_int), &status, NULL);

If a kernel execution hangs and causes a reset, status will be set to a negative integer indicating execution failure (often CL_EXEC_STATUS_ERROR_FOR_EVENTS_IN_WAIT_LIST or a vendor-specific negative code) rather than CL_COMPLETE.

Recovery Strategy

Once a hang or reset is detected, the existing cl_context and all child objects (command queues, memory buffers, programs, and events) are considered invalid and cannot be reused. Recovery requires a sequential teardown and rebuild.

Step 1: Drain and Release Faulted Resources

Attempting to issue new work to the invalid context will fail. The host must safely release all existing handles associated with the failed context:

  1. Release all allocated cl_event handles.
  2. Release all cl_mem buffers and images.
  3. Release all cl_kernel and cl_program objects.
  4. Release all cl_command_queue instances.
  5. Call clReleaseContext on the failed context.

Step 2: Poll for Device Re-availability

After an OS TDR event (such as Windows TDR or Linux DRM GPU reset), the graphics driver requires time to reinitialize the hardware. The host application should enter a polling loop querying clGetDeviceIDs:

cl_uint num_devices = 0;
cl_int err;
do {
    // Sleep briefly to yield CPU execution
    sleep_ms(100);
    err = clGetDeviceIDs(platform_id, CL_DEVICE_TYPE_GPU, 1, &device_id, &num_devices);
} while (err == CL_DEVICE_NOT_AVAILABLE);

Once clGetDeviceIDs returns CL_SUCCESS, the driver has restored the GPU to an operational state.

Step 3: Rebuild Context and Pipelines

With the device available again:

  1. Call clCreateContext and reattach the pfn_notify error handler.
  2. Create a new command queue using clCreateCommandQueueWithProperties (or clCreateCommandQueue).
  3. Re-upload buffer data from host memory backups.
  4. Rebuild the cl_program via clCreateProgramWithSource (or binaries) and clBuildProgram.
  5. Re-create the necessary cl_kernel objects.

Step 4: Resume Workload via Checkpoints

To avoid an immediate secondary crash upon resuming:

  • Maintain Host-Side Checkpoints: Save completed batch states on the host so execution can resume from the last known valid partition rather than restarting from zero.
  • Reduce Global Work Size: If the hang was triggered by exceeding the operating system's kernel watchdog timeout (e.g., standard 2-second Windows TDR), slice large global work sizes into smaller tiles and enqueue them iteratively to periodically release the GPU to the display server.
