OpenCL Small Work Size Launch Overhead

Launching OpenCL kernels with small global work sizes introduces severe performance penalties where runtime overhead vastly exceeds actual computation time. When the number of work-items is insufficient to saturate the compute units of a modern accelerator like a GPU, fixed driver execution latency, command dispatch costs, and hardware underutilization combine to negate the parallel processing advantages of the platform. Understanding these bottlenecks is critical for optimizing execution pipelines and deciding when to batch workloads or execute code on the host CPU instead.

Fixed API and Driver Launch Latency

Every clEnqueueNDRangeKernel call incurs a non-trivial amount of fixed host-side and driver-side overhead. This includes:

  • API Processing: Argument validation, state tracking, and building hardware command packets on the CPU.
  • Context Switching and Dispatch: Passing the command buffer from the user-space OpenCL runtime through the OS kernel driver to the device command queue.
  • Hardware Scheduling: The device-level command processor reading the packet and dispatching it to compute arrays.

This sequence typically takes between 5 to 50 microseconds depending on the operating system, driver efficiency, and hardware platform. If a kernel with a small global work size completes its execution in less than a microsecond, the dispatch overhead constitutes over 95% of the total execution time, creating a severe CPU-bound bottleneck.

Underutilization of Compute Units

GPUs achieve high throughput by running tens of thousands of threads concurrently across multiple Compute Units (CUs).

  • Wavefront/Warp Inefficiency: GPUs group work-items into SIMD vectors (e.g., warps of 32 threads on NVIDIA, wavefronts of 32 or 64 threads on AMD). If the global work size is smaller than the native vector size, or not an exact multiple, hardware execution lanes are masked off, wasting potential compute power.
  • Occupancy Loss: A modern GPU may contain dozens of CUs capable of executing multiple resident warps simultaneously to hide memory latency. A small global work size may only map to a fraction of a single CU, leaving the remainder of the device completely idle while still consuming active runtime resources.

Inability to Hide Memory Latency

Massively parallel architectures do not rely on large cache hierarchies to minimize memory access times; instead, they rely on zero-overhead thread scheduling to switch to active warps while others wait for memory requests. With a small global work size, there are not enough resident work-groups to hide global memory access latency. Consequently, the execution pipelines stall frequently, making memory-bound kernels significantly slower than equivalent implementations running on a multi-core CPU.

Data Transfer and Synchronization Imbalance

Small kernels frequently operate on small sets of data. When data must be moved across PCIe buses via clEnqueueWriteBuffer and read back using clEnqueueReadBuffer, the bus latency dominates the operation. Even on integrated GPUs with unified memory, cache flushes and synchronization barriers between the host and device incur costs that easily surpass the processing time of small workloads.

Mitigation Strategies

To eliminate the performance penalty of small kernel dispatches, consider the following approaches:

  1. Kernel Fusion: Combine multiple small kernels operating sequentially on related data into a single, larger kernel to amortize launch costs.
  2. Batching and Aggregation: Queue work until a sufficiently large dataset is accumulated, allowing you to launch an NDRange with thousands of work-items instead of dozens.
  3. Host Execution: Fall back to the CPU using standard multi-threading (e.g., OpenMP or C++ threads) for operations with small datasets where device dispatch latency outweighs parallel compute gains.
  4. Persistent Kernels: Launch a long-running kernel with enough threads to fully saturate the GPU, utilizing lock-free queues in device memory to feed small tasks directly to the running work-items without re-invoking the host dispatch mechanism.
