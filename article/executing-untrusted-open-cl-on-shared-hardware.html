Executing Untrusted OpenCL on Shared Hardware

Executing untrusted OpenCL kernels on shared hardware exposes systems to severe security challenges, including memory corruption, side-channel leakage, denial-of-service, and host compromise. Because hardware accelerators like GPUs and FPGAs were historically engineered for raw throughput rather than multi-tenant isolation, running third-party computational workloads requires understanding and mitigating risks across the hardware, driver, and application layers.

Inadequate Memory Isolation

Unlike modern CPUs, many graphics processing units (GPUs) and specialized accelerators lack fine-grained memory management units (MMUs) capable of enforcing strict hardware-level memory protection per work-group or kernel. While contemporary architectures are improving, shared memory (local memory), registers, and global device memory may not be completely isolated between tasks. An untrusted kernel might leverage out-of-bounds pointer arithmetic or buffer overflows to read from or write to memory regions assigned to other processes or host-device communication buffers.

Uninitialized State and Data Remanence

When a compute device allocates memory for a new OpenCL context or buffer, the underlying driver may not automatically zero-fill the allocated physical pages. If uninitialized global or local memory buffers are allocated directly after a sensitive workload (such as cryptographic processing or proprietary model inference), an untrusted kernel can read residual data from the shared memory spaces, leading to cross-context information disclosure.

Timing and Side-Channel Attacks

Shared accelerators utilize shared physical components, including compute units, memory controllers, execution pipelines, and multi-level caches. An untrusted OpenCL kernel can monitor hardware resource contention to infer sensitive data processed by co-located kernels. By observing memory bus latency, branch divergence, or cache occupancy, an attacker can reconstruct cryptographic keys, detect memory access patterns, or extract model architectures and weights belonging to other tenants.

Denial of Service and Resource Starvation

Kernel preemption on compute accelerators is often significantly less mature than preemptive multitasking on CPUs. Many drivers rely on coarse-grained preemption or cooperative execution models. An untrusted kernel can execute non-terminating loops, provoke deadlock conditions, or saturate memory bandwidth, completely stalling the device. In many operating systems, a hung GPU trigger a driver timeout and reset (such as Windows TDR), which forcefully terminates all concurrent and pending tasks across all tenants.

Driver and JIT Compiler Vulnerabilities

OpenCL source code or intermediate representations (such as SPIR-V) are compiled at runtime by the vendor’s user-mode driver or just-in-time (JIT) compiler. Because these compilers are vast and complex software components running with high privileges, they represent a significant attack surface. Maliciously crafted OpenCL C syntax or malformed intermediate code can exploit memory corruption vulnerabilities within the driver compiler itself, resulting in arbitrary code execution on the host CPU with the privileges of the calling process.

Mitigation Strategies

Securing shared environments against malicious OpenCL kernels requires a defense-in-depth approach:

  • Hardware-Level Partitioning: Utilize devices supporting hardware-enforced spatial partitioning (such as NVIDIA MIG or equivalent multi-instance technologies) to isolate compute units and memory channels physically.
  • Kernel Static Analysis and Verification: Validate SPIR-V binaries before execution using strict validators to enforce bounds-checking and reject unauthorized memory operations.
  • Driver Hardening and Sandboxing: Run the OpenCL host process inside isolated containers or lightweight virtual machines with restricted device access, minimizing the host attack surface if a driver exploit occurs.
  • Memory Clearing Enforcements: Explicitly zero-initialize all allocated device memory buffers and clear caches between context switches to prevent residual data exposure.
  • Watchdogs and Execution Quotas: Implement rigorous timeout mechanisms to terminate any kernel that exceeds predefined execution time or resource usage thresholds.
