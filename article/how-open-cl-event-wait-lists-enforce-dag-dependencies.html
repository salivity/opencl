How OpenCL Event-Wait-Lists Enforce DAG Dependencies

OpenCL relies on event-wait-lists to manage fine-grained synchronization across asynchronous operations executed on heterogeneous compute devices. By associating each enqueued command with an event object and passing sets of prerequisite events into subsequent commands, developers can model and enforce complex Directed Acyclic Graph (DAG) execution flows without stalling the host CPU.

Understanding OpenCL Events and Wait-Lists

In OpenCL, operations such as kernel executions (clEnqueueNDRangeKernel) and memory copies (clEnqueueReadBuffer, clEnqueueCopyBuffer) are asynchronous. When a command is enqueued, the API optionally returns a cl_event object representing that specific operation.

An event tracks the lifetime and state of a command through four stages:

  1. CL_QUEUED: The command is placed in the command queue.
  2. CL_SUBMITTED: The command is sent to the target device.
  3. CL_RUNNING: The device is currently executing the command.
  4. CL_COMPLETE: The command has finished execution.

An event-wait-list is an array of cl_event pointers passed into an enqueue function via the num_events_in_wait_list and event_wait_list arguments. The OpenCL runtime guarantees that the newly enqueued command will not begin execution until every event in its wait-list reaches the CL_COMPLETE status.

Modeling DAG Dependencies

A Directed Acyclic Graph represents workflows where nodes are tasks and directed edges are execution dependencies. In an OpenCL DAG:

  • Nodes are discrete commands enqueued to a device (e.g., data upload, Kernel A, Kernel B, data download).
  • Edges are directed precedence constraints defined by events linking parent tasks to child tasks.

Because events uniquely identify the completion of specific nodes, they allow execution trees to diverge (fan-out) and converge (fan-in) dynamically.

Fan-Out (One-to-Many Dependencies)

A single operation can serve as the prerequisite for multiple downstream operations. For instance, after transferring an initial dataset to the device, an event E_init is returned. Multiple independent kernels can be enqueued simultaneously, each including E_init in their respective wait-lists:

// Step 1: Initial upload generates E_init
clEnqueueWriteBuffer(queue, buffer, CL_FALSE, ..., 0, NULL, &E_init);

// Step 2: Kernels A and B branch out; both wait for E_init
cl_event wait_init[] = { E_init };
clEnqueueNDRangeKernel(queue, kernelA, ..., 1, wait_init, &E_kernelA);
clEnqueueNDRangeKernel(queue, kernelB, ..., 1, wait_init, &E_kernelB);

Kernels A and B can now execute concurrently if device resources allow.

Fan-In (Many-to-One Dependencies)

When downstream tasks require results from multiple preceding tasks, an event-wait-list aggregates several completion events into a single barrier condition:

// Step 3: Kernel C requires both Kernel A and Kernel B to complete
cl_event wait_AB[] = { E_kernelA, E_kernelB };
clEnqueueNDRangeKernel(queue, kernelC, ..., 2, wait_AB, &E_kernelC);

Kernel C remains blocked until both E_kernelA and E_kernelB transition to CL_COMPLETE, preserving data integrity across execution paths.

Cross-Queue and Out-of-Order Synchronization

Event-wait-lists provide two primary capabilities that make DAG execution robust:

  1. Out-of-Order Execution Queues: By default, standard OpenCL queues execute commands in order (FIFO). When creating a queue with CL_QUEUE_OUT_OF_ORDER_EXEC_MODE_ENABLE, commands execute as soon as resources and dependencies permit. In this mode, event-wait-lists are the sole mechanism controlling execution order, maximizing hardware utilization.
  2. Inter-Queue Synchronization: Events generated in one command queue can be placed into the event-wait-list of a command in an entirely different queue, even if the queues target different physical devices (e.g., synchronization between an integrated GPU and a discrete GPU within the same OpenCL context).

Memory Management and Cleanup

Events consume runtime resources. For every retained event returned by an enqueue call, the host application must call clReleaseEvent once the event is no longer needed in subsequent wait-lists. Releasing an event decouples host-side tracking while permitting the device to safely discard internal metadata once dependent commands finish execution.
