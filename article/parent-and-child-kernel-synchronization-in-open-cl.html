Parent and Child Kernel Synchronization in OpenCL

This article explains the synchronization semantics governing parent and child kernels in OpenCL 2.0 and later, where device-side enqueue allows kernels to spawn subsequent work directly on the device. It covers the lifecycle dependencies between parent and child executions, event-based ordering controls, and the memory visibility guarantees required to prevent data races and ensure deterministic execution.

Parent Kernel Completion Dependency

In OpenCL device-side enqueue, a parent kernel cannot reach a completed state until all of its child kernels—and any nested descendant kernels—have fully finished execution. Even if all work-items of the parent kernel execute their final instructions, the parent kernel execution status remains active on the host and the device queue until every child kernel enqueued by any of its work-groups has finished. Consequently, any host-side event waiting on the parent kernel will only trigger once the entire tree of descendant kernels is complete.

Execution Ordering and Child Launching

Child kernels do not automatically execute in the order they are enqueued unless explicit constraints are provided:

  • Asynchronous Launch: By default, child kernels are enqueued asynchronously. A child kernel can begin execution while the parent kernel is still running, provided device execution resources are available.
  • Out-of-Order Execution: Device queues are out-of-order queues by default. If a parent issues multiple child kernels without specifying dependencies, they may run concurrently or in an arbitrary order.
  • Event Wait Lists (clk_event_t): To enforce sequential or ordered execution among child kernels, developers use device-side events. A child kernel can accept an event wait list, preventing it from executing until the specified predecessor child kernels have signaled completion.

Enqueue Flags and Scope

When invoking enqueue_kernel, synchronization behavior can also be dictated using execution flags:

  • CLK_ENQUEUE_FLAGS_NO_WAIT: The child kernel begins execution without waiting on the parent kernel or work-group, subject only to its event wait list.
  • CLK_ENQUEUE_FLAGS_WAIT_WORK_GROUP: The child kernel does not execute until all work-items in the enqueuing work-group reach the enqueue point or a specified synchronization barrier.
  • CLK_ENQUEUE_FLAGS_WAIT_KERNEL: The child kernel is deferred until the parent kernel execution finishes completely, running effectively as a post-parent continuation task.

Memory Consistency and Visibility Semantics

Synchronization between parent and child kernels relies on explicit memory consistency rules defined by the OpenCL memory model:

  1. Parent-to-Child Visibility: When a parent kernel enqueues a child kernel, there is an implicit release operation on global memory. When the child kernel begins execution, it performs an implicit acquire operation. This guarantees that all global memory writes performed by the enqueuing parent work-item prior to the enqueue_kernel call are visible to the child kernel.
  2. Child-to-Child Visibility: When a child kernel depends on another child kernel via a device event (clk_event_t), completion of the preceding child acts as a release, and the start of the dependent child acts as an acquire. All global memory updates made by the first child are guaranteed visible to the subsequent child.
  3. Child-to-Parent Visibility: Because a parent kernel cannot wait synchronously on a child kernel within the execution of a single work-item (OpenCL does not support blocking wait calls on device events inside a work-item), a parent generally cannot read data written by its own child kernel during its active execution. Instead, child-to-parent data flow occurs across kernel boundaries—such as when a parent completes and a subsequent host-side or deferred task reads the combined outputs.
  4. Local Memory Isolation: Local memory is private to the work-group that allocates it. A parent cannot share its work-group local memory directly with a child kernel. Instead, child kernels must be provisioned with their own local memory allocations passed as arguments during the enqueue call.
