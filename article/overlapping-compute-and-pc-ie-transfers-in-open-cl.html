Overlapping Compute and PCIe Transfers in OpenCL

Achieving full concurrency between PCIe data transfers and device computation in OpenCL requires pipelining operations across multiple independent command queues. By combining multi-buffering techniques, non-blocking memory calls, pinned host memory, and cross-queue event synchronization, the PCIe read engine, PCIe write engine, and GPU compute units can operate simultaneously without blocking one another.

Hardware Prerequisites

To achieve complete overlap, the underlying hardware must support concurrent operations:

  • Full-Duplex PCIe Bus: Independent transmit and receive paths allowing concurrent Host-to-Device (H2D) and Device-to-Host (D2H) operations.
  • Dual Direct Memory Access (DMA) Engines: Dedicated copy engines on the device for memory transfers independent of the compute units.
  • Concurrent Compute and Copy Engines: The device driver and hardware must support executing a compute kernel while DMA engines saturate the PCIe bus.

Essential OpenCL Configuration

1. Pinned (Page-Locked) Host Memory

Standard host memory allocated via malloc is pageable. The OpenCL driver cannot transfer pageable memory directly via DMA; it must first perform an implicit, synchronous copy to an internal pinned buffer. To avoid this bottleneck, allocate pinned host buffers using either:

  • clCreateBuffer with the CL_MEM_ALLOC_HOST_PTR flag, accessed via clEnqueueMapBuffer.
  • OS-specific allocation APIs registered with OpenCL through clCreateBuffer with CL_MEM_USE_HOST_PTR.

2. Multiple In-Order Command Queues

While a single out-of-order queue (CL_QUEUE_OUT_OF_ORDER_EXEC_MODE_ENABLE) can conceptually handle concurrent operations, hardware mapping is often more deterministic when using multiple in-order command queues. A typical three-queue model consists of:

  • Queue 1 (Upload): Dedicated exclusively to H2D memory transfers (clEnqueueWriteBuffer or non-blocking copies).
  • Queue 2 (Compute): Dedicated exclusively to kernel execution (clEnqueueNDRangeKernel).
  • Queue 3 (Download): Dedicated exclusively to D2H memory transfers (clEnqueueReadBuffer or non-blocking maps).

Implementing the Pipelining Pattern

Complete overlap is achieved through software pipelining (triple buffering). The data is partitioned into \(N\) chunks. At any given moment in the steady state of the pipeline:

  1. Chunk \(i\) is transferred back to the host via Queue 3 (D2H).
  2. Chunk \(i+1\) is executing on the compute units via Queue 2.
  3. Chunk \(i+2\) is transferred to the device via Queue 1 (H2D).

Event Synchronization Across Queues

Because operations reside in different in-order queues, dependencies must be explicitly declared using OpenCL events (cl_event):

  1. Upload Stage: Enqueue non-blocking H2D transfer in Queue 1, generating event_upload[i].
  2. Compute Stage: Enqueue kernel execution in Queue 2. Pass event_upload[i] into the event wait list of clEnqueueNDRangeKernel, ensuring computation begins only when data arrives. This generates event_compute[i].
  3. Download Stage: Enqueue non-blocking D2H transfer in Queue 3. Pass event_compute[i] into the event wait list of clEnqueueReadBuffer, ensuring transfers begin only when execution finishes. This generates event_download[i].
  4. Buffer Reuse: Ensure the upload of chunk \(i+3\) waits on the completion of chunk \(i\) via event_download[i] so shared device buffers are not overwritten prematurely.

Pipeline Execution Loop

Iteration k:
  Queue 1: Enqueue H2D  (Chunk k+1) -> waits for Chunk k-2 D2H (if recycling buffers) -> triggers Event_H2D[k+1]
  Queue 2: Enqueue Kernel(Chunk k)   -> waits for Event_H2D[k]                         -> triggers Event_Kernel[k]
  Queue 3: Enqueue D2H  (Chunk k-1) -> waits for Event_Kernel[k-1]                     -> triggers Event_D2H[k-1]

All enqueue commands must set the blocking_read or blocking_write parameters to CL_FALSE. Only the final synchronization point—or periodic batch synchronization using clWaitForEvents—should block the host thread.

Common Pitfalls to Avoid

  • Blocking Calls Inside the Loop: Using CL_TRUE for any read/write operation immediately stalls host dispatch, breaking the asynchronous pipeline.
  • Shared Command Queues: Placing transfers and compute tasks in the same in-order queue forces serial execution, regardless of device DMA capabilities.
  • Implicit Memory Dependencies: Using the same OpenCL memory object (cl_mem) for concurrent read/write operations without multi-buffering creates data hazards that driver runtimes often serialize automatically.
