OpenCL Kernel Priority with cl_khr_priority_hints

The cl_khr_priority_hints extension provides an API mechanism in OpenCL to assign relative scheduling priorities to command queues, enabling the hardware scheduler to favor latency-sensitive kernels over background compute workloads. This article explains how the extension is structured, the priority levels it introduces, how to configure these hints during queue creation, and how the underlying device driver handles execution arbitration.

Purpose of the Extension

By default, OpenCL command queues treat submitted tasks with equal weight across the device, scheduling kernels based primarily on submission order and resource availability. In mixed-workload environments—such as interactive graphics combined with heavy asynchronous compute—background kernels can cause latency spikes in critical tasks.

The cl_khr_priority_hints extension solves this by enabling host applications to designate a queue as high, medium, or low priority. The driver and hardware use these hints to make informed scheduling, preemption, and resource allocation decisions between competing queues on the same OpenCL context or device.

Supported Priority Levels

The extension introduces the cl_queue_priority_khr property type along with three specific priority tokens passed via the queue properties list:

  • CL_QUEUE_PRIORITY_HIGH_KHR: Indicates that commands submitted to this queue require minimal execution latency. The scheduler allocates execution resources to these kernels first and may preempt lower-priority tasks if supported by the hardware architecture.
  • CL_QUEUE_PRIORITY_MED_KHR: The default operational priority level. Kernels execute under standard round-robin or FIFO scheduling models.
  • CL_QUEUE_PRIORITY_LOW_KHR: Applied to throughput-oriented or non-urgent background workloads. The scheduler may starve or delay these tasks whenever medium- or high-priority queues have work available.

Because these values are defined as "hints," hardware implementations are not required to enforce strict real-time scheduling. If an underlying architecture lacks preemption mechanisms or granular priority scheduling, the driver may fall back to standard execution behavior.

Configuring Queue Priority

Queue priorities are configured at queue creation time using the clCreateCommandQueueWithProperties function (or clCreateCommandQueueWithPropertiesKHR on older OpenCL versions). The priority hint cannot be altered once the queue is instantiated.

Before using the extension, verify its presence by querying CL_DEVICE_EXTENSIONS using clGetDeviceInfo. Once confirmed, construct a property list containing the priority property and value pair:

cl_queue_properties properties[] = {
    CL_QUEUE_PROPERTIES, CL_QUEUE_PROFILING_ENABLE, // Optional additional properties
    CL_QUEUE_PRIORITY_KHR, CL_QUEUE_PRIORITY_HIGH_KHR,
    0 // Null-terminated list
};

cl_command_queue queue = clCreateCommandQueueWithProperties(
    context, 
    device, 
    properties, 
    &err
);

Kernels enqueued to this high-priority command queue inherit that priority during device execution.

Scheduling and Hardware Impact

When multiple queues submit workloads simultaneously, the GPU or compute device scheduler uses priority hints in several ways:

  1. Work-Group Dispatch: High-priority work-groups are issued to compute units (CUs) before work-groups from lower-priority queues.
  2. Context Switching and Preemption: On hardware that supports compute preemption, a running low-priority kernel can be suspended at instruction or thread-group boundaries to immediately service a high-priority command.
  3. Memory Subsystem Arbitration: Some implementations prioritize memory transactions generated by high-priority command queues at the level of the memory controller, reducing cache thrashing and memory latency for critical kernels.
