Why AoS Harms Memory Coalescing in OpenCL

Memory throughput is one of the most critical factors determining the performance of OpenCL kernels on GPU architectures. Using an Array of Structures (AoS) data layout frequently degrades kernel performance by preventing global memory access from being coalesced. This article examines the mechanics of GPU memory coalescing, demonstrates how the interleaved fields in an AoS layout cause strided memory access, and explains why this pattern results in wasted bandwidth compared to alternatives like Structure of Arrays (SoA).

On modern GPUs, work-items are executed concurrently in hardware groups, often referred to as wavefronts (AMD) or warps (NVIDIA). When the work-items within a wavefront execute a load or store instruction targeting global memory, the GPU memory controller attempts to combine, or coalesce, those individual requests into a single, wide memory transaction (typically a 32-, 64-, or 128-byte cache line). Memory coalescing succeeds when consecutive work-items access contiguous and properly aligned memory addresses, allowing the hardware to satisfy 32 or 64 memory requests with minimal read or write cycles.

An Array of Structures layout stores heterogeneous fields together for each individual element sequentially in memory. For example, consider an array representing 3D particles:

typedef struct {
    float x;
    float y;
    float z;
    float mass;
} Particle;

Particle particles[N];

In this layout, the data is laid out sequentially as x0, y0, z0, mass0, x1, y1, z1, mass1, x2.... In standard parallelization models, consecutive OpenCL work-items process consecutive elements. Therefore, work-item 0 accesses particles[0].x, work-item 1 accesses particles[1].x, and work-item 2 accesses particles[2].x.

Because of the intervening y, z, and mass fields, the addresses accessed by consecutive work-items are not adjacent. Instead, they are separated by the stride of the structure's full size—16 bytes in this case. Work-item 0 requests offset 0, work-item 1 requests offset 16, and work-item 2 requests offset 32. This strided access breaks the contiguous access requirement needed for coalescing.

When memory access is strided, the GPU memory controller cannot combine the work-items' requests into a minimal number of transactions. To fetch a 4-byte float for each work-item, the hardware must fetch entire cache lines containing the unrequested adjacent fields (y, z, and mass). Most of the data brought into the cache in that cycle is discarded or sits unused until subsequent instructions, leading to severe memory bandwidth underutilization and higher latency. If the stride is large enough, each work-item might trigger its own distinct memory fetch, multiplying the number of required memory transactions by the structure's size.

To resolve this bottleneck, OpenCL developers transition from AoS to Structure of Arrays (SoA):

typedef struct {
    float x[N];
    float y[N];
    float z[N];
    float mass[N];
} ParticleArrays;

In an SoA layout, all x components reside sequentially in memory. When work-item 0 reads x[0], work-item 1 reads x[1], and work-item 2 reads x[2], the accessed addresses are perfectly contiguous. The memory controller can combine these requests into a single transaction, maximizing cache line utilization and enabling the kernel to achieve peak memory throughput.
