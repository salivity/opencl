Using OPENCL_VERSION for OpenCL 1.2 vs 2.0

The __OPENCL_VERSION__ predefined preprocessor macro enables developers to write portable kernel code that safely targets multiple OpenCL runtimes from a single source file. By checking this macro at compile time using standard preprocessor directives, developers can write optimized code paths that leverage advanced OpenCL 2.0 capabilities while maintaining compatible fallbacks for OpenCL 1.2 hardware.

How __OPENCL_VERSION__ Evaluates

The OpenCL compiler defines __OPENCL_VERSION__ as an integer representing the OpenCL C language version supported by the device compiler. The value follows the format major * 100 + minor:

  • OpenCL 1.2: Evaluates to 120
  • OpenCL 2.0: Evaluates to 200

Because the value is an integer, developers can use standard comparison operators (>=, <, ==) within preprocessor statements such as #if, #elif, and #else.

Implementing Conditional Code Paths

To support both OpenCL 1.2 and 2.0, write conditional blocks checking if __OPENCL_VERSION__ is greater than or equal to 200.

#if __OPENCL_VERSION__ >= 200
    // OpenCL 2.0+ implementation
    void process_data(global int* output, int* input) {
        // Uses 2.0 generic address space (no explicit address space qualifier on 'input')
        atomic_fetch_add_explicit((atomic_int*)output, *input, memory_order_relaxed);
    }
#else
    // OpenCL 1.2 fallback implementation
    void process_data(__global int* output, __global int* input) {
        // Requires explicit address space qualifiers and legacy atomic built-ins
        atomic_add(output, *input);
    }
#endif

Key Language Differences Handled by the Macro

  1. Generic Address Space: OpenCL 2.0 introduced the generic address space (__generic), allowing functions to receive pointers to __global, __local, or __private memory without separate function overloads. In OpenCL 1.2, address space qualifiers must be explicitly declared for every pointer parameter.

  2. Atomic Operations: OpenCL 2.0 aligned with C11 atomics, introducing types like atomic_int and fine-grained memory synchronization functions (such as atomic_fetch_add_explicit). OpenCL 1.2 relies on older 32-bit and 64-bit built-in functions like atomic_add or atom_add.

  3. Shared Virtual Memory (SVM) and Pipes: OpenCL 2.0 features such as built-in pipe types (pipe) and device-side kernel enqueue cannot be parsed by an OpenCL 1.2 compiler. Encapsulating these features behind #if __OPENCL_VERSION__ >= 200 prevents compilation errors on legacy runtimes.

  4. Work-Group Built-in Functions: OpenCL 2.0 added expressive work-group collective operations, such as work_group_broadcast and work_group_reduce_add. Using the version macro allows you to utilize these efficient hardware-accelerated collectives on 2.0 drivers while substituting manual local-memory reduction loops on 1.2 drivers.
