How cl_khr_p2p Bypasses Host Memory in OpenCL

The cl_khr_p2p extension enables direct, high-speed memory copies between discrete OpenCL devices by completely bypassing host system RAM and CPU mediation. In traditional multi-device workflows, transferring data from one device to another requires a two-step "staging" process through the host memory over the PCIe bus. By leveraging PCIe Peer-to-Peer (P2P) direct memory access, cl_khr_p2p maps the physical memory spaces of adjacent devices directly to each other, cutting transfer latency in half and freeing system memory bandwidth for other compute tasks.

The Traditional Host-Staging Bottleneck

Without peer-to-peer capabilities, transferring data between two accelerators (such as two GPUs) requires a double traversal of the PCIe bus:

  1. Device A pushes data over the PCIe link into a pinned buffer in the host system's RAM.
  2. The host CPU orchestrates the transfer and synchronizes execution.
  3. The host system pushes the data from host RAM back over the PCIe link to Device B.

This standard pipeline doubles PCIe bus utilization, introduces synchronization overhead, and is strictly bound by host system memory bandwidth and CPU availability.

Direct Address Space Mapping via PCIe BARs

The cl_khr_p2p extension circumvents this staging cycle by exploiting PCIe Base Address Registers (BARs). Modern PCIe devices use BARs to expose portions of their local device memory (VRAM) to the broader PCIe fabric.

When cl_khr_p2p is initialized between compatible devices:

  • The OpenCL driver identifies the physical topology of the PCIe interconnect.
  • The memory space of Device B is mapped into the physical address space reachable by Device A.
  • The driver exposes an OpenCL command queue capable of orchestrating P2P operations directly, treating the remote device's memory as a directly accessible target.

DMA Controller Orchestration

Once memory addresses are exposed across the interconnect, the actual data movement is handled entirely by hardware Direct Memory Access (DMA) engines located on the devices themselves:

  • DMA Initiation: The OpenCL runtime issues a P2P transfer command (such as direct buffer copies). The local GPU's DMA controller takes ownership of the transfer.
  • Root Complex and PCIe Switch Routing: The DMA controller initiates read or write transaction layer packets (TLPs) targeted directly at the physical PCIe address of the peer device. If both devices sit on the same PCIe switch, the traffic traverses only the switch without even touching the CPU host bridge (Root Complex). If they sit on separate PCIe lanes connected to the same CPU socket, traffic routes strictly through the PCIe Root Complex without writing to system RAM.
  • Zero Host Intervention: The CPU merely issues the initial queue command and receives an interrupt when the DMA transaction completes. The host DRAM is never read from or written to during the transfer.

By removing the intermediate host hop, cl_khr_p2p maximizes bidirectional throughput, minimizes end-to-end communication latency, and eliminates host memory footprint overhead in multi-device OpenCL pipelines.
