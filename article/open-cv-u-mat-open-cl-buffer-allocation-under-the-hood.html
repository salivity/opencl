OpenCV UMat OpenCL Buffer Allocation Under the Hood

When you instantiate an OpenCV cv::UMat, OpenCV relies on its Transparent API (T-API) framework to seamlessly bridge host-side execution and hardware acceleration. Under the hood, allocating an OpenCL-backed UMat involves querying device runtime states, delegating work to a specialized MatAllocator, invoking native OpenCL driver APIs such as clCreateBuffer, and setting up a synchronization tracking structure called UMatData. This process allows OpenCV to manage GPU memory lifecycle, alignment, and lazy data transfers between the host CPU and the compute device without requiring manual buffer synchronization from the user.

OpenCL Runtime and Context Verification

The allocation begins with OpenCV evaluating the execution environment via cv::ocl::useOpenCL(). If OpenCL support is disabled or unavailable at runtime, OpenCV seamlessly falls back to standard system memory allocation using cv::fastMalloc.

When OpenCL is active, the runtime acquires the global OpenCL environment managed by OpenCV's internal context manager. This singleton infrastructure holds the active OpenCL platform, device handles, the shared cl_context, and the default cl_command_queue. OpenCV validates device capabilities, ensuring that parameters such as maximum memory allocation size (CL_DEVICE_MAX_MEM_ALLOC_SIZE) and address alignment rules will not be violated by the upcoming buffer request.

Delegation to the OpenCLAllocator

A cv::UMat does not manage memory directly; it delegates allocation to a concrete instance of cv::MatAllocator. For OpenCL operations, this is handled by the internal OpenCLAllocator.

The allocator receives dimensional specifications—width, height, element type, and channels—and computes the total payload size. Crucially, the allocator factors in padding and memory alignment:

  • Row Step Computation: The allocator calculates the row stride (step) ensuring lines are aligned to boundaries optimal for GPU direct memory access (DMA) and compute unit SIMD vector operations.
  • Size Alignment: The total byte size is padded to satisfy OpenCL alignment constraints, preventing misaligned memory accesses within compiled OpenCL kernels.

Native Buffer Allocation (clCreateBuffer / Shared Virtual Memory)

Once memory dimensions and alignments are calculated, the allocator directly calls the OpenCL runtime. In standard configurations, it issues:

cl_mem clCreateBuffer(
    context,
    CL_MEM_READ_WRITE,
    total_size,
    NULL,
    &errcode
);

The CL_MEM_READ_WRITE flag informs the OpenCL driver that the kernel can both read and write to this device address space.

On hardware configurations that support Shared Virtual Memory (SVM), such as modern integrated GPUs, the allocator checks if coarse-grained or fine-grained SVM is enabled. If available, OpenCV bypasses standard cl_mem handles in favor of clSVMAlloc, allocating memory that resides within a shared address space accessible by both CPU and GPU without discrete copy operations.

Wrapping into UMatData

Upon successful buffer creation, OpenCV wraps the raw cl_mem object into a cv::UMatData control block. UMatData is the internal state tracker responsible for:

  • Reference Counting: It tracks how many cv::UMat or sub-region views reference the underlying buffer, mirroring the behavior of cv::Mat::addref() and cv::Mat::release(). When the count drops to zero, the allocator calls clReleaseMemObject.
  • Resource Pointers: It stores the native cl_mem handle in its handle member, while keeping the host-accessible CPU pointer (origdata and data) unallocated or set to nullptr.
  • State and Access Flags: It sets state flags tracking whether the most up-to-date copy of the data resides on the device, on the host, or is currently shared.

Lazy Synchronization Strategy

The initial allocation does not synchronize or map data to the host. Host memory allocation is deferred entirely.

If a user later requests a CPU-bound view by invoking UMat::getMat(cv::ACCESS_READ) or ACCESS_WRITE, the OpenCLAllocator triggers lazy synchronization. It allocates host memory on-demand and calls clEnqueueReadBuffer or clEnqueueMapBuffer on the active command queue. Conversely, if host operations modify the data and a GPU operation is subsequently called on the UMat, the T-API marks the device copy as dirty and executes clEnqueueWriteBuffer before dispatching the next OpenCL kernel.
