SoA vs AoS in OpenCL Data Layouts

This article examines the performance impact of Structure-of-Arrays (SoA) versus Array-of-Structures (AoS) data layouts within OpenCL kernels. Selecting the appropriate memory layout is critical for achieving optimal compute throughput on heterogeneous hardware, as it directly dictates global memory bandwidth efficiency, coalescing behavior, cache utilization, and SIMD instruction mapping.

Understanding AoS and SoA

In an Array-of-Structures (AoS) layout, individual records containing multiple fields are placed sequentially in memory. For example, a 3D particle simulation stored as an AoS groups each particle's x, y, and z coordinates together:

typedef struct {
    float x;
    float y;
    float z;
} Particle;

Particle particles[N];

In a Structure-of-Arrays (SoA) layout, the fields are separated into distinct parallel arrays:

typedef struct {
    float x[N];
    float y[N];
    float z[N];
} ParticleArrays;

Memory Coalescing

The primary performance driver in OpenCL GPU programming is memory coalescing. GPUs execute work-items in groups (known as warps on NVIDIA or wavefronts on AMD). When work-items within a warp execute a load or store instruction simultaneously, the hardware attempts to combine those individual memory requests into a single continuous transaction.

  • AoS and Strided Access: When a work-item reads the x coordinate in an AoS layout, adjacent work-items read their respective x values separated by the stride of the structure (e.g., sizeof(float) * 3). This strided access prevents the memory controller from coalescing the requests into a single transaction, leading to multiple high-latency memory transactions and wasted memory bus bandwidth.
  • SoA and Coalesced Access: In an SoA layout, adjacent work-items access adjacent elements (x[0], x[1], x[2], etc.). This unit-stride pattern enables the hardware to merge all requests across the wavefront into a single contiguous cache-line load, achieving near 100% memory bus utilization.

Cache Efficiency and Bandwidth Waste

OpenCL kernels often require only a subset of an object's fields during a specific execution phase.

  • Under AoS, loading one attribute requires fetching the entire cache line, which pulls unused fields into the cache. This causes cache pollution, reduces effective cache capacity, and wastes global memory bandwidth on data that is never computed.
  • Under SoA, each array is dedicated to a single attribute. If a kernel only needs x and y coordinates, it never accesses the memory pages assigned to z or other auxiliary fields, preserving cache lines exclusively for relevant data.

Vectorization and SIMD Utilization

On architectures that rely on vector units (such as CPU OpenCL targets or older GPU architectures), SoA naturally aligns with SIMD execution models. Data can be loaded directly into SIMD registers across consecutive items without requiring costly unpack, shuffle, or permute instructions that are typically necessary to reorganize AoS data for vector arithmetic.

Array of Structures of Arrays (AoSoA)

While SoA is generally superior for OpenCL GPU targets, it can occasionally lead to Translation Lookaside Buffer (TLB) thrashing if an algorithm simultaneously reads from many distinct large arrays. To balance coalescing and locality, high-performance kernels sometimes employ an Array of Structures of Arrays (AoSoA), also known as tiled AoS. AoSoA chunks data into small structs containing vector-sized arrays (e.g., vectors of size 16 or 32), ensuring perfect coalescing within a warp while maintaining spatial locality across different attributes.

Conclusion

For virtually all OpenCL kernels executed on massively parallel hardware, the Structure-of-Arrays (SoA) approach drastically outperforms Array-of-Structures (AoS). By enabling hardware memory coalescing, eliminating unused data transfers, and maximizing cache utility, SoA resolves the primary memory-bound bottlenecks common in parallel compute tasks.
