Prevent Bank Conflicts in OpenCL Matrix Transpose

In high-performance GPU computing using OpenCL, matrix transpose implementations typically use local memory (also known as shared memory) as an intermediate staging area to achieve coalesced global memory reads and writes. However, reading columns from this intermediate buffer often leads to shared memory bank conflicts, which serialize thread access and reduce performance. This article explains the hardware mechanisms behind local memory banks, why standard 2D block transpose patterns cause simultaneous collisions, and how adding a simple 1-element pad to array dimensions redistributes access across banks to maintain peak memory throughput.

Understanding GPU Local Memory Banks

GPU local memory is divided into equally sized memory modules called banks, typically 32 banks on modern architectures (matching warp or wavefront sizes). Each bank has a width of 4 bytes (32 bits), corresponding to a single float or integer:

  • Successive 32-bit words are assigned to successive banks.
  • Word address \(0\) maps to Bank \(0\), address \(1\) to Bank \(1\), up to address \(31\) mapping to Bank \(31\). Address \(32\) wraps back to Bank \(0\).
  • Formally: \(\text{Bank Index} = (\text{Byte Address} / 4) \pmod{32}\).

When threads in a wavefront access local memory simultaneously, the access is optimal if each thread requests data from a distinct bank. If two or more threads request different words from the same bank in the same cycle, a bank conflict occurs. The hardware must serialize these conflicting requests, increasing latency proportionally to the conflict degree (e.g., a 32-way conflict executes 32 times slower).

The Transpose Bottleneck Without Padding

A typical matrix transpose tiles data into local memory to ensure that both the read from global memory and the write to global memory are coalesced. Consider a standard block size of \(32 \times 32\) floats:

#define TILE_DIM 32
__local float tile[TILE_DIM][TILE_DIM];

The execution flow proceeds in two steps:

  1. Row-wise Write: Threads write row data coalesced from global memory into the local tile: tile[local_row][local_col] = global_input[...]; Threads in the same wavefront share the same local_row while local_col ranges from \(0\) to \(31\). The linear index is: \[\text{Index} = \text{local\_row} \times 32 + \text{local\_col}\] Because local_col steps by 1, adjacent threads access consecutive 4-byte words, which map to Banks \(0\) through \(31\). There are zero bank conflicts.

  2. Column-wise Read: To transpose the data, threads read from the local tile along the orthogonal axis: float val = tile[local_col][local_row]; Here, threads in the same wavefront share the same local_row (now the second index) while local_col (the first index) ranges from \(0\) to \(31\). The linear memory address for thread \(i\) is: \[\text{Index}_i = i \times 32 + \text{local\_row}\]

Evaluating the bank mapping: \[\text{Bank Index}_i = (i \times 32 + \text{local\_row}) \pmod{32} \equiv \text{local\_row} \pmod{32}\]

Because \(i \times 32\) is a multiple of \(32\), every thread \(i\) in the wavefront computes the exact same bank index (\(\text{local\_row}\)). All 32 threads simultaneously access different memory addresses within a single bank, causing a maximum 32-way bank conflict.

How Dimension Padding Resolves Conflicts

Padding the inner dimension of the local memory allocation alters the memory stride without changing the algorithm's logical structure. By adding 1 element of padding to the column dimension, the local array is declared as:

#define TILE_DIM 32
#define PADDING 1
__local float tile[TILE_DIM][TILE_DIM + PADDING];

The pitch (stride) of each row in memory increases from 32 elements to 33 elements.

The Mathematical Shift

With the padding applied, each successive row starts at an offset shifted by 1 word relative to the bank structure.

During the column-wise read: float val = tile[local_col][local_row];

The linear index for thread \(i\) (where \(i = \text{local\_col}\)) becomes: \[\text{Index}_i = i \times (32 + 1) + \text{local\_row} = 33i + \text{local\_row}\]

Calculating the target bank index: \[\text{Bank Index}_i = (33i + \text{local\_row}) \pmod{32}\] \[\text{Bank Index}_i = (32i + i + \text{local\_row}) \pmod{32}\] \[\text{Bank Index}_i = (i + \text{local\_row}) \pmod{32}\]

As thread index \(i\) increments from \(0\) to \(31\), \((i + \text{local\_row}) \pmod{32}\) maps uniquely to bank indices \(0\) through \(31\) (shifted cyclically by local_row). Every thread in the wavefront now targets a unique bank in the exact same clock cycle.

Summary of Benefits

  • Zero Serialization: Eliminates the 32-way serialization, allowing all threads in a wavefront to read local memory in a single cycle.
  • Minimal Memory Overhead: For a \(32 \times 32\) block of single-precision floats (4096 bytes), adding 1 float per row requires only 32 extra floats (128 bytes), representing a negligible ~3.1% local memory footprint increase.
  • No Logic Branching: The code structure remains unchanged except for the buffer declaration, avoiding any register pressure or control flow divergence.
