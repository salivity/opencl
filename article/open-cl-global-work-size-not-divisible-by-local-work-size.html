OpenCL Global Work Size Not Divisible by Local Work Size

In OpenCL, the outcome of specifying a global work size that is not evenly divisible by the local work size depends on the OpenCL version targeted by your application. In OpenCL 1.x, this mismatch violates API constraints and triggers a runtime failure, whereas OpenCL 2.0 and later versions natively accommodate non-uniform work-groups. This article explains the exact behavior across different OpenCL specifications, the specific errors returned, and the standard techniques used to safely execute kernels when your data size does not align with your hardware work-group dimensions.

Behavior in OpenCL 1.0, 1.1, and 1.2

In OpenCL versions prior to 2.0, the runtime strictly requires that each dimension of the global_work_size array must be an exact integer multiple of the corresponding dimension in local_work_size.

If you invoke clEnqueueNDRangeKernel with a local_work_size that does not evenly divide the global_work_size, the function immediately fails and returns the error code:

CL_INVALID_WORK_GROUP_SIZE

The kernel will not execute, and any dependent commands queued in the OpenCL command queue will fail or stall depending on your event handling logic.

Behavior in OpenCL 2.0 and Later

Starting with OpenCL 2.0, support for non-uniform work-groups was introduced. When using an OpenCL 2.x or 3.x driver that supports this feature, the API allows the global work size to be non-divisible by the local work size.

When this occurs:

  • The runtime executes the kernel without throwing an error.
  • The workload is divided into standard, full-sized work-groups, along with one or more "partial" work-groups that handle the remaining elements along the boundary.
  • Inside the partial work-groups, functions like get_local_size() and get_enqueued_local_size() report different values: get_enqueued_local_size() returns the nominal local size passed to the launch, while get_local_size() returns the actual number of active work-items in that specific group.

Standard Solutions for Strict Divisibility

If you must maintain compatibility with OpenCL 1.2 or run on hardware that lacks non-uniform work-group support, you have two primary options:

1. Pad the Global Work Size and Use Boundary Checks

The most common approach is rounding the global size up to the next multiple of the local work size, then discarding surplus threads inside the kernel.

Host-side calculation:

size_t local_size = 256;
size_t actual_elements = 1000;
size_t global_size = ((actual_elements + local_size - 1) / local_size) * local_size;

// Pass actual_elements as a kernel argument
clSetKernelArg(kernel, 1, sizeof(unsigned int), &actual_elements);
clEnqueueNDRangeKernel(queue, kernel, 1, NULL, &global_size, &local_size, 0, NULL, NULL);

Kernel-side guard:

__kernel void process_data(__global float* data, unsigned int total_elements) {
    size_t id = get_global_id(0);
    
    // Guard against execution on padded work-items
    if (id >= total_elements) {
        return;
    }
    
    // Core processing logic
    data[id] *= 2.0f;
}

2. Let the Runtime Determine Local Size

If your algorithm does not depend on local memory or work-group barriers, you can pass NULL for the local_work_size parameter in clEnqueueNDRangeKernel. The OpenCL implementation will automatically select a valid, optimal local work-group configuration that divides the provided global dimensions evenly.
