OpenCL Memory Strides and Hardware Prefetching

This article examines how hardware prefetchers interact with global memory access strides in OpenCL compute kernels. When OpenCL work-items access global memory, the physical stride—the step size between memory addresses requested by adjacent work-items or sequential loop iterations—dictates whether hardware prefetch mechanisms accelerate data transfer or degrade performance. Understanding this relationship reveals why certain strided access patterns trigger memory amplification, cache thrashing, and stalls on modern heterogeneous architectures.

The Mechanics of Access Strides in OpenCL

In OpenCL, global memory bandwidth is maximized when work-items within a work-group access adjacent memory addresses in parallel. This is known as a unit stride (stride-1) access pattern.

  • Unit Stride (Stride-1): Work-item \(i\) accesses address \(A\), while work-item \(i+1\) accesses address \(A + 1\).
  • Non-Unit Stride (Stride-\(N\)): Work-items access memory separated by an offset \(N\) (e.g., address \(A + (i \times N)\)), commonly found when accessing interleaved data structures like Arrays of Structures (AoS) or transposing multi-dimensional matrices.
  • Irregular/Gather Stride: Memory addresses are determined dynamically via lookup tables or pointer chasing, creating unpredictable step sizes.

How Hardware Prefetchers Function

Hardware prefetchers analyze patterns in the memory access stream to fetch data from higher-latency memory tiers (DRAM or L2) into lower-latency caches (L1 or registers) before an execution unit explicitly issues the load instruction.

  • Stream/Spatial Prefetchers: Detect consecutive cache line accesses and fetch upcoming adjacent lines.
  • Stride Prefetchers: Track history tables of instruction addresses (Program Counters) and record the distance between consecutive memory references. If a consistent delta (\(\Delta = \text{Address}_k - \text{Address}_{k-1}\)) is detected, the prefetcher issues speculative loads for \(\text{Address} + \Delta, \text{Address} + 2\Delta\), and so forth.

The Interaction Between Strides and Prefetchers

1. Coalescing vs. Prefetching Under Unit Strides

Under a unit stride, an OpenCL wavefront (or warp) issues a coalesced memory request. Hardware memory controllers group these requests into the minimum number of cache-line-sized transactions (typically 32 to 128 bytes).

Hardware prefetchers easily identify this linear, sequential progression through memory. Spatial prefetchers trigger proactive loads for the subsequent cache lines, hiding memory latency almost entirely when access patterns match the prefetcher’s lookahead distance.

2. Non-Unit Constant Strides (Small \(N\))

When work-items execute with a small non-unit stride (e.g., reading every fourth integer), two separate phenomena occur:

  • Memory Coalescing Failure: Instead of loading a single cache line that serves all work-items in a sub-group, the hardware must fetch multiple distinct cache lines to fulfill the same instruction.
  • Prefetcher Triggering: On processors with stride-aware prefetchers (such as CPUs and certain modern GPU compute units), the prefetcher adapts to the constant step size \(N\). It will speculative load future cache lines separated by \(N\).

While this avoids direct stall latency on future operations, it causes memory bandwidth amplification: the hardware fetches entire 64-byte or 128-byte cache lines only to consume a fraction of the data within them. Consequently, the prefetcher aggressively exhausts memory bus bandwidth by loading non-contiguous blocks.

3. Large or Varying Strides (Large \(N\) or Variable Deltas)

When the stride \(N\) exceeds the hardware tracking capability or the physical distance of the prefetcher's stream buffer window, performance degrades sharply:

  • Prefetch Table Thrashing: Hardware prefetch units use finite-capacity tracking tables (e.g., Reference Prediction Tables). If a work-group spawns thousands of divergent or widely spaced memory streams, the stride history table suffers constant cache evictions, causing the prefetcher to deactivate or generate incorrect speculative requests.
  • Cache Pollution: Speculative reads for large strides often arrive too late to hide latency or evict active, useful data from L1/L2 caches to store data that may not be consumed immediately.

Architectural Discrepancies: GPU vs. CPU Targets

The manifestation of this interaction varies significantly depending on the target hardware executing the OpenCL kernel:

  • CPUs as OpenCL Targets: CPU cores rely heavily on deep, aggressive multi-level stride and stream prefetchers to mask high memory latency. While a constant stride-\(N\) is frequently detected and prefetched successfully, the low cache-line utilization (bytes used versus bytes transferred) often caps compute throughput at the physical memory bus limit.
  • GPUs as OpenCL Targets: GPUs rely primarily on massive multithreading and fast context switching between wavefronts rather than deep speculative prefetchers to hide latency. Modern GPUs do feature L2 and system-level cache prefetchers, but these are optimized strictly for linear streaming. Non-unit strides break SIMD memory coalescing at the instruction level, flooding the memory pipeline with independent requests that can overwhelm the GPU's internal request queues and disable hardware prefetching logic.

Optimizing OpenCL for Prefetcher Efficiency

To ensure hardware prefetchers complement OpenCL kernel execution rather than bottleneck it:

  1. Transform AoS to SoA: Refactor data from Arrays of Structures to Structures of Arrays to eliminate artificial strides inside work-item batches.
  2. Local Memory (LDS) Staging: For unavoidable strided algorithms (like matrix transpositions), load data into __local memory using coalesced, stride-1 global loads, synchronize via barrier(CLK_LOCAL_MEM_FENCE), and perform the strided access pattern entirely inside the low-latency local scratchpad.
  3. Explicit Vector Loads: Use built-in vector types (e.g., vload4, vload8) when reading sequential elements to force the generation of wide, predictable memory transactions that help hardware stream analyzers establish reliable prefetch streams.
