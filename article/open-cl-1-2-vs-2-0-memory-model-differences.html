OpenCL 1.2 vs 2.0 Memory Model Differences

The transition from OpenCL 1.2 to OpenCL 2.0 marked a fundamental evolution in heterogeneous computing, shifting the framework from a disjoint, manually coordinated memory architecture to a unified, modern memory model. While OpenCL 1.2 required explicit data transfers and offered rudimentary synchronization primitives, OpenCL 2.0 introduced Shared Virtual Memory (SVM), adopted the formal C11/C++11 memory consistency model, integrated fine-grained atomic operations with explicit scopes, and added a generic address space. These changes significantly reduced developer boilerplate and enabled native sharing of complex data structures between host CPUs and accelerator devices.

Shared Virtual Memory (SVM)

The most prominent change in OpenCL 2.0 is Shared Virtual Memory. In OpenCL 1.2, host memory and device memory were strictly distinct address spaces. Transferring data required allocating explicit buffers on the device (cl_mem) and manually copying data back and forth using API calls like clEnqueueReadBuffer and clEnqueueWriteBuffer. This made sharing pointer-based data structures, such as linked lists or trees, impractical because pointers in host memory were invalid in device memory.

OpenCL 2.0 introduced three levels of SVM:

  • Coarse-Grained Buffer SVM: Allows the host and device to share a single virtual address range for a buffer. Synchronization is managed using explicit map/unmap enqueue commands, eliminating the need to copy data, though updates are only visible at map boundaries.
  • Fine-Grained Buffer SVM: Enables concurrent, fine-grained access to individual memory locations within an SVM buffer by both host and device without map/unmap commands.
  • Fine-Grained System SVM: Extends fine-grained access to the entire operating system virtual address space. Any standard pointer allocated via system memory allocators (like malloc) can be dereferenced directly inside a device kernel.

Alignment with the C11/C++11 Memory Model

OpenCL 1.2 lacked a formalized memory consistency model. Visibility of memory writes across different work-items, work-groups, and the host relied on broad barrier functions and implicit kernel termination boundaries.

OpenCL 2.0 directly integrated the ISO C11/C++11 memory consistency model. This defined explicit acquire-release semantics and sequential consistency across heterogeneous platforms. It introduced formal memory orders, enabling fine-grained control over compiler and hardware instruction reordering:

  • memory_order_relaxed
  • memory_order_acquire
  • memory_order_release
  • memory_order_acq_rel
  • memory_order_seq_cst

Scoped Atomic Operations

In OpenCL 1.2, atomic functions (such as atom_add and atom_xchg) were limited to 32-bit (and optionally 64-bit) integers with implicit, broad synchronization constraints.

OpenCL 2.0 introduced C11-style atomic operations that accept explicit memory order and memory scope parameters. The new memory_scope enumeration defines exactly which execution units participate in the synchronization:

  • memory_scope_work_item: Limited to the current thread.
  • memory_scope_work_group: Synchronizes threads within the same work-group.
  • memory_scope_device: Synchronizes across the entire OpenCL device.
  • memory_scope_all_svm_devices: Synchronizes across both the host CPU and all connected SVM-capable devices.

This scope hierarchy allows developers to build lock-free algorithms and concurrent queues that operate safely across the CPU-GPU boundary.

Generic Address Space

OpenCL 1.2 enforced named address spaces (__global, __local, __private, and __constant). Functions accepting pointers had to be explicitly authored or overloaded for each address space, increasing code duplication.

OpenCL 2.0 introduced a generic (unnamed) address space. A pointer declared without an address space qualifier can point to global, local, or private memory dynamically. The hardware and compiler resolve the target address space at execution time, streamlining code reuse and facilitating standard C-style pointer usage inside kernels.
