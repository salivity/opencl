OpenCL Command Queue Priority Extensions

OpenCL allows developers to prioritize specific workloads across multiple command queues primarily through the cl_khr_priority_hints extension and related vendor-specific implementations. While standard OpenCL execution operates on a first-come, first-served or out-of-order scheduling model without strict scheduling guarantees across queues, priority extensions enable the host application to mark certain command queues as high, normal, or low priority. This article explains how queue priority works in OpenCL, how to implement it, and how hardware vendors handle task prioritization.

The Priority Mechanism in OpenCL

Standard OpenCL command queues created with clCreateCommandQueue or clCreateCommandQueueWithProperties do not mandate relative execution priorities. When multiple queues submit work to the same device simultaneously, the underlying hardware scheduler interleaves commands arbitrarily or executes them in submission order.

To solve this, the Khronos Group introduced the cl_khr_priority_hints extension, which has been widely adopted or complemented by proprietary vendor mechanisms (such as those from Intel, AMD, and ARM). This extension allows applications to provide execution scheduling hints directly to the device driver when instantiating a command queue.

Implementing Queue Priorities

Queue priorities are assigned during queue creation using clCreateCommandQueueWithProperties (standardized in OpenCL 2.0 and backported to 1.2 via extensions).

1. Checking Extension Support

Before setting priority hints, the host program must query the device to verify that cl_khr_priority_hints is present in the CL_DEVICE_EXTENSIONS string:

size_t ext_size;
clGetDeviceInfo(device_id, CL_DEVICE_EXTENSIONS, 0, NULL, &ext_size);
char *extensions = (char *)malloc(ext_size);
clGetDeviceInfo(device_id, CL_DEVICE_EXTENSIONS, ext_size, extensions, NULL);

// Check if "cl_khr_priority_hints" exists in the extensions string

2. Defining Priority Properties

The extension introduces the property token CL_QUEUE_PRIORITY_KHR, which accepts three defined levels:

  • CL_QUEUE_PRIORITY_HIGH_KHR: Work submitted to this queue should be scheduled before commands from normal or low-priority queues.
  • CL_QUEUE_PRIORITY_MED_KHR: The default priority level, equivalent to standard queue creation.
  • CL_QUEUE_PRIORITY_LOW_KHR: Background tasks that should yield execution resources to higher-priority work.

3. Queue Creation Example

The priority is passed into the properties array when creating the queue:

cl_queue_properties properties[] = {
    CL_QUEUE_PRIORITY_KHR, 
    CL_QUEUE_PRIORITY_HIGH_KHR,
    0
};

cl_command_queue high_prio_queue = clCreateCommandQueueWithProperties(
    context, 
    device_id, 
    properties, 
    &err
);

Vendor Implementations and Hardware Behavior

The impact of queue priorities depends heavily on the vendor's driver stack and hardware execution model.

  • Intel: Intel heavily utilizes cl_khr_priority_hints in integrated and discrete GPUs, particularly for media processing and low-latency display tasks. When higher-priority queues submit work, the hardware command streamer prioritizes their execution dispatches over lower-priority contexts.
  • AMD: AMD historically exposed priority features through driver hints and extensions. AMD's Asynchronous Compute Engines (ACE) allow compute workloads to run concurrently with graphics. Queues designated with high priority can claim a higher proportion of compute unit wave slots.
  • ARM Mali & Mobile Vendors: Mobile GPUs frequently rely on queue prioritization to maintain smooth user interface rendering while compute-heavy machine learning inference or camera post-processing runs in the background on lower-priority queues.
  • NVIDIA: While NVIDIA supports OpenCL, its primary priority features reside within proprietary CUDA streams. In OpenCL contexts, priority hints are often mapped to simple driver-level scheduling policies or fall back to standard round-robin dispatch.

Practical Limitations and Caveats

  • Priority as a "Hint": The specification explicitly designates these priority values as "hints." Drivers and hardware schedulers are not legally required by the OpenCL specification to guarantee strict real-time preemption.
  • Preemption Granularity: Hardware capabilities dictate how fast a high-priority queue can interrupt lower-priority work. If the GPU only supports command-level preemption (waiting for a current kernel dispatch to finish), long-running kernels on a low-priority queue will still delay high-priority tasks. Finer preemption (such as instruction-level or thread-group preemption) provides much faster response times.
  • Resource Starvation: Aggressive dispatch of commands to a CL_QUEUE_PRIORITY_HIGH_KHR queue can starve tasks running on medium or low-priority queues, potentially causing host-side timeouts or latency spikes.
