OpenCL Double Buffering: Asynchronous Transfers

In high-performance computing, minimizing device idle time is critical for maximizing throughput across heterogeneous architectures. This article explains how double-buffering techniques combined with asynchronous memory operations in OpenCL enable the concurrent execution of compute kernels and data transfers. By decoupling memory operations from computation through independent command queues and event-based synchronization, developers can hide peripheral component interconnect express (PCIe) latencies and maximize hardware utilization.

The Bottleneck of Synchronous Execution

In a naive OpenCL pipeline, operations execute sequentially: the host transfers data to the device, the compute units process the data, and the host reads back the results. Because PCIe data transfers and GPU compute units utilize distinct physical pathways on the hardware, running these operations sequentially leaves one subsystem completely idle while the other works. PCIe bus latency becomes a dominant bottleneck, particularly for memory-bound workloads or applications processing large, continuous streams of data.

Principles of Double Buffering

Double buffering resolves this hardware underutilization by dividing the working dataset into smaller chunks and allocating two separate sets of device and host buffers, conventionally designated as Buffer A and Buffer B.

Instead of waiting for an entire batch to finish processing before loading the next, the system alternates between the two sets:

  • While the device executes a kernel on the data inside Buffer A, the host transfers the subsequent chunk of input data into Buffer B via Direct Memory Access (DMA).
  • Once the kernel completes on Buffer A, the roles invert: the device executes the kernel on Buffer B, while the host transfers processed results from Buffer A back to host memory and writes the next chunk of incoming data into Buffer A.

Orchestrating Asynchronous Operations in OpenCL

To achieve physical overlap, the underlying hardware must feature independent compute engines and DMA transfer engines (often full-duplex copy engines). In OpenCL, this concurrency is exposed and managed using command queues, asynchronous API commands, and event wait lists.

1. Command Queue Architecture

OpenCL commands submitted to a single in-order queue execute sequentially, precluding overlap. To enable asynchronous execution, developers can use one of two approaches:

  • Multiple In-Order Queues: Create separate in-order cl_command_queue instances pointing to the same device—typically one dedicated to memory transfers (Host-to-Device and Device-to-Host) and another dedicated to kernel execution.
  • Out-of-Order Queue: Create a single queue initialized with the CL_QUEUE_OUT_OF_ORDER_EXEC_MODE_ENABLE property, allowing the runtime to reorder independent tasks as long as dependency constraints are satisfied.

2. Non-Blocking Transfers

Memory transfers must be dispatched asynchronously to return control to the host immediately, allowing subsequent operations to be enqueued. OpenCL provides non-blocking flags for memory operations:

  • clEnqueueWriteBuffer and clEnqueueReadBuffer are called with the blocking_write or blocking_read parameter set to CL_FALSE.
  • Pinned (page-locked) host memory, allocated using CL_MEM_ALLOC_HOST_PTR or mapped via clEnqueueMapBuffer, is required to ensure that the DMA controller can access the host data directly without operating system intervention or paging delays.

3. Event-Driven Synchronization

Because queues operate asynchronously, explicit synchronization prevents race conditions—such as a kernel launching before its input data arrives, or a transfer overwriting data currently in use. OpenCL uses cl_event objects to synchronize tasks across queues.

Each enqueued operation produces an event that tracks its execution status. Subsequent commands accept an event wait list (cl_event*) and will not begin until the events in the list transition to CL_COMPLETE.

In an alternating double-buffered loop:

  1. Transfer In (Buffer B): Depends on the completion of the kernel previously reading Buffer B (if in a steady state).
  2. Kernel Execution (Buffer A): Depends on the completion of the transfer event that loaded data into Buffer A.
  3. Transfer Out (Buffer A): Depends on the completion of the kernel event that processed Buffer A.

By tracking these dependency chains, the host enqueues operations ahead of time, enabling the OpenCL runtime and hardware scheduler to execute memory transfers across the PCIe bus simultaneously with compute execution on the compute cores.
