OpenCL Built-in Kernels on Custom Accelerators

OpenCL provides built-in kernels as a standardized mechanism to expose and control non-programmable, fixed-function hardware accelerators, such as specialized digital signal processors, video decoders, and custom ASICs. Instead of compiling OpenCL C code via a JIT compiler, the host application interacts with pre-existing, hardwired execution pipelines exposed by the device driver. This article explains how custom non-programmable devices identify, declare, instantiate, and execute these built-in kernels using the OpenCL host API.

Device Discovery and Querying Capabilities

A non-programmable accelerator is typically registered with the OpenCL runtime under the device type CL_DEVICE_TYPE_CUSTOM. Because these devices lack traditional programmable compute units and C-based instruction decoders, you cannot query or compile runtime source code.

Instead, the host application queries the device for a semicolon-delimited list of hardware-supported kernel names using clGetDeviceInfo:

char kernel_names[1024];
clGetDeviceInfo(device_id, CL_DEVICE_BUILT_IN_KERNELS, sizeof(kernel_names), kernel_names, NULL);

This returns the hardware functions natively baked into the silicon, such as specific matrix multiplication blocks, cryptographic transforms, or filter pipelines.

Program Creation with Built-in Kernels

Standard OpenCL workflows use clCreateProgramWithSource or clCreateProgramWithBinary. For custom fixed-function hardware, the OpenCL API provides clCreateProgramWithBuiltInKernels:

cl_program program = clCreateProgramWithBuiltInKernels(
    context,
    1,
    &device_id,
    "custom_matrix_mult;custom_convolution",
    &err
);

This function creates a valid cl_program object tied to the target device without invoking a compiler frontend. The runtime validates the supplied kernel names against the hardware driver’s internal registry of hardwired capabilities.

Kernel Creation and Configuration

Once the program object is created, kernel instantiation follows the standard OpenCL flow. The host creates a cl_kernel object using clCreateKernel, passing the exact string identifier of the target built-in function:

cl_kernel kernel = clCreateKernel(program, "custom_matrix_mult", &err);

Argument configuration is handled via clSetKernelArg. Even though the accelerator is non-programmable, it requires input data, output destinations, and configuration flags:

clSetKernelArg(kernel, 0, sizeof(cl_mem), &input_buffer);
clSetKernelArg(kernel, 1, sizeof(cl_mem), &output_buffer);
clSetKernelArg(kernel, 2, sizeof(int), &matrix_dimension);

The underlying driver maps these arguments directly to memory-mapped registers, direct memory access (DMA) source/destination descriptors, or hardware control registers on the physical accelerator.

Execution and Dispatch

Execution on a custom accelerator is triggered using clEnqueueNDRangeKernel.

size_t global_work_size[1] = { 1 };
clEnqueueNDRangeKernel(
    command_queue,
    kernel,
    1,
    NULL,
    global_work_size,
    NULL,
    0,
    NULL,
    &execution_event
);

For strictly non-programmable hardware, the dimensional grid often requires specific constrained values (such as an NDRange of 1 or matching the exact hardware pipeline width), as defined by the vendor's device specifications.

Upon dispatch, the driver translates the enqueue command into low-level hardware interrupts, writes to control registers (such as setting a "start" bit), and initiates hardware-level DMA transfers. Synchronization, dependency tracking, and completion notifications are integrated directly into the standard OpenCL event profiling mechanism via cl_event.
