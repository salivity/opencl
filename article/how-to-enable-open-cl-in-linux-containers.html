How to Enable OpenCL in Linux Containers

Enabling OpenCL hardware acceleration inside Linux containers requires granting container processes access to host GPU device nodes, mounting userspace drivers, and configuring specific runtime environment variables. Depending on whether your hardware is Intel, AMD, or NVIDIA, you must pass interfaces such as /dev/dri and /dev/kfd alongside flags that register OpenCL Installable Client Drivers (ICD). This guide details the mandatory device nodes, permission settings, and environment variables needed to execute OpenCL workloads within Docker and Podman environments.

Essential Device Nodes

Containers share the host kernel, meaning GPU acceleration requires exposing host kernel-mode driver character devices into the container namespace.

/dev/dri (Direct Rendering Infrastructure)

The /dev/dri directory is essential for Intel and AMD graphics, as well as generic Linux Direct Rendering Manager (DRM) compute interfaces. It typically contains two types of device files:

  • cardX (e.g., /dev/dri/card0): Primary node responsible for modesetting and display output.
  • renderD128 (and subsequent numbers): Render nodes dedicated to unprivileged, display-free execution. OpenCL compute runtimes primarily rely on these nodes to submit compute queues without requiring an active X11 or Wayland session.

To pass this interface into a container:

--device /dev/dri
# Or targeting only the render node:
--device /dev/dri/renderD128:/dev/dri/renderD128

/dev/kfd (Kernel Fusion Driver)

The /dev/kfd node is required specifically for AMD hardware utilizing the ROCm (Radeon Open Compute) runtime. While AMD drivers interact with /dev/dri for memory management and DRM integration, the Kernel Fusion Driver handles user-mode compute queues, signal handling, and heterogeneous system architecture (HSA) operations.

For AMD ROCm-based OpenCL, you must expose both /dev/kfd and /dev/dri:

--device /dev/kfd --device /dev/dri

Permissions and Linux User Groups

Inside the host, device nodes under /dev/dri and /dev/kfd belong to privileged system groups—typically render or video. If the container runs as a non-root user, the container user must be mapped to matching group IDs to prevent EACCES (Permission Denied) errors.

  • Host Group Detection: Find the GIDs on your host system: 
    getent group render | cut -d: -f3
getent group video | cut -d: -f3
  • Container Attachment: Pass the detected groups to the container runtime: 
    --group-add video
--group-add render

Crucial Environment Variables

Environment variables govern OpenCL ICD selection, visibility, and platform-specific capabilities inside the container.

1. General OpenCL Environment Variables

The OpenCL standard uses an ICD loader (libOpenCL.so) to enumerate and dispatch calls to vendor-specific runtimes listed in .icd text files.

  • OCL_ICD_VENDORS: Overrides the default search path (/etc/OpenCL/vendors) for OpenCL ICD registration files. Set this if your ICD files are mounted in a non-standard container location: 
    -e OCL_ICD_VENDORS=/opt/OpenCL/vendors
  • OPENCL_VENDOR_PATH: Used by alternative loader implementations to discover .icd files: 
    -e OPENCL_VENDOR_PATH=/etc/OpenCL/vendors

2. AMD ROCm Environment Variables

For AMD hardware utilizing the ROCm OpenCL stack, several environment variables control hardware selection and runtime constraints:

  • ROCR_VISIBLE_DEVICES: Limits OpenCL execution to specific GPU IDs (e.g., 0, 1, or comma-separated indices). 
    -e ROCR_VISIBLE_DEVICES=0
  • GPU_DEVICE_ORDINAL: Legacy variable used by AMD runtime engines to target specific cards.
  • HSA_OVERRIDE_GFX_VERSION: Useful when using consumer AMD GPUs that are architectures closely related to officially supported ROCm enterprise chips (e.g., setting 10.3.0 for Navi 21/22/23 architectures): 
    -e HSA_OVERRIDE_GFX_VERSION=10.3.0

3. NVIDIA OpenCL Environment Variables

NVIDIA containers do not require direct /dev/dri binding when using the NVIDIA Container Toolkit. Instead, the runtime mounts the driver libraries and exposes the devices dynamically via environment variables:

  • NVIDIA_VISIBLE_DEVICES: Controls which GPUs are mapped into the container. Set to all or specific GPU UUIDs/indices: 
    -e NVIDIA_VISIBLE_DEVICES=all
  • NVIDIA_DRIVER_CAPABILITIES: Crucial for OpenCL. By default, some base images only enable standard CUDA compute. You must explicitly supply compute and utility to map OpenCL libraries: 
    -e NVIDIA_DRIVER_CAPABILITIES=compute,utility

4. Intel Compute-Runtime Variables

Intel NEO (Compute Runtime for OpenCL) primarily relies on the presence of /dev/dri/renderD*. However, debug and behavior flags can be configured via:

  • NEOReadDebugKeys: Enables runtime overriding via debug variables when set to 1.
  • ZEX_NUMBER_OF_CCS: Specifies the number of Compute Command Streamers exposed to the runtime on supported Intel discrete GPUs (e.g., Data Center GPU Flex or Max series).

Implementation Examples

Intel OpenCL Execution

Intel requires mapping /dev/dri, adding the relevant render group, and ensuring the intel-opencl-icd package is installed in the container image:

docker run --rm \
  --device /dev/dri \
  --group-add $(getent group render | cut -d: -f3) \
  intel/opencl:latest clinfo

AMD ROCm OpenCL Execution

AMD requires mapping both /dev/kfd and /dev/dri, along with device-level permissions and visibility declarations:

docker run --rm \
  --device /dev/kfd \
  --device /dev/dri \
  --group-add video \
  --group-add render \
  -e ROCR_VISIBLE_DEVICES=all \
  rocm/opencl:latest clinfo

NVIDIA OpenCL Execution

NVIDIA leverages the NVIDIA Container Runtime rather than manual character device passthrough:

docker run --rm \
  --gpus all \
  -e NVIDIA_DRIVER_CAPABILITIES=compute,utility \
  nvidia/opencl:runtime-ubuntu22.04 clinfo
