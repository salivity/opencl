OpenCL Work-Groups and Compute Unit Scheduling

This article provides an overview of OpenCL work-groups and their execution model on modern hardware. It explains the fundamental components that define a work-group—including work-items, shared memory, and synchronization primitives—and details how the OpenCL runtime and hardware schedulers assign and execute these groups across available compute units.

Defining an OpenCL Work-Group

In OpenCL, a computation is organized into an N-Dimensional Range (NDRange) of discrete execution units called work-items. A work-group is a coarse-grained collection of these work-items that execute the same kernel program concurrently. Work-groups can be configured in one, two, or three dimensions, reflecting the spatial layout of the data being processed.

A work-group is defined by three critical characteristics:

  1. Shared Local Memory: Work-items within the same work-group have access to a dedicated, low-latency memory space known as local memory (or shared memory in architectures like CUDA). Work-items from different work-groups cannot access each other's local memory.
  2. Barrier Synchronization: OpenCL provides execution and memory barriers (such as work_group_barrier) that allow work-items within the same work-group to synchronize their execution flow. Synchronization between distinct work-groups is not natively supported within a single kernel launch.
  3. Relative Indexing: Each work-item has a global ID representing its position within the entire NDRange, a local ID representing its coordinates inside its specific work-group, and a work-group ID identifying which group it belongs to.

How Work-Groups Are Scheduled Across Compute Units

When a kernel is enqueued, the OpenCL runtime and underlying hardware scheduler break down the total execution space into work-groups and distribute them across the device's hardware Compute Units (CUs).

1. Atomicity of Work-Group Assignment

A single work-group is strictly assigned to one Compute Unit. It cannot be subdivided across multiple CUs because the work-items within the group depend on the local memory and hardware synchronization barriers physically tied to that specific CU.

2. Resource Allocation and Occupancy

A Compute Unit can host one or more work-groups simultaneously, depending on resource availability. Before scheduling a work-group to a CU, the hardware verifies that sufficient resources exist, primarily:

  • Registers: The total register file space required by all work-items in the work-group.
  • Local Memory Allocation: The total amount of local memory requested by the kernel.
  • Hardware Contexts: The physical limit of tracking threads and groups on the CU.

If a CU has sufficient resources, it will accept multiple work-groups to maximize hardware occupancy and hide memory latency. If resources are insufficient, the pending work-groups remain in a hardware or driver dispatch queue.

3. Low-Level Execution (Sub-Groups, Wavefronts, and Warps)

Once a work-group is resident on a CU, its work-items are further grouped into SIMD (Single Instruction, Multiple Data) execution batches, known in OpenCL as sub-groups (referred to as wavefronts on AMD architectures or warps on NVIDIA architectures). The CU's instruction scheduler selects ready sub-groups and dispatches their instructions across the physical vector arithmetic logic units (ALUs).

4. Completion and Dynamic Scheduling

Work-groups are scheduled independently and can execute in any order. When all work-items of a work-group complete their execution, the CU releases the allocated local memory, registers, and tracking contexts. The hardware scheduler then immediately assigns the next available work-group from the queue to that CU until all work-groups within the NDRange are retired.
