OpenCL Device-Side Enqueue Performance Overheads

Device-side enqueue, introduced in OpenCL 2.0, allows an executing kernel to launch micro-kernels directly on the compute device without host CPU intervention. While this nested parallelism simplifies dynamic algorithms like adaptive mesh refinement or tree traversals, it introduces non-trivial performance costs. Launching fine-grained micro-kernels incurs overheads across hardware scheduling latency, memory management, synchronization tracking, and compute unit resource partitioning, often offsetting the benefits if micro-kernels are too small.

Scheduling Latency and Queue Contention

Launching a micro-kernel requires the device to construct a command packet, assign NDRange dimensions, and submit this work to a device-side command queue.

  • Command Queue Serialization: Device command queues have finite depth. When thousands of work-items simultaneously attempt to enqueue child kernels, the internal hardware scheduler encounters queue contention, leading to serialization at the enqueue site.
  • Launch Latency: Even without host-to-device roundtrip latency, the on-chip dispatch mechanisms take hundreds of clock cycles to validate arguments, configure the execution grid, and schedule the child NDRange onto compute units.

Memory Overhead and Argument Passing

Parent and child kernels do not automatically share private execution state, requiring explicit memory staging.

  • Argument Buffer Allocation: Passing arguments to child micro-kernels requires writing data to device-accessible parameter buffers. Creating and populating these parameter structures consumes global or specialized device-side scratchpad memory.
  • Context Preservation: If a parent kernel must retain its state while waiting for child micro-kernels, its register allocations and private variables must remain resident in hardware resources, which limits overall occupancy.

Divergence and Branch Penalties

In SIMD/SIMT architectures, instructions execute in lockstep across work-groups or sub-groups (warps/wavefronts).

  • Control Flow Divergence: If only a subset of work-items within a warp triggers a micro-kernel enqueue, the remaining work-items must stall until the enqueue instruction completes.
  • Non-Uniform Grid Sizing: Heterogeneous micro-kernel dimensions can fragment the GPU execution pipeline, leaving compute units underutilized if micro-kernel grids do not evenly divide into native hardware execution widths (e.g., 32 or 64 threads).

Synchronization and Event Tracking

Tracking the execution state of dynamically launched micro-kernels adds significant hardware overhead.

  • Event Object Overhead: Managing execution order requires OpenCL event objects (clk_event_t). Creating, profiling, and retiring device-side events requires tracking state in on-chip memory buffers.
  • Device Barriers: Waiting for child kernels via synchronization barriers stalls the parent work-group, keeping its compute resources (registers, local memory) pinned and unavailable to other pending work-groups.

Resource Partitioning and Occupancy Reduction

A GPU has a fixed budget of registers and local memory (LDS/SRAM) per Compute Unit (CU).

  • Register Pressure: When parent kernels and child micro-kernels run concurrently on the same compute units, they split available hardware registers. This can force register spilling into slower global memory (VRAM).
  • Occupancy Degradation: Child micro-kernels with high local resource demands can block parent work-groups from making progress, reducing the active warp count and hindering the GPU's primary latency-hiding mechanism.
