OpenCL cl_khr_depth_images: Depth Image Sampling

This article provides an overview of the cl_khr_depth_images extension in OpenCL, examining how it enhances standard image processing. It details the dedicated channel formats introduced for depth data, describes depth-comparison sampling techniques, and highlights how the extension bridges compute kernels with 3D graphics pipelines for tasks such as shadow mapping and depth-of-field rendering.

Introduction of Dedicated Depth Image Formats

Standard OpenCL implementations primarily support standard color formats with multi-channel layouts such as CL_RGBA or CL_R. The cl_khr_depth_images extension introduces the CL_DEPTH image channel order, allowing memory objects to be explicitly allocated for depth values.

The extension enables compatibility with specific depth data types, including:

  • CL_UNORM_INT16: 16-bit normalized unsigned integer depth values.
  • CL_FLOAT: 32-bit floating-point depth values.
  • Packed formats such as 24-bit normalized integers paired with stencil buffers where supported by the implementation.

When a compute kernel samples a depth image, the scalar depth value is read from the single-channel source and returned as a floating-point value.

Depth-Comparison and Shadow Sampling

The most significant functional enhancement added to OpenCL sampling capabilities is depth-comparison sampling, often referred to as percentage-closer filtering (PCF) or shadow sampling in real-time rendering.

Without this extension, a kernel developer must manually retrieve the stored depth value using coordinates, compare it against a reference depth value in software, and implement custom filtering routines to avoid harsh aliasing. cl_khr_depth_images leverages underlying GPU texture hardware to execute this operation natively.

When configured via the sampler:

  1. Reference Value Evaluation: The sampling coordinate contains an extra component representing the reference depth value (\(D_{ref}\)).
  2. Hardware Comparison: The hardware compares \(D_{ref}\) against the depth value (\(D\)) fetched from the image using comparison modes (such as less-than or equal-to).
  3. Hardware Filtering: If linear filtering is enabled, the hardware evaluates the comparison condition for adjacent texels and returns a filtered interpolation of the boolean comparison results. This produces smooth transitions directly from the hardware sampler.

Extended Built-In Read Functions

The OpenCL C shading language is extended with overloaded variants of the read_imagef built-in function to handle depth sampling.

  • Standard Depth Reads: Developers can use coordinates formatted as float2 (for 2D depth images) or float4 (for 2D depth image arrays) to read the raw scalar depth stored in the texture.
  • Comparison Reads: Built-in functions accept coordinate vectors containing the reference depth (for example, a float4 coordinate where the third component specifies \(D_{ref}\) for a 2D depth image). The return value represents the comparison factor, typically ranging from 0.0 (fully in shadow / failed test) to 1.0 (fully lit / passed test).

Graphics Interoperability and Performance

By aligning OpenCL texture sampling mechanics with OpenGL and Vulkan hardware conventions, cl_khr_depth_images removes the need for format translation. Depth buffers generated by rasterization hardware can be shared directly with OpenCL kernels as depth textures via cross-API sharing extensions (cl_khr_gl_sharing).

This allows compute kernels to perform post-processing effects—such as Screen-Space Ambient Occlusion (SSAO), custom shadow map filtering, and volumetric light scattering—with minimal memory overhead and native hardware sampling speed.
