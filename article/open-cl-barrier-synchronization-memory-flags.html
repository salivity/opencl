OpenCL Barrier Synchronization Memory Flags

This article provides an overview of the memory flags used to control memory synchronization when executing an OpenCL barrier. In OpenCL, execution barriers halt work-items within a work-group until all items reach the synchronization point. Passing specific memory fence flags to these barriers dictates whether cached or queued reads and writes in local, global, or image memory spaces become visible to other work-items before execution resumes.

Primary Memory Fence Flags for barrier()

In OpenCL 1.x and OpenCL 2.x/3.0, the traditional barrier() function takes a bitfield parameter of type cl_mem_fence_flags. These flags define which memory hierarchies must complete pending operations before any work-item continues past the barrier.

1. CLK_LOCAL_MEM_FENCE

The CLK_LOCAL_MEM_FENCE flag ensures that all reads and writes to local memory (__local address space) issued by any work-item in the work-group before the barrier are fully committed and visible to all other work-items in the same work-group.

  • Use case: Staging data in shared local memory (scratchpad memory) before reading it collaboratively across the work-group.

2. CLK_GLOBAL_MEM_FENCE

The CLK_GLOBAL_MEM_FENCE flag ensures that all reads and writes to global memory (__global address space) made by work-items in the work-group prior to the barrier are committed and visible across the work-group.

  • Use case: Ordering writes to global buffers between execution phases without ending the kernel launch. Note that while this ensures visibility within the current work-group, it does not guarantee global visibility across different work-groups.

3. Combining Flags (CLK_LOCAL_MEM_FENCE | CLK_GLOBAL_MEM_FENCE)

Flags can be combined using a bitwise OR operation. Supplying both flags forces the synchronization of both local memory buffers and global device memory simultaneously before any work-item passes the barrier.

OpenCL 2.0+ Extended Memory Flags and Scopes

Starting with OpenCL 2.0, the API introduced work_group_barrier() and fine-grained memory models, offering additional flags and explicit memory scopes.

Additional Fence Flag: CLK_IMAGE_MEM_FENCE

OpenCL 2.0 added the CLK_IMAGE_MEM_FENCE flag. When passed to a barrier, it guarantees that reads and writes targeting image objects complete and become visible to other work-items.

Memory Scope Modifiers (memory_scope)

While the memory flags specify what memory is synchronized, OpenCL 2.0+ introduces memory scopes to control who participates in the visibility of the barrier:

  • memory_scope_work_item: Synchronizes operations locally for the calling thread only.
  • memory_scope_sub_group: Limits synchronization visibility to the work-items within the immediate sub-group (hardware warp or wavefront).
  • memory_scope_work_group: The default scope behavior, synchronizing visibility across all work-items inside the work-group.
  • memory_scope_device: Extends visibility across all work-items running on the entire compute device.
  • memory_scope_all_svm_devices: Extends visibility across multiple devices sharing Shared Virtual Memory (SVM).

Execution Rules and Best Practices

  • Uniform Execution: Every work-item in a work-group must execute the barrier. Placing a barrier inside conditional branches (if/else) that diverge within a work-group results in undefined behavior or hardware deadlocks.
  • Cost Management: Using CLK_GLOBAL_MEM_FENCE generally incurs a higher hardware latency cost than CLK_LOCAL_MEM_FENCE, as global memory accesses often require flushing cache lines to device RAM. Only specify the flags strictly required by your algorithm's data dependencies.
