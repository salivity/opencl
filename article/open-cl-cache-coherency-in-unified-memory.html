OpenCL Cache Coherency in Unified Memory

This article explores how OpenCL maintains cache coherency across unified host-device memory architectures. It details the mechanisms governed by OpenCL’s Shared Virtual Memory (SVM) specifications, the functional differences between coarse-grained and fine-grained memory sharing, the use of explicit mapping commands, and the role of memory consistency models—including atomic operations and memory fences—in synchronizing data between host CPUs and device GPUs.

The Challenge of Unified Memory Coherency

In heterogeneous systems where the CPU (host) and GPU or accelerator (device) share an address space, maintaining a consistent view of data is complex. Both processors maintain their own independent, multi-tiered cache hierarchies (L1, L2, L3). Without active management, writes executed by the host can remain trapped in its local caches, leaving the device to read stale data, and vice versa.

OpenCL handles this synchronization primarily through its Shared Virtual Memory (SVM) framework, introduced in OpenCL 2.0, which balances hardware capabilities with explicit software management.

Shared Virtual Memory (SVM) Levels

OpenCL defines three distinct levels of SVM, each handling cache coherency differently:

  1. Coarse-Grained Buffer SVM: Coherency is maintained strictly at kernel execution boundaries using explicit software synchronization. Memory regions are allocated to share virtual addresses, but hardware cache coherency is not assumed. The OpenCL runtime relies on map and unmap commands (clEnqueueSVMMap and clEnqueueSVMUnmap). Mapping a region prompts the driver to flush the device's write caches and invalidate the host's read caches, allowing the host to safely access the data. Unmapping reverses the process, flushing the host’s modified caches back to system memory before the device kernel launches.

  2. Fine-Grained Buffer SVM: Coherency operates at the granularity of individual bytes or cache lines within designated SVM buffers. Under this model, host and device can access the buffer simultaneously without explicit map and unmap commands. Coherency is guaranteed either through underlying hardware cache coherency (such as integrated GPU-CPU architectures or cache-coherent interconnects) or through targeted driver-managed memory flushes executed alongside OpenCL synchronization events.

  3. Fine-Grained System SVM: This extends fine-grained coherency beyond pre-allocated OpenCL buffers to the entire operating system virtual address space. Any standard pointer allocated via standard system allocators (like malloc) can be passed to an OpenCL kernel. This model relies directly on system hardware features, such as Page Address Space IDs (PASID), PCIe Address Translation Services (ATS), or coherent bus protocols (such as CXL or AMD Infinity Fabric), ensuring hardware-level snooping or directory-based coherency across all host and device caches.

The OpenCL Memory Consistency Model

For fine-grained access without map/unmap commands, OpenCL applies a memory consistency model adapted from the C11 and C++11 memory models. This model defines precisely when modifications made by one processing unit become visible to another:

  • Acquire and Release Semantics: OpenCL relies on acquire-release synchronization to order memory operations. A release fence or atomic operation forces all prior writes in the local processor’s pipeline and private caches to be flushed out to a globally visible memory state. An acquire operation invalidates stale local cache lines, ensuring subsequent reads fetch the newly updated values from memory.
  • Atomic Operations: OpenCL provides atomic operations (such as atomic_store, atomic_load, and read-modify-write functions) configured with specific memory scopes: memory_scope_work_group, memory_scope_device, or memory_scope_all_svm_devices. Using memory_scope_all_svm_devices instructs the hardware memory controller to coordinate cache line invalidations and write-backs across both the host CPU and all connected OpenCL devices.

Hardware vs. Software Execution

The specific mechanism used to maintain coherency depends on the underlying system topology:

  • Discrete Systems: On systems with discrete GPUs over traditional PCIe buses that lack hardware cache coherency, OpenCL drivers compensate by translating fine-grained access markers into targeted DMA transfers, page-fault handling, and explicit cache line flushes.
  • Integrated Systems: On systems-on-chip (SoCs) or systems with hardware-coherent interconnects, cache coherency is handled at the hardware level. Cache-coherency protocols (such as MESI/MOESI variants) snoop memory buses and invalidate or update shared cache lines across CPU and GPU cores automatically as memory accesses occur. In these environments, OpenCL's software layer simply maps execution commands to the corresponding CPU/GPU hardware fence instructions.
