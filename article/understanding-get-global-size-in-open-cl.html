Understanding get_global_size in OpenCL

In OpenCL, the get_global_size built-in function informs a running kernel of the total number of work-items allocated across the entire execution space along a specified dimension. By providing the kernel with the global dimensions of the NDRange (N-Dimensional Range), it enables each parallel instance to determine boundaries, compute global data offsets, and safely map compute threads to data elements.

The NDRange and Execution Dimensions

When a host application enqueues an OpenCL kernel using clEnqueueNDRangeKernel, it defines the overall problem space as an NDRange of 1, 2, or 3 dimensions. Each point within this space is executed as an individual work-item.

The get_global_size function provides direct access to the size of this domain from within the kernel:

size_t get_global_size(uint dimindx);

The parameter dimindx specifies the dimension index:

  • 0 queries the size along the X-dimension.
  • 1 queries the size along the Y-dimension.
  • 2 queries the size along the Z-dimension.

The function returns the total number of global work-items configured for that specific axis.

Mapping Data and Linear Indexing

Parallel programs frequently map multi-dimensional execution grids to flat, linear memory buffers. While get_global_id identifies the current work-item's location along a specific axis, get_global_size provides the width or depth required to calculate memory strides.

For example, when processing a 2D image mapped to a 1D buffer, the linear index is computed as:

size_t x = get_global_id(0);
size_t y = get_global_id(1);
size_t width = get_global_size(0);

size_t global_index = y * width + x;

Here, get_global_size(0) informs the kernel of the row pitch, ensuring each work-item accesses the correct memory address.

Boundary Checking and Data Protection

Host programs often pad global NDRange sizes to multiples of the local work-group size to optimize hardware utilization. When this happens, the total number of launched work-items can exceed the actual data size.

Kernels use get_global_size—or values passed relative to it—to ensure work-items do not access memory beyond allocated buffer limits:

__kernel void process_data(__global float* data, uint actual_data_length) {
    size_t id = get_global_id(0);

    // Guard against out-of-bounds access
    if (id < actual_data_length) {
        data[id] *= 2.0f;
    }
}

Supporting Grid-Stride Loops

When the dataset is larger than the maximum number of concurrent work-items supported by the hardware, developers use grid-stride loops. Instead of launching one work-item per data element, a fixed grid is launched where each work-item iterates through the data in steps equal to the total execution size:

__kernel void stride_kernel(__global float* data, uint n) {
    size_t global_id = get_global_id(0);
    size_t total_workers = get_global_size(0);

    for (size_t i = global_id; i < n; i += total_workers) {
        data[i] = data[i] + 1.0f;
    }
}

In this pattern, get_global_size informs the kernel of the total stride length, allowing the execution domain to cleanly sweep across arbitrary data sizes regardless of hardware limitations.
