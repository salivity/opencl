atomic_work_item_fence Guarantees in OpenCL 2.0

In OpenCL 2.0, the atomic_work_item_fence function enforces explicit memory ordering and synchronization constraints across work-items without requiring a direct read-modify-write operation. By acting as a standalone memory barrier, it ensures that memory operations initiated by a work-item become visible to other work-items according to predefined memory scopes and ordering semantics. This article details the synchronization guarantees provided by atomic_work_item_fence, covering its memory domain flags, ordering consistency models, visibility scopes, and how it establishes formal "happens-before" relationships.

Function Signature and Core Mechanism

The function is defined as:

void atomic_work_item_fence(cl_mem_fence_flags flags, 
                            memory_order order, 
                            memory_scope scope);

Unlike basic work-group barriers (work_group_barrier), which also synchronize execution flow, atomic_work_item_fence synchronizes memory operations exclusively. Work-items do not wait for each other to reach the fence; instead, the fence restricts the hardware and compiler from reordering memory accesses across the fence boundary.

Memory Domain Guarantees (flags)

The flags argument determines which address spaces are affected by the fence:

  • CLK_GLOBAL_MEM_FENCE: Enforces ordering for loads and stores to global memory.
  • CLK_LOCAL_MEM_FENCE: Enforces ordering for loads and stores to local (shared) memory.
  • CLK_IMAGE_MEM_FENCE: Enforces ordering for reads and writes to OpenCL image objects.

Bitwise OR operations can combine these flags (e.g., CLK_GLOBAL_MEM_FENCE | CLK_LOCAL_MEM_FENCE) to enforce simultaneous ordering guarantees across multiple memory regions.

Memory Ordering Semantics (order)

OpenCL 2.0 adopts the C11/C++11 memory model. The order parameter defines how operations before and after the fence are ordered relative to one another:

  • memory_order_relaxed: Provides no ordering guarantees. It ensures atomicity if used with atomic variables, but memory accesses can freely move across the fence.
  • memory_order_acquire: Prevents subsequent reads and writes in the program order from being hoisted before the fence. It is typically paired with an atomic read to ensure data updated by another work-item becomes visible.
  • memory_order_release: Prevents preceding reads and writes in the program order from being sunk after the fence. It is used before an atomic write to publish shared data safely.
  • memory_order_acq_rel: Combines both acquire and release semantics. Preceding memory accesses cannot pass below the fence, and subsequent memory accesses cannot pass above it.
  • memory_order_seq_cst (Sequentially Consistent): Enforces memory_order_acq_rel guarantees while also guaranteeing a globally consistent total ordering of all sequentially consistent operations across the specified scope.

Scope Guarantees (scope)

The scope parameter defines the boundary within the execution hierarchy where the ordering guarantees apply:

  • memory_scope_work_item: Ordering is restricted solely to the calling work-item. It prevents compiler reordering but does not synchronize across execution units.
  • memory_scope_work_group: Guarantees that the ordering constraints are visible to all work-items within the same work-group.
  • memory_scope_device: Guarantees visibility and ordering across all work-groups executing on the same OpenCL device.
  • memory_scope_all_svm_devices: Extends ordering guarantees across multiple devices and the host CPU within a Shared Virtual Memory (SVM) system.

Establishing the "Synchronizes-With" Relationship

A standalone fence does not synchronize with another standalone fence on its own. Instead, atomic_work_item_fence establishes an inter-thread synchronization sequence when paired with atomic operations:

  1. Release Sequence: Work-item A writes non-atomic or atomic data to memory, executes atomic_work_item_fence(..., memory_order_release, scope), and then performs an atomic write (even with memory_order_relaxed) to a flag variable.
  2. Acquire Sequence: Work-item B reads the flag variable using an atomic read (even with memory_order_relaxed), evaluates the condition, and immediately executes atomic_work_item_fence(..., memory_order_acquire, scope).

When Work-item B observes the value written by Work-item A, a synchronizes-with relationship is established. Consequently, all memory operations performed by Work-item A prior to its release fence are guaranteed to happen-before and be fully visible to any memory operations executed by Work-item B after its acquire fence.
