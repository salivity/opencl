OpenCL write_imageui Unsigned Integer Guide

The write_imageui built-in function in OpenCL is designed to store unnormalized unsigned integer pixel data into specific coordinates of an image object. This article covers how write_imageui accepts a 4-component vector, maps color channels according to the image format, handles precision down-conversion to underlying image types, and requires exact integer coordinate addressing to ensure memory-safe operations.

Function Signature and Inputs

In OpenCL C, write_imageui is overloaded across various dimensionalities (1D, 2D, 3D, and image arrays). A typical 2D image signature appears as:

void write_imageui(image2d_t image, int2 coord, uint4 color);

The function expects three primary arguments:

  • image: A valid OpenCL image memory object qualified with the __write_only or __read_write access qualifier.
  • coord: An integer-based coordinate vector (int, int2, or int4) specifying the exact pixel location. Unlike normalized floating-point reads, image writes always require unnormalized integer coordinates.
  • color: A uint4 vector containing the four data components \((x, y, z, w)\) to be written into the pixel.

Absence of Float Normalization

Unlike write_imagef, which expects floating-point values in the range \([0.0, 1.0]\) and converts them to fixed-point representations, write_imageui treats data as pure, unnormalized unsigned integers. The values passed in the uint4 vector are preserved directly as integer values and are not scaled by the maximum integer representation of the target channel format.

Target Channel Data Types and Down-Conversion

The write_imageui function is explicitly intended for image formats configured with integer channel data types:

  • CL_UNSIGNED_INT8
  • CL_UNSIGNED_INT16
  • CL_UNSIGNED_INT32

When writing to an image configured with CL_UNSIGNED_INT32, each 32-bit unsigned integer component in the color vector maps directly to the corresponding channel in device memory with full bit-level fidelity.

When writing to lower-precision formats like CL_UNSIGNED_INT8 or CL_UNSIGNED_INT16, OpenCL converts the 32-bit unsigned integers from the uint4 vector down to the destination bit-width. Depending on the OpenCL implementation and specification conformance, values exceeding the maximum representable capacity (\(255\) for 8-bit, \(65535\) for 16-bit) are truncated to the least significant bits or clamped to the maximum range. Passing values within the native limits of the format guarantees lossless conversion.

Channel Ordering and Component Mapping

The components of the color vector \((x, y, z, w)\) map to the standard color channels \((R, G, B, A)\). How these values are stored depends on the image_channel_order set during image creation:

  • Single-channel formats (e.g., CL_R): Only the color.x component is written to memory. The y, z, and w components are discarded.
  • Dual-channel formats (e.g., CL_RG): The color.x and color.y components are stored; the z and w components are ignored.
  • Three-channel formats (e.g., CL_RGB): The color.x, color.y, and color.z components are written; color.w is ignored.
  • Four-channel formats (e.g., CL_RGBA): All four components \((x, y, z, w)\) are written to their respective channels.

If an image format uses an alternative arrangement such as CL_BGRA or CL_ARGB, OpenCL automatically handles the swizzling so that color.x corresponds to Red, color.y to Green, color.z to Blue, and color.w to Alpha.

Coordinate Addressing and Boundary Safety

Coordinates provided to write_imageui must fall within the defined dimensions of the image: \(0 \le x < \text{width}\), \(0 \le y < \text{height}\), and \(0 \le z < \text{depth}\). OpenCL image write functions do not support samplers or addressing modes like wrap-around or clamp-to-edge. Supplying coordinates outside the image bounds results in undefined behavior, which can cause silent data corruption or GPU hardware faults. Boundary validation must be implemented manually within the kernel before invoking write_imageui.
