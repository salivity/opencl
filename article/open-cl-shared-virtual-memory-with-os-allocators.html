OpenCL Shared Virtual Memory with OS Allocators

This article examines the mechanisms that allow OpenCL to access and process data residing in standard virtual memory regions managed by operating system allocators like malloc, new, or mmap. By bridging host and device address spaces through features like Shared Virtual Memory (SVM), hardware translation services, and unified coherency models, OpenCL eliminates the need for manual buffer copies and pointer translations across heterogeneous compute devices.

Fine-Grained System Shared Virtual Memory (SVM)

The primary OpenCL mechanism that allows execution on host OS-managed virtual memory is Fine-Grained System SVM, introduced in OpenCL 2.0.

OpenCL defines three tiers of Shared Virtual Memory:

  • Coarse-Grained Buffer SVM: Shares virtual addresses at the buffer level, requiring explicit map and unmap operations to synchronize access.
  • Fine-Grained Buffer SVM: Allows concurrent read/write operations at a byte level using OpenCL-specific allocators (clSVMAlloc).
  • Fine-Grained System SVM: Extends fine-grained access to the entire host virtual address space.

Under Fine-Grained System SVM, developers can pass pointers allocated via standard OS memory functions (such as malloc in C or std::allocator in C++) directly into OpenCL kernels without reallocating through the OpenCL runtime or creating explicit cl_mem buffer objects.

Address Translation: IOMMU, ATS, and PRI

To read and write OS virtual addresses, the compute device must translate virtual addresses into physical addresses managed by the host memory controller. This is accomplished via hardware-level address translation interfaces:

  1. IOMMU / SMMU Integration: On integrated processors (such as APUs), the GPU shares the system MMU or interfaces directly with an Input-Output Memory Management Unit (IOMMU), enabling the GPU to query the CPU's existing page tables directly.
  2. PCIe Address Translation Services (ATS): Discrete accelerators communicate with the host via PCIe ATS. When a kernel references a virtual address, the device requests the corresponding physical address from the host root complex.
  3. Page Request Interface (PRI): If the requested memory page is not yet resident in physical RAM or has been paged out by the OS, PRI allows the device to trigger a page fault on the host CPU. The operating system handles the fault, maps the page into physical memory, and informs the device to resume execution.

Heterogeneous Memory Management (HMM)

At the operating system level, frameworks such as Linux's Heterogeneous Memory Management (HMM) provide the infrastructure required for Fine-Grained System SVM. HMM mirrors process page tables to device-specific page tables and enables:

  • Demand Paging: Device drivers can mirror CPU page tables on demand without pinning all host memory ahead of time.
  • Page Migration: Operating systems can transparently migrate pages between host system RAM and device-local high-bandwidth memory (VRAM) while retaining the original virtual address.

Cache Coherency and Atomic Synchronization

Accessing OS-allocated virtual memory requires consistent views of memory across CPU and device caches. OpenCL relies on:

  • Hardware Coherent Interconnects: Interconnect protocols (such as PCIe with CXL, CCIX, or proprietary coherent buses) maintain hardware-level cache coherency between CPU caches and device caches.
  • C11/OpenCL 2.0 Atomics: OpenCL kernels use memory scopes (such as memory_scope_all_svm_devices) and atomic operations consistent with the C11 memory model. This ensures that modifications made by the GPU to OS-allocated memory are correctly ordered and visible to host CPU threads without requiring manual cache flush operations.
