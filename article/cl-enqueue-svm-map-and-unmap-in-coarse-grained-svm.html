clEnqueueSVMMap and Unmap in Coarse-Grained SVM

In OpenCL, Shared Virtual Memory (SVM) simplifies heterogeneous programming by allowing the host and device to share a unified virtual address space. In coarse-grained buffer SVM, hardware cache coherency between the host CPU and the OpenCL device is not maintained automatically during execution. This article explains the roles of clEnqueueSVMMap and clEnqueueSVMUnmap, demonstrating how they establish memory consistency, coordinate buffer ownership, and ensure safe data access between the host and device.

Understanding Coarse-Grained SVM Constraints

Coarse-grained SVM guarantees that the host and device use identical pointer values to reference data, eliminating the need to translate between host pointers and cl_mem objects. However, synchronization and cache coherence are bounded at the granularity of OpenCL commands.

Because the host and device do not maintain automatic hardware-level cache snooping or page synchronization in coarse-grained mode, concurrent access to the same memory region causes race conditions and undefined behavior. Explicit synchronization points are required to define when the host owns the memory and when the device owns the memory.

The Role of clEnqueueSVMMap

clEnqueueSVMMap transfers memory ownership of an SVM allocation from the OpenCL device back to the host CPU. Its primary responsibilities include:

  1. Enforcing Execution Order: It enqueues a command into the OpenCL command queue that waits for preceding device operations (such as compute kernels) targeting that SVM allocation to complete.
  2. Synchronizing Caches: It instructs the OpenCL runtime and driver to flush device caches and invalidate host CPU caches. This ensures that any modifications made by an OpenCL kernel are completely visible to the host.
  3. Granting Host Access Rights: Depending on the flags provided (CL_MAP_READ, CL_MAP_WRITE, or CL_MAP_WRITE_INVALIDATE_REGION), it prepares the memory region so the host can safely read or overwrite the memory using standard CPU pointers.

If clEnqueueSVMMap is set to blocking (CL_TRUE), the function returns only after cache synchronization is complete, allowing immediate CPU access. If non-blocking (CL_FALSE), the host must wait on an associated event before accessing the pointer.

The Role of clEnqueueSVMUnmap

Once the host finishes reading or modifying the SVM buffer, it must release control before enqueuing any subsequent device commands that reference that data. clEnqueueSVMUnmap handles this transition:

  1. Flushing Host Writes: It forces any updates made by the CPU out of host caches and into memory accessible by the OpenCL device.
  2. Relinquishing Host Access: It informs the OpenCL runtime that the CPU has completed its access to the specified pointer region.
  3. Unblocking Dependent Device Commands: Subsequent commands in the command queue (such as next-stage kernels) that depend on this unmap event can safely proceed, assured that they will operate on the latest data written by the CPU.

Typical Workflow Pattern

A standard coarse-grained SVM pipeline follows a strict handoff sequence:

  1. Allocation: Memory is created using clSVMAlloc without the CL_MEM_SVM_FINE_GRAIN_BUFFER flag.
  2. Device Processing: An OpenCL kernel executes, passing the SVM pointer via clSetKernelExecInfo and clSetKernelArgSVMPointer.
  3. Acquisition (Map): The application calls clEnqueueSVMMap to wait for the kernel to finish and update host visibility.
  4. Host Processing: The CPU reads or modifies the buffer using normal pointer dereferencing.
  5. Release (Unmap): The application calls clEnqueueSVMUnmap to flush CPU writes back to device-visible memory.
  6. Further Execution or Deallocation: The device can run additional kernels on the updated data, or the host can release the allocation using clSVMFree.

Without explicit mapping and unmapping, coarse-grained SVM workflows will suffer from stale reads, incomplete writes, and memory corruption due to unsynchronized hardware caches.
