clCreateProgramWithBuiltInKernels for Fixed-Function Blocks

This article explains the purpose and architectural role of the clCreateProgramWithBuiltInKernels function in the OpenCL framework. It specifically addresses how developers use this function to expose and orchestrate non-programmable, fixed-function hardware blocks within a standardized OpenCL pipeline, bypassing runtime compilation while preserving unified memory and execution management.

Standard OpenCL workflows target programmable processors such as CPUs, GPUs, and DSPs using clCreateProgramWithSource for runtime compilation or clCreateProgramWithBinary for pre-compiled device binaries. However, modern heterogeneous System-on-Chips (SoCs) and FPGA accelerators frequently feature dedicated, fixed-function hardware blocks—such as video decoders, cryptographic engines, image signal processors (ISPs), and specialized neural processing units. These components are physically hardwired or restricted to microcode, meaning they cannot ingest arbitrary OpenCL C code or run traditional compilation pipelines.

The clCreateProgramWithBuiltInKernels function bridges this gap by creating an OpenCL program object containing a predefined list of kernel names recognized directly by the target device or driver. Instead of providing source code or intermediate binaries, the developer specifies the target devices and the exact names of the built-in kernels they intend to invoke.

When targeting fixed-function accelerators, the primary purposes of clCreateProgramWithBuiltInKernels include:

  • Enabling Non-Programmable Silicon: It allows fixed-function hardware to be integrated into an OpenCL context. The host application can configure and execute hardware tasks as if they were standard compute kernels, using standard OpenCL APIs like clEnqueueNDRangeKernel.
  • Eliminating Compilation Overhead: Because the operational logic is embedded in the physical silicon or driver firmware, no dynamic compilation, link step, or code generation is required. This drastically reduces initialization time and program build latency.
  • Providing a Unified Memory and Execution Model: Fixed-function blocks can share data buffers (cl_mem) and synchronization mechanisms (cl_event) with fully programmable devices within the same context. A pipeline can, for example, capture an image, process it via a fixed-function hardware block, and immediately feed the output into a programmable GPU kernel with zero-copy overhead.
  • Standardized Hardware Discovery: Devices expose their supported fixed-function capabilities through the CL_DEVICE_BUILT_IN_KERNELS query via clGetDeviceInfo. This allows host software to dynamically discover available hardware routines at runtime and instantiate them deterministically using clCreateProgramWithBuiltInKernels.
