How Multiple OpenCL Vendors Coexist on One System

Modern computer systems frequently feature heterogeneous hardware configurations, such as an Intel CPU alongside an NVIDIA discrete GPU and an AMD accelerator. To allow these disparate devices to function under a unified programming interface, OpenCL relies on an architecture known as the Installable Client Driver (ICD) model. Through the centralized OpenCL ICD Loader and platform-specific registration files, an operating system can identify, expose, and dispatch commands to multiple distinct vendor drivers simultaneously without collision.

The Role of the ICD Loader

At the center of multi-vendor coexistence is the OpenCL ICD Loader. Instead of linking applications directly to a specific vendor's driver library (such as nvopencl.dll or libamdocl64.so), developers link their applications against a generic OpenCL library (OpenCL.dll on Windows or libOpenCL.so on Linux).

The ICD Loader acts as an abstraction layer and dynamic dispatcher. When an OpenCL application starts, the ICD Loader scans the operating system for installed vendor drivers, loads each driver into memory, and constructs a unified list of available platforms.

Vendor Driver Registration

To notify the ICD Loader of their presence, hardware vendors register their dynamic libraries during driver installation using standardized operating system locations:

  • Linux: Drivers place a plain text file with a .icd extension inside the /etc/OpenCL/vendors/ directory. Each .icd file contains the absolute path or library name of the vendor’s shared object (for example, /usr/lib/x86_64-linux-gnu/libnvidia-opencl.so.1).
  • Windows: Drivers register their dynamic-link libraries (DLLs) in the Windows Registry under the key: HKEY_LOCAL_MACHINE\SOFTWARE\Khronos\OpenCL\Vendors A DWORD value of 0 is assigned to each entry, where the value name is the full path to the vendor-specific OpenCL DLL.

Because each vendor writes to its own isolated file or registry key, installations and updates from one vendor do not overwrite or interfere with another.

Discovery and the Dispatch Table

When an application calls clGetPlatformIDs, the ICD Loader performs the following sequence:

  1. Enumeration: It reads the registration directory or registry key to detect all installed vendor drivers.
  2. Loading: It opens each vendor library dynamically using standard system routines (dlopen on POSIX systems or LoadLibrary on Windows).
  3. Validation: It verifies that each library exposes the required Khronos ICD extension function, clIcdGetPlatformIDsKHR.
  4. Aggregation: It queries each vendor driver for its available platforms and returns the combined list of platforms to the application.

To route function calls accurately, OpenCL platforms and handles (such as contexts, command queues, and memory objects) contain a pointer to a dispatch table as their first member. When an application invokes an OpenCL API call—such as clEnqueueNDRangeKernel—the ICD Loader inspects the target handle, retrieves the vendor-specific dispatch table, and forwards the execution directly to that vendor's implementation.

Application Control

Once the ICD Loader exposes the aggregated platforms, the application determines how they are utilized. An application can iterate through the available platforms, query device capabilities (such as whether a device is an integrated GPU, a discrete GPU, or a multicore CPU), and selectively create separate OpenCL contexts for each vendor's hardware. This architecture ensures complete vendor coexistence, allowing a single program to distribute workloads across completely different hardware architectures concurrently.
