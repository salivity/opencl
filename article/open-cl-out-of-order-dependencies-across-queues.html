OpenCL Out-of-Order Dependencies Across Queues

Managing execution dependencies across distinct command queues in OpenCL relies on event objects (cl_event) and event wait lists. Even when queues are configured with CL_QUEUE_OUT_OF_ORDER_EXEC_MODE_ENABLE, OpenCL allows developers to explicitly define a Directed Acyclic Graph (DAG) of execution. By passing events generated from one queue into the wait lists of commands in another queue, the OpenCL runtime coordinates cross-queue synchronization at the device driver level without requiring host-side synchronization stalls.

The Role of Event Objects

In OpenCL, every enqueued command—such as clEnqueueNDRangeKernel, clEnqueueReadBuffer, or clEnqueueCopyBuffer—accepts an optional pointer to return a cl_event. This event acts as a synchronization token that transitions through specific execution states: CL_QUEUED, CL_SUBMITTED, CL_RUNNING, and finally CL_COMPLETE.

When an operation is enqueued into an out-of-order queue (Queue A), it returns an event. That event can immediately be passed to a command enqueued into a different queue (Queue B), establishing an explicit dependency.

Event Wait Lists

Most enqueue functions accept an array of event pointers (event_wait_list) and a count (num_events_in_wait_list).

When Queue B receives a command with an event wait list containing an event from Queue A:

  1. The command in Queue B enters the queue immediately.
  2. The OpenCL runtime ensures the command does not transition to CL_RUNNING until the specified event from Queue A reaches CL_COMPLETE.
  3. Other independent commands in Queue B (if Queue B is also out-of-order) can execute concurrently or out-of-sequence, provided they do not depend on incomplete events.

This mechanism avoids blocking the host CPU, allowing asynchronous scheduling directly handled by the GPU or OpenCL driver.

Synchronization Markers and Barriers

OpenCL provides synchronization primitives to streamline dependency management across multiple queues:

  • clEnqueueMarkerWithWaitList: Enqueues a marker command that waits for a list of events to complete before signaling its own event. This is ideal for aggregating multiple dependencies across multiple queues into a single cl_event token.
  • clEnqueueBarrierWithWaitList: Enqueues a barrier in a target queue. In an out-of-order queue, this barrier ensures that all previously enqueued commands within that specific queue, as well as any external events provided in the wait list, must complete before any subsequent commands in that queue are allowed to execute.

Scope and Limitations

For cross-queue dependency tracking using events to work, all participating command queues must reside within the same OpenCL context (cl_context). The queues may target the same device or different devices, provided those devices belong to that shared context.

If queues belong to distinct OpenCL contexts, events cannot be shared directly. In such scenarios, cross-queue dependencies must be resolved through host-side blocking mechanisms, such as clWaitForEvents or clFinish.
