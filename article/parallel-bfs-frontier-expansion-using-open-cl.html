Parallel BFS Frontier Expansion Using OpenCL

Parallel Breadth-First Search (BFS) implementations in OpenCL rely on frontier queue expansion to concurrently process graph levels across massively parallel compute units. In parallel BFS, the frontier consists of vertices discovered at the current depth whose unvisited neighbors must be explored to form the next depth's frontier. Expanding this queue efficiently on a GPU requires managing irregular graph topologies, synchronizing parallel memory writes, and calculating dynamic queue offsets using parallel prefix scans to maintain high memory throughput and prevent race conditions.

Graph Representation in Device Memory

To facilitate efficient memory access patterns within an OpenCL kernel, graphs are commonly stored using the Compressed Sparse Row (CSR) format. The CSR format represents the graph using two primary global memory arrays:

  • Row Offsets (vertex_offsets): Points to the start and end indices of each vertex's adjacency list.
  • Column Indices (edge_targets): Stores the actual target neighbor IDs continuously in memory.

A third array, the status or visited array (often a bitmask or integer array), tracks visited states to avoid cycles and redundant processing.

The Frontier Expansion Pipeline

Expanding the frontier queue from depth \(k\) to depth \(k+1\) typically follows a multi-phase or kernel-driven pipeline.

1. Degree Identification and Work-Item Mapping

At the start of an iteration, an OpenCL work-item (or work-group) is assigned to a vertex currently in the active frontier array. The work-item queries the CSR row offsets to determine the vertex's degree (number of outgoing edges). Because natural graphs often exhibit skewed degree distributions, mapping a single work-item to a single high-degree vertex can cause severe thread divergence. More advanced implementations map high-degree vertices to entire work-groups and low-degree vertices to individual work-items.

2. Prefix Scan for Output Indexing

Because vertices have varying numbers of neighbors, work-items cannot deterministically write discovered neighbors into a contiguous global array without knowing where their block of memory starts. An exclusive parallel prefix sum (scan) is performed on the degree counts of all active vertices. This scan calculates the exact write offset for each work-item in an intermediate or next-frontier queue, guaranteeing contiguous memory writes and eliminating the serialization bottleneck of atomic counters.

3. Neighbor Inspection and Duplicate Filtering

Once write offsets are determined, work-items iterate through the adjacency lists in the edge_targets array. For each neighbor:

  • The work-item inspects the global visited array.
  • To prevent multiple parallel threads from claiming the same newly discovered node, the thread executes an atomic primitive, such as atomic_xchg or atomic_cmpxchg, on the neighbor's visited flag.
  • If the atomic operation succeeds (confirming the node was unvisited), the neighbor is marked as visited and qualified for inclusion in the next frontier.

4. Queue Compaction

Because many neighbors are already visited, allocating queue space strictly based on degree leads to a sparse array containing invalid entries. To avoid processing empty slots in subsequent iterations, OpenCL implementations compact the queue.

Compaction can be done locally or globally:

  • Local Compaction: Work-items use OpenCL local memory (__local) and local barriers (barrier(CLK_LOCAL_MEM_FENCE)) to aggregate valid neighbors within the work-group before writing a dense chunk to global memory via a single work-group-level atomic add.
  • Global Compaction: A secondary parallel scan filters out inactive slots, creating a tightly packed frontier array for depth \(k+1\).

Iteration Control and Synchronization

Frontier expansion continues level-by-level until the generated frontier size is zero. Because OpenCL's core specification lacks a native, device-wide grid barrier across all work-groups, synchronization between BFS levels is generally handled on the host side.

The host enqueues the expansion kernel, reads back the count of the newly formed frontier (or checks a termination flag via a pinned host buffer), swaps the pointers for the current and next frontier queues, and launches the kernel for the next depth level. This host-managed loop ensures memory consistency across all compute units before the next frontier begins expansion.
