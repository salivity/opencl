Coalesced Memory Access in OpenCL Global Memory

Coalesced memory access in OpenCL is a vital hardware-level optimization pattern where consecutive work-items within a work-group simultaneously access contiguous memory addresses in global memory. When work-items align their requests in this structured manner, the hardware memory controller merges individual access operations into a single, high-bandwidth transaction. Understanding how to structure memory access patterns to achieve coalescing is essential for maximizing global memory throughput and avoiding latency bottlenecks in GPU-accelerated computing.

How Coalesced Memory Transactions Work

Modern GPUs execute work-items in synchronized hardware groups known as warps (NVIDIA) or wavefronts (AMD). When an instruction requests data from global memory, the hardware attempts to service the requests of all work-items in that warp or wavefront simultaneously.

A memory transaction is coalesced when the memory addresses accessed across the active work-items meet specific criteria:

  1. Consecutive Addressing: Work-item \(i\) accesses memory address \(A\), and work-item \(i+1\) accesses memory address \(A + 1\) (unit stride).
  2. Proper Alignment: The starting address of the group request is aligned to the memory transaction boundary, typically 32, 64, or 128 bytes depending on the hardware architecture and data type size.
  3. Contiguity: The accessed elements reside within the same hardware cache line or memory segment.

When these conditions are met, the memory controller issues a single transaction (or a minimal number of burst transactions) to satisfy the entire group of work-items, utilizing maximum bus width and maximizing effective bandwidth.

Coalesced vs. Uncoalesced Patterns

The physical layout of memory significantly impacts whether access will coalesce:

  • Unit Stride (Coalesced): Work-items indexed sequentially access sequential array elements:

    int id = get_global_id(0);
float value = data[id]; // Fully coalesced

    In this pattern, a 32-thread warp accessing 4-byte floating-point values accesses a continuous 128-byte block. The hardware fulfills this in a single 128-byte transaction.

  • Strided Access (Uncoalesced): Work-items access data with a stride greater than one:

    int id = get_global_id(0);
float value = data[id * stride]; // Non-coalesced if stride > 1

    If the stride forces work-items to request addresses that span multiple cache lines, the memory controller must serialize the requests into multiple transactions. For example, if each work-item accesses a separate cache line, a 32-thread warp requires 32 distinct transactions, discarding most fetched data and wasting memory bandwidth.

  • Random or Indirect Access (Uncoalesced): Accessing memory via an indirection table (data[index_map[id]]) scatters requests across disparate memory segments, severely degrading throughput due to high serialization.

Data Layout: Structure of Arrays (SoA) vs. Array of Structures (AoS)

Data organization directly determines whether OpenCL kernels achieve coalescing.

  • Array of Structures (AoS): Storing composite data as struct Particle { float x, y, z; } particles[N]; causes thread \(i\) accessing particles[i].x to be offset from thread \(i+1\) accessing particles[i+1].x by the full size of the struct. This introduces strided access and degrades memory efficiency.
  • Structure of Arrays (SoA): Storing data in parallel arrays (float x[N]; float y[N]; float z[N];) allows thread \(i\) and thread \(i+1\) to read consecutive elements from x, resulting in perfectly coalesced transactions.

To achieve optimal performance in OpenCL kernels, algorithms must be designed around continuous, unit-stride patterns mapped directly to global work-item IDs, ensuring the underlying GPU architecture can saturate its memory bus.
