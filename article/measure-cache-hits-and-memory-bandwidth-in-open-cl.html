Measure Cache Hits and Memory Bandwidth in OpenCL

Optimizing OpenCL kernels requires understanding memory subsystem efficiency, specifically how effectively data is cached and whether the kernel saturates the available device memory bandwidth. Because the standard OpenCL API does not expose low-level hardware performance counters, measuring cache hit rates and memory bandwidth saturation relies on vendor-specific hardware profiling tools or combining OpenCL event profiling with analytical calculation models. This guide outlines the exact tools, metrics, and formulas needed to extract these performance indicators across major hardware platforms.

1. Using Vendor-Specific Hardware Profilers

OpenCL abstractly targets heterogeneous architectures, but physical cache lines and memory controllers exist at the hardware level. To view hardware counters directly, you must use the profiler tailored to your target device:

  • NVIDIA GPUs (Nsight Compute): While designed primarily for CUDA, Nsight Compute can profile OpenCL kernels running on NVIDIA hardware. Focus on the metric l1tex__t_sectors_pipe_lsu_mem_global_op_ld_lookup_hitrate.pct for L1 cache hits and lts__t_sectors_hitrate.pct for L2 cache hit rate. For bandwidth, inspect dram__bytes.sum.per_second to see actual memory throughput compared to peak capacity.
  • AMD GPUs (Radeon Developer Tool Suite / ROCm Profiler): Use rocprof or the Radeon GPU Profiler (RGP). Key metrics include TCC_HIT and TCC_MISS (Texture Cache / L2 cache hit and miss counts). Memory saturation is measured via the channels reporting memory controller requests and utilization percentages of the High Bandwidth Memory (HBM) or GDDR bus.
  • Intel GPUs and CPUs (Intel VTune Profiler): Intel VTune provides the "GPU Compute/Media Hotspots" analysis mode. It directly visualizes L3 cache hit/miss rates, sampler cache performance, and the Graphics Technology Interface (GTI) bandwidth to system memory.

2. Measuring Cache Hit Rates

Cache performance is measured by tracking requests that hit versus those that require a lookup in a higher-level cache or global DRAM.

Using vendor counters, the hit rate percentage is calculated as:

\[\text{Cache Hit Rate (\%)} = \frac{\text{Total Cache Hits}}{\text{Total Cache Hits} + \text{Total Cache Misses}} \times 100\]

If hit rates are low (typically below 60% for memory-bound algorithms), it indicates irregular or uncoalesced memory access patterns. In OpenCL, improving memory coalescing—ensuring adjacent work-items access adjacent memory addresses—directly increases cache line utilization and reduces cache misses.

3. Measuring Memory Bandwidth Saturation

Bandwidth saturation indicates whether a kernel is fundamentally bottlenecked by the device's physical memory bus. Assessing saturation requires calculating both theoretical peak bandwidth and effective memory bandwidth.

Step A: Determine Theoretical Peak Bandwidth

Locate your hardware's specifications for memory clock rate, bus width, and data multiplier (e.g., DDR/GDDR):

\[\text{Theoretical Bandwidth (GB/s)} = \frac{\text{Memory Clock (MHz)} \times \text{Bus Width (bits)} \times \text{Multiplier}}{8 \times 1000}\]

Step B: Measure Effective Memory Bandwidth

To calculate the bandwidth achieved by your kernel, record the precise execution time and compute the total data transferred:

  1. Measure Execution Time: Enable profiling by passing CL_QUEUE_PROFILING_ENABLE when creating the OpenCL command queue. Query the start and end execution timestamps using clGetEventProfilingInfo with CL_PROFILING_COMMAND_START and CL_PROFILING_COMMAND_END. The difference yields duration in nanoseconds.
  2. Calculate Bytes Transferred: Sum the exact number of bytes read from global memory buffers and written back to global memory buffers over the execution.

Calculate the achieved bandwidth:

\[\text{Achieved Bandwidth (GB/s)} = \frac{(\text{Bytes Read} + \text{Bytes Written}) \times 10^9}{\text{Execution Time (ns)} \times 10^9}\]

Step C: Evaluate Saturation

Compare the achieved bandwidth to the theoretical maximum:

\[\text{Bandwidth Saturation (\%)} = \frac{\text{Achieved Bandwidth}}{\text{Theoretical Bandwidth}} \times 100\]

Due to protocol overhead, command arbitration, and burst alignment limits, real-world saturation typically tops out between 75% and 85% of theoretical peak bandwidth. If your kernel achieves metrics in this range, the kernel is fully memory-bound, and further gains will require algorithmic changes to reduce total data access, such as moving intermediate data into OpenCL __local memory.
