Why OpenCL Work-Items Must Execute the Same Barrier

In OpenCL, the barrier function synchronizes execution and memory operations across all work-items in a single work-group. The OpenCL specification strictly mandates that every work-item within a work-group must encounter the exact same barrier instruction to avoid program deadlocks, undefined behavior, and hardware hangs. This article explains the underlying architectural and logical reasons why divergent barrier execution is prohibited in parallel computing kernels.

The Mechanism of Work-Group Synchronization

A barrier acts as a coordination checkpoint. When a work-item hits a barrier—such as barrier(CLK_LOCAL_MEM_FENCE) or work_group_barrier(...)—it halts execution until every other work-item in that specific work-group reaches that identical point. Only when all work-items have arrived does the hardware allow any of them to advance past the barrier.

This synchronization ensures data integrity. In typical OpenCL programs, work-items collaborate by reading and writing to shared local memory (__local). Without a synchronized pause, fast-executing work-items might read uninitialized data or overwrite values that slower work-items have not yet consumed, leading to race conditions.

Prevention of Deadlocks

The primary reason all work-items must encounter the same barrier is the prevention of infinite deadlocks.

Consider an algorithm where a barrier is placed inside a conditional branch:

if (get_local_id(0) % 2 == 0) {
    // Barrier A
    barrier(CLK_LOCAL_MEM_FENCE);
} else {
    // Barrier B
    barrier(CLK_LOCAL_MEM_FENCE);
}

In this scenario, even-indexed work-items halt at Barrier A waiting for odd-indexed work-items. However, the odd-indexed work-items diverge into the else block and stop at Barrier B, waiting for the even-indexed work-items. Because neither set can proceed until the other joins them at their respective barrier, the work-group enters a permanent deadlock.

To eliminate this class of deadlock, the OpenCL specification dictates that barriers must be encountered convergently. If a barrier resides within conditional code, the condition must evaluate identically for all work-items in the work-group.

Hardware Execution Models and Divergence

Underlying GPU architectures execute work-items in lockstep groups, often referred to as warps (NVIDIA) or wavefronts (AMD). These sub-groups share a single instruction pointer:

  1. Lockstep Execution: When code diverges (e.g., via an if-else statement), the hardware masks off the inactive threads while executing one branch, then flips the mask to execute the other branch.
  2. Barrier Hardware: The hardware barrier synchronization logic monitors arrival counts. If instructions diverge such that some lanes wait on a synchronization signal that inactive lanes cannot generate, the execution pipeline stalls indefinitely.

Because modern hardware primitives are designed around unified control flow for synchronization, divergent barriers cannot be scheduled efficiently or reliably.

Dynamic Control Flow Rules

The requirement applies dynamically rather than purely statically. Work-items must encounter the exact same dynamic execution instance of the barrier.

If a barrier is placed inside a loop:

  • Every work-item in the work-group must execute the loop the exact same number of times.
  • If one work-item exits a loop early while others remain, the work-items inside the loop will wait indefinitely for the departed item to hit the subsequent barrier iterations, triggering undefined behavior.

Enforcing that all work-items encounter the identical barrier ensures deterministic synchronization, aligns with the physical execution constraints of SIMD/SIMT hardware, and guarantees program correctness across diverse computing devices.
