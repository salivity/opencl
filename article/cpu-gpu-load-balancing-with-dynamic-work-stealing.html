CPU-GPU Load Balancing with Dynamic Work-Stealing

Heterogeneous computing environments combining multi-core CPUs and GPUs through OpenCL often suffer from performance bottlenecks caused by static workload division and unpredictable execution times. Dynamic work-stealing schedulers solve this imbalance by enabling underutilized processors to autonomously take tasks from overloaded compute units. By accounting for architectural disparities, memory transfer latencies, and adaptive task granularity, dynamic work-stealing optimizes system throughput and minimizes idle runtime across disparate hardware pools.

The Challenge of Heterogeneity in OpenCL

CPUs and GPUs feature fundamentally different architectural strengths. CPUs excel at low-latency, branch-heavy, sequential tasks (MIMD), whereas GPUs thrive on high-throughput, massively parallel operations (SIMD/SIMT). In a standard OpenCL context, a single application context may expose multiple cl_device_id handles with distinct memory spaces and execution characteristics.

Static workload partitioning—such as splitting iterations based on fixed compute capacity ratios—frequently fails because:

  • Kernel execution times fluctuate due to dynamic data branching and memory access patterns.
  • OpenCL memory transfer overhead over PCIe buses varies dynamically with system load.
  • Thermal throttling or background operating system tasks alter compute capacities mid-execution.

Core Mechanics of Work-Stealing

In a standard work-stealing model, each compute node (or worker thread managing an OpenCL device) maintains its own local double-ended queue (deque) of tasks.

  1. Local Execution: A worker pushes and pops tasks from the tail of its deque, minimizing synchronization contention and maintaining data cache locality.
  2. Stealing Protocol: When a worker’s deque becomes empty, it enters a thief state, selects a victim worker (often randomly or based on topology), and attempts to steal tasks from the head of the victim's deque using atomic operations.

Adapting Work-Stealing for CPU-GPU Pools

Directly applying uniform work-stealing to a heterogeneous OpenCL context causes performance degradation. GPUs starved of data cannot process tiny tasks efficiently, and CPUs become overwhelmed if assigned massive, throughput-oriented parallel kernels. To balance heterogeneous loads effectively, work-stealing schedulers must incorporate specialized design strategies:

Dynamic Chunk Sizing and Adaptive Granularity

A uniform task size is impractical across different device types. Schedulers must employ adaptive chunking:

  • GPU Chunks: Must be large enough to saturate compute units and amortize OpenCL kernel launch overhead and DMA data transfers.
  • CPU Chunks: Should be smaller to maintain responsiveness and avoid long tail latencies at the end of execution.
  • Guided Self-Scheduling: Task sizes decrease dynamically as execution progresses, allowing large initial tasks to keep GPUs busy while finer chunks at the end prevent stragglers.

Locality-Aware and Cost-Aware Victim Selection

Stealing across heterogeneous boundaries incurs substantial latency due to host-device data migration. A high-efficiency scheduler evaluates transfer costs before approving a steal:

  • Affinity Tracking: Tasks track where their dependent OpenCL memory objects (cl_mem) currently reside. Thieves prioritize victims that share the same memory space (e.g., another GPU on the same PCIe switch or integrated CPU memory).
  • Cost-Benefit Heuristics: A steal operation only proceeds if the estimated computation time on the target device exceeds the round-trip PCIe transfer time plus kernel execution overhead.

Asymmetric Stealing Policies

Stealing rules must be directional rather than symmetric:

  • CPU stealing from GPU: A CPU worker acts as an effective safety net for slow GPU executions by stealing the tail-end chunks of remaining parallel iterations, preventing the GPU from becoming a long-tail straggler.
  • GPU stealing from CPU: GPUs should only steal if the victim has a sufficiently large block of homogeneous parallel tasks that justify the kernel compilation, data transfer, and dispatch cycles.

Execution Framework and Synchronization

Implementing dynamic work-stealing across OpenCL devices typically relies on a host-side runtime runtime layer:

  1. Host-Side Worker Threads: Dedicated host threads manage each OpenCL command queue (cl_command_queue). One or more threads manage the multi-core CPU, while dedicated threads drive the discrete GPUs.
  2. Non-Blocking Synchronization: Lock-free deques using atomic primitives minimize coordination overhead between host threads managing concurrent device dispatches.
  3. Asynchronous Pipelining: Workers leverage non-blocking OpenCL calls (clEnqueueNDRangeKernel, clEnqueueCopyBuffer) and OpenCL event objects (cl_event) to overlap the execution of stolen kernels with the data transfers of upcoming tasks.

By combining adaptive chunk sizing, transfer-cost heuristics, and directional stealing policies, dynamic work-stealing schedulers effectively neutralize hardware disparities, driving maximum utilization across heterogeneous CPU-GPU OpenCL pools.
