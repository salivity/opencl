OpenCL 1.2 Image Read and Write Restrictions

In OpenCL 1.2, developers face strict limitations when attempting to simultaneously read from and write to the same image object within a single kernel. Unlike general memory buffers, image objects are subject to hardware-level texture and surface pipeline optimizations that enforce access exclusivity. This article outlines the access qualifier restrictions, the consequences of argument aliasing, memory coherency barriers, and standard architectural workarounds in OpenCL 1.2.

Access Qualifier Constraints

In OpenCL 1.2, image objects cannot be declared with simultaneous read and write capabilities. The specification restricts image arguments to either the __read_only (or read_only) qualifier or the __write_only (or write_only) qualifier. The __read_write qualifier for image types was only introduced in later specifications (OpenCL 2.0) and is not legally available in OpenCL 1.2. Consequently, a single image variable inside a kernel cannot execute both read_image* and write_image* functions.

Argument Aliasing and Undefined Behavior

A common workaround developers attempt is passing the same underlying host-side image object (cl_mem) to two separate kernel arguments—one qualified as __read_only and the other as __write_only. Under OpenCL 1.2, this produces undefined behavior.

The OpenCL 1.2 specification states that if a memory object is written to by a kernel, it cannot be simultaneously read by the same kernel via another argument unless the reads and writes are strictly disjoint and explicitly supported, which is not guaranteed for images. Hardware drivers typically bind read images to texture sampling hardware and write images to frame-buffer or surface-store units. Because these paths maintain separate, non-coherent caches, modifying an image through the write path will not reliably update the read cache during the same dispatch.

Lack of Intra-Kernel Synchronization for Images

Even if a developer attempts to coordinate access between work-items using work-group barriers (barrier(CLK_GLOBAL_MEM_FENCE) or barrier(CLK_LOCAL_MEM_FENCE)), OpenCL 1.2 provides no memory fence operation specifically tailored to synchronize image caches across work-items. Barriers guarantee completion and visibility for standard memory buffers, but they do not enforce coherency across mixed read-write texture pipelines.

Standard Workarounds in OpenCL 1.2

To modify and read image data within the constraints of OpenCL 1.2, implementations must use alternative architectural patterns:

  • Ping-Pong Buffering: Allocate two separate image objects of the same format and dimensions. One image serves as the read-only source for the first dispatch, while the second serves as the write-only destination. Subsequent iterations swap the roles of these images across separate clEnqueueNDRangeKernel calls, utilizing host-level event synchronization.
  • Conversion to Linear Buffers: When simultaneous in-place read and write operations are strictly necessary within a single execution pass, data must be stored in standard linear buffer objects (cl_mem created with CL_MEM_READ_WRITE). Linear buffers support read-write qualifiers and adhere to standard global memory fence semantics, though they forfeit hardware-accelerated texture filtering, normalized addressing, and border clamping.
