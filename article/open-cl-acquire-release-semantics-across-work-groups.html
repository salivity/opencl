OpenCL Acquire-Release Semantics Across Work-Groups

In OpenCL 2.0 and later versions, acquire-release semantics govern how and when memory modifications made by one thread become visible to others. Traditionally, distinct work-groups operate in complete isolation without global execution barriers, deferring memory synchronization across work-groups until kernel execution concludes. By leveraging acquire and release atomic operations with the appropriate memory scopes, developers can establish well-defined "happens-before" relationships between independent work-groups, enabling safe, fine-grained cross-work-group communication and global memory visibility during a single kernel launch.

The Baseline: Isolation of Work-Groups

In standard OpenCL execution, work_group_barrier only synchronizes work-items residing in the same work-group and operating on local or global memory. Hardware architectures generally map work-groups to independent compute units, each with private L1 caches or scratchpad memories.

Without explicit memory ordering, an update to global memory by Work-Group A is not guaranteed to be flushed to a coherent cache level, nor is Work-Group B guaranteed to invalidate its local caches to observe those updates. Consequently, data races and stale reads occur if work-groups attempt to synchronize through standard global variables without finishing the kernel.

The Mechanics of Acquire and Release

Acquire-release semantics enforce directional memory ordering constraints around atomic operations:

  • Release Semantics (memory_order_release): Prevents preceding memory reads and writes from being reordered after the atomic store. When a work-item performs a release store, all prior global and local memory writes made by that work-item are committed and made visible to other threads that later synchronize with that release.
  • Acquire Semantics (memory_order_acquire): Prevents subsequent memory reads and writes from being reordered before the atomic load. When a work-item performs an acquire load, it invalidates stale cached data, ensuring that all reads following the acquire see the updates made prior to the matching release store.

Establishing Cross-Work-Group Visibility

For memory operations to bridge the boundary between separate work-groups, two conditions must be met:

  1. Synchronized Pair: Work-Group A must execute an atomic store with memory_order_release (or memory_order_acq_rel), and Work-Group B must read the value written by Work-Group A using an atomic load with memory_order_acquire (or memory_order_seq_cst).
  2. Proper Scope: The operations must specify a memory scope wider than the work-group. OpenCL provides memory_scope_device (for synchronization across all work-groups on the device) and memory_scope_all_svm_devices (for synchronization across the host and device in Shared Virtual Memory environments). If memory_scope_work_group is used, the visibility guarantee remains confined within the executing work-group, failing to synchronize across work-group boundaries.

When Work-Group B's acquire load successfully reads the value stored by Work-Group A's release store, a synchronizes-with relationship is established.

Practical Impact on Memory Visibility

This mechanism fundamentally changes memory visibility across the GPU in the following ways:

  • Producer-Consumer Patterns: Work-Group A can write a large payload to non-atomic global buffers and then publish a "ready" flag using an atomic release store. Work-Group B continuously polls this flag with an atomic acquire load. Once the flag is observed, all prior non-atomic payload writes by Work-Group A are fully visible and coherent to Work-Group B.
  • Hardware Cache Management: At the hardware level, release semantics trigger cache write-backs or bypasses to shared cache tiers (such as L2 or device memory), while acquire semantics mandate cache invalidation of the reading unit's private cache levels, eliminating stale reads.
  • Elimination of Kernel Splitting: Developers are no longer forced to split algorithms into multiple kernel launches to achieve global synchronization, reducing command queue dispatch overhead and keeping transient data hot in intermediate caches.
