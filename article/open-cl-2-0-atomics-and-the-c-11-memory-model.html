OpenCL 2.0 Atomics and the C11 Memory Model

OpenCL 2.0 introduced a major overhaul of its synchronization primitives by adopting the ISO C11 memory model standards for atomic operations. This alignment replaced the legacy, loosely defined OpenCL 1.x atomics with formal memory ordering semantics, shared virtual memory synchronization, and fine-grained memory visibility rules. By adopting C11 principles, OpenCL 2.0 enables reliable lock-free programming across heterogeneous devices while tailoring the standard to fit massively parallel GPU architectures.

Adoption of C11 Memory Orders

Prior to OpenCL 2.0, atomic operations were limited in scope and lacked formal memory ordering guarantees, functioning primarily as sequentially consistent or relaxed operations depending on vendor implementation. OpenCL 2.0 directly incorporates the memory order enumerations defined in the C11 standard (stdatomic.h), giving developers precise control over compiler and hardware instruction reordering:

  • memory_order_relaxed: Guarantees atomicity for the target variable but provides no synchronization or ordering constraints relative to other memory operations.
  • memory_order_acquire: Applied to read operations, ensuring that subsequent reads and writes cannot be reordered before this acquire operation.
  • memory_order_release: Applied to write operations, ensuring that prior reads and writes cannot be reordered after this release operation.
  • memory_order_acq_rel: Combines acquire and release semantics for read-modify-write operations.
  • memory_order_seq_cst: Enforces a total, globally consistent order across all participating threads.

Extension with Memory Scopes

While C11 targets symmetric multiprocessing (SMP) environments where all threads typically share a uniform memory view, heterogeneous hardware relies on a hierarchical execution model. To adapt C11 semantics to this reality, OpenCL 2.0 extends C11 atomics with an explicit memory_scope parameter.

The memory scope defines the visibility boundary of the synchronization effect:

  • memory_scope_work_item: Synchronizes operations only within the executing work-item (useful primarily for sub-buffers or self-contained state machines).
  • memory_scope_sub_group: Limits synchronization to a hardware warp or wavefront.
  • memory_scope_work_group: Confines the visibility of memory operations to work-items within the same work-group sharing local memory.
  • memory_scope_device: Extends synchronization across all work-groups executing on the specific OpenCL device.
  • memory_scope_all_svm_devices: Extends visibility across both host (CPU) and device (GPU) memory boundaries in Shared Virtual Memory (SVM) configurations.

Through these scopes, OpenCL 2.0 allows an acquire-release operation to synchronize only the necessary subset of cores, avoiding the severe performance penalties of flushing memory pipelines across an entire GPU.

Atomic Types and Operations

OpenCL 2.0 mirrors C11 atomic type definitions, introducing explicit atomic types such as atomic_int, atomic_uint, atomic_float, and atomic_flag. These types can reside in either the __global or __local address spaces.

Functions closely follow C11 signatures, suffixed with explicit memory order and scope variants. For example:

  • C11 standard: atomic_fetch_add_explicit(object, operand, order)
  • OpenCL 2.0: atomic_fetch_add_explicit(object, operand, order, scope)

This consistency reduces the cognitive overhead for programmers migrating C11 parallel algorithms to OpenCL kernels.

Fences and Synchronization

OpenCL 2.0 replaces the legacy barrier() and mem_fence() functions with atomic_work_item_fence(). This function aligns with the C11 atomic_thread_fence() mechanism by establishing synchronization without requiring an atomic read-modify-write operation on a specific variable. It accepts memory flags (CLK_GLOBAL_MEM_FENCE, CLK_LOCAL_MEM_FENCE), a memory_order, and a memory_scope, formalizing synchronizes-with relationships between distinct work-items.

Host-Device Synchronization via SVM

A primary motivation for aligning OpenCL 2.0 with C11 was the introduction of Shared Virtual Memory (SVM). In fine-grained system SVM, host threads running native C11/C++11 code and device work-items running OpenCL C code can manipulate the same memory pointers simultaneously. By utilizing identical memory models, an atomic_store_explicit executed with release semantics on a CPU thread can be properly synchronized with an atomic_load_explicit executed with acquire semantics on an OpenCL compute unit.
