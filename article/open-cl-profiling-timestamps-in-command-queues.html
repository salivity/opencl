OpenCL Profiling Timestamps in Command Queues

This article provides an overview of how OpenCL command queues utilize event profiling to capture high-resolution timestamps for performance tracing. By enabling profiling capabilities on a command queue and attaching event objects to queued commands, developers can extract precise timing information across different stages of execution. This allows for accurate measurement of queue latency, submission overhead, and actual hardware kernel execution time to diagnose performance bottlenecks.

Enabling Profiling on the Command Queue

By default, an OpenCL command queue does not record execution timestamps to avoid unnecessary runtime overhead. To track timing metrics, you must explicitly enable profiling when creating the command queue.

In OpenCL 2.0 and later, this is done by passing the CL_QUEUE_PROFILING_ENABLE flag within the property array to clCreateCommandQueueWithProperties:

cl_queue_properties properties[] = {
    CL_QUEUE_PROPERTIES, 
    CL_QUEUE_PROFILING_ENABLE, 
    0
};
cl_command_queue queue = clCreateCommandQueueWithProperties(context, device, properties, &err);

For OpenCL 1.x, the flag is passed directly as a bitfield argument to clCreateCommandQueue.

Capturing Events

When an OpenCL command is enqueued—such as a kernel execution (clEnqueueNDRangeKernel) or a memory transfer (clEnqueueReadBuffer)—the API allows you to capture an associated event object by passing a pointer to a cl_event variable as the last parameter.

When the queue has profiling enabled, the OpenCL runtime automatically associates timestamp records with this event object as the command progresses through its lifecycle.

The Four Profiling Timestamps

OpenCL tracks four distinct states for each profiled command. Each timestamp is recorded as a 64-bit unsigned integer (cl_ulong) representing time in nanoseconds derived from a device-specific monotonic timer.

  1. CL_PROFILING_COMMAND_QUEUED: The point in time when the host CPU successfully enqueues the command into the host-side command queue.
  2. CL_PROFILING_COMMAND_SUBMIT: The point in time when the host submits the command to the target device's internal processing queue.
  3. CL_PROFILING_COMMAND_START: The exact moment the device starts executing the command or kernel.
  4. CL_PROFILING_COMMAND_END: The exact moment the device finishes processing the command and results become available.

Querying Profiling Data

Timestamps are queried after the command has fully finished execution. If you query an event before it reaches the CL_COMPLETE status, the query will fail. Developers typically call clWaitForEvents or clFinish to ensure the device has completed the operation.

Data is extracted using clGetEventProfilingInfo:

cl_ulong time_queued, time_submit, time_start, time_end;

clGetEventProfilingInfo(event, CL_PROFILING_COMMAND_QUEUED, sizeof(cl_ulong), &time_queued, NULL);
clGetEventProfilingInfo(event, CL_PROFILING_COMMAND_SUBMIT, sizeof(cl_ulong), &time_submit, NULL);
clGetEventProfilingInfo(event, CL_PROFILING_COMMAND_START, sizeof(cl_ulong), &time_start, NULL);
clGetEventProfilingInfo(event, CL_PROFILING_COMMAND_END, sizeof(cl_ulong), &time_end, NULL);

Deriving Performance Metrics

Because the timestamps represent absolute values from an implementation-defined timebase, individual timestamp values are arbitrary on their own. Performance tracing relies on the differences between these timestamps:

  • Host-to-Device Queue Latency: time_submit - time_queued
    Measures how long a command waited in the software queue before submission to hardware.
  • Driver and Hardware Scheduling Overhead: time_start - time_submit
    Measures delay between submission and the actual start of execution on the compute units.
  • Pure Execution Time: time_end - time_start
    Measures the actual duration the kernel ran on the target hardware. This is the primary metric for GPU/accelerator compute performance.
  • Total Lifecycle Duration: time_end - time_queued
    Measures the entire turnaround time of the command from initial scheduling to completion.

Key Considerations

  • Timer Resolution: You can determine the underlying precision of the device timer by querying clGetDeviceInfo with CL_DEVICE_PROFILING_TIMER_RESOLUTION, which returns the timer resolution in nanoseconds.
  • Cross-Device Comparison: Timestamps generated by different devices within the same context are not guaranteed to share the same clock origin. Therefore, you should not calculate time differences using timestamps from two different OpenCL devices.
  • Memory Management: Every cl_event created to capture profiling timestamps must be explicitly released using clReleaseEvent once the profiling data is extracted to prevent memory leaks.
