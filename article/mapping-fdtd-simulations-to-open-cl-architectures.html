Mapping FDTD Simulations to OpenCL Architectures

Finite Difference Time Domain (FDTD) electromagnetic simulation maps naturally to OpenCL grid architectures due to its regular spatial structure and inherently parallel, localized updates. This article explores how the core mathematical framework of FDTD—namely Yee's spatial lattice and leapfrog time-stepping—aligns with the OpenCL execution and memory hierarchies. Key topics covered include spatial discretization across work-items, managing temporal synchronization through kernel launches, optimizing memory bandwidth using Structure of Arrays (SoA) and local memory, and handling computational boundaries like Perfectly Matched Layers (PML).

Spatial Mapping: Yee Cells to OpenCL NDRanges

The FDTD method discretizes Maxwell's curl equations in both space and time using the Yee lattice. In this lattice, electric field (\(\vec{E}\)) and magnetic field (\(\vec{H}\)) components are interleaved at half-grid intervals along the Cartesian axes (\(x, y, z\)).

OpenCL maps computational tasks across an N-dimensional range (NDRange). A 3D FDTD spatial volume of size \(N_x \times N_y \times N_z\) maps directly to a 3D NDRange:

  • Work-Item: Each work-item (thread) is responsible for updating the field components of a single Yee cell or a specific field component (\(E_x, E_y, E_z\) or \(H_x, H_y, H_z\)) at index \((i, j, k)\).
  • Work-Group: Spatial blocks (e.g., \(16 \times 8 \times 2\) or \(8 \times 8 \times 4\) cells) are grouped into OpenCL work-groups to execute concurrently on single Compute Units (CUs) or Streaming Multiprocessors (SMs).
  • Flat vs. 3D Indexing: While OpenCL natively supports 3D index spaces via get_global_id(0), get_global_id(1), and get_global_id(2), developers often flatten the 3D domain into a 1D index array (id = x + y * Nx + z * Nx * Ny) to reduce hardware register pressure and simplify memory address generation.

Temporal Mapping: Leapfrog Updates and Kernel Dispatch

FDTD uses a staggered, explicit time-stepping scheme where \(\vec{H}\) is updated at half-time steps (\(t + \Delta t / 2\)) using spatial curls of \(\vec{E}\), and \(\vec{E}\) is updated at integer time steps (\(t + \Delta t\)) using spatial curls of \(\vec{H}\).

Because every update across the entire grid depends on neighbor values from the immediate prior step, global synchronization is strictly required between the \(\vec{E}\)-field update and the \(\vec{H}\)-field update.

OpenCL lacks a native, low-latency device-wide barrier spanning multiple work-groups across an entire GPU. Consequently, the temporal leapfrog cycle is mapped into two distinct host-side kernel dispatches per time step:

  1. Enqueue \(\vec{H}\)-update kernel: Computes the new magnetic fields across the 3D grid using current electric fields.
  2. Implicit Host Synchronization: The OpenCL command queue acts as an execution barrier, ensuring all work-groups complete the \(\vec{H}\)-update before the next kernel starts.
  3. Enqueue \(\vec{E}\)-update kernel: Computes the new electric fields across the 3D grid using the newly computed magnetic fields.

This cycle repeats for the total number of time steps required by the simulation.

Memory Architecture and Stencil Optimization

FDTD is predominantly memory-bandwidth-bound rather than compute-bound. Calculating an update requires computing spatial derivatives using a nearest-neighbor stencil (typically second-order central differences involving six adjacent points). Optimizing data flow through the OpenCL memory hierarchy is critical for high performance.

Data Layout: Structure of Arrays (SoA)

Storing components as an Array of Structures (e.g., an array containing interleaved \(\{Ex, Ey, Ez\}\) structs) leads to strided, non-coalesced memory access. Instead, FDTD on OpenCL uses a Structure of Arrays (SoA) layout: six independent, contiguous 1D global memory buffers for \(E_x, E_y, E_z, H_x, H_y,\) and \(H_z\). This guarantees that adjacent work-items reading adjacent cells along the fast-moving dimension (usually the \(x\)-axis) trigger coalesced memory transactions, maximizing memory bus utilization.

Cache and Local Memory (Tiling)

Because neighboring cells reuse the same field values to compute curls, spatial tiling using OpenCL __local memory (scratchpad RAM) can reduce redundant reads from global memory. A work-group loads an extended tile of field values—including "halo" or boundary cells—into __local memory, synchronizes with a barrier(CLK_LOCAL_MEM_FENCE), and evaluates the spatial finite differences directly from cache. On modern architectures with large, fast hardware L1 and L2 caches, direct reads through global memory with read-only caching qualifiers (__global const * restrict) often achieve comparable throughput with lower code complexity.

Handling Boundary Conditions

Simulations require absorbing boundary conditions, typically Convolutional Perfectly Matched Layers (CPML), to emulate open space and prevent artificial reflections at grid limits. CPML introduces auxiliary differential equations and additional state variables at the edges of the grid.

Mapping CPML directly inside the primary domain update kernel causes severe warp/wavefront divergence because only edge work-items execute the complex CPML equations. To prevent computational inefficiency on OpenCL devices:

  • Kernel Partitioning: The primary update kernel runs exclusively on the core interior domain without conditional boundary checks.
  • Dedicated Boundary Kernels: Separate, smaller OpenCL kernels are dispatched specifically to update the six 2D boundary slabs (faces) of the 3D bounding box where CPML mathematics apply.

This decomposition keeps the bulk execution pipeline uniform, maximizing instruction throughput across compute units.
