OpenCL Context Callback Error Types

In OpenCL, runtime errors are divided into two main categories: synchronous errors returned directly by API calls, and asynchronous errors reported through the context notification callback (pfn_notify). While API return codes capture immediate, predictable validation failures such as invalid parameters or unsupported features, the context callback handles asynchronous hardware faults, runtime execution failures, and driver-level diagnostics that occur while workloads execute on the device.

Asynchronous Execution Failures

When commands are enqueued to a cl_command_queue, the enqueue call returns almost instantaneously with CL_SUCCESS if the command was successfully scheduled. Any failure that occurs later during the physical execution of that command cannot be returned by the initiating API call. These asynchronous execution failures—such as hardware execution traps, invalid memory accesses (segmentation faults on the device), and misaligned memory pointers—are routed directly to the context notification callback as human-readable error messages in the errinfo parameter.

Hardware Hangs and Device Loss

Hardware-level anomalies that occur mid-execution trigger callback notifications. These include:

  • Timeout Detection and Recovery (TDR): Operating systems enforce execution time limits on graphical processing units. If a kernel runs too long without yielding, the OS resets the graphics driver, triggering an asynchronous device loss notification.
  • Device Disconnection: For external or hot-pluggable devices (such as eGPUs or FPGA accelerators), physical disconnection or fatal PCIe communication dropouts are reported via the callback.
  • Thermal and Power Throttles/Faults: Hardware exceptions related to power state transitions or critical over-temperature shutdowns during compute execution.

Dynamic Resource Exhaustion

While initial buffer allocations via clCreateBuffer return standard cl_int codes such as CL_OUT_OF_HOST_MEMORY or CL_OUT_OF_RESOURCES, dynamic resource exhaustion during runtime execution is surfaced through the callback. Examples include:

  • Kernel private memory or local memory exhaustion that could not be determined at compilation or launch time.
  • Printf buffer exhaustion during kernel execution.
  • Unified Virtual Memory (SVM) page allocation and migration failures occurring asynchronously during device access.

Driver Diagnostic and Validation Layer Messages

Most OpenCL implementations use the pfn_notify callback to pass non-fatal implementation-defined diagnostic information. These include:

  • JIT compilation and link warnings triggered dynamically during background optimization passes.
  • Platform-specific driver warnings regarding sub-optimal work-group sizing or fallback paths.
  • Diagnostic logging produced by active OpenCL validation and debugging layers.

Mechanism Differences Between API Returns and Callbacks

Unlike API functions that populate a standard cl_int status code, the OpenCL context callback does not pass a standard numeric error code. Instead, the OpenCL specification defines the callback signature to accept a string pointer (const char *errinfo) and an implementation-dependent binary payload (const void *private_info). The text provided in errinfo contains vendor-specific descriptions of the underlying driver or hardware failure, making the callback essential for logging, debugging, and post-mortem analysis of unrecoverable runtime states.
