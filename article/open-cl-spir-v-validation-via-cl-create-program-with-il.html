OpenCL SPIR-V Validation via clCreateProgramWithIL

This article examines how an OpenCL 2.1 or 3.0 runtime processes and validates a Standard Portable Intermediate Representation (SPIR-V) module using the clCreateProgramWithIL API. It covers the initial ingestion process, binary header verification, capability and memory model checking, semantic validation, and how compilation is deferred until the build phase.

Ingestion and API-Level Verification

When an application calls clCreateProgramWithIL, it passes a pointer to the SPIR-V binary (const void *il), the byte size (size_t length), and a target cl_context. The OpenCL runtime first performs baseline parameter checks:

  • Memory and Length Checks: The runtime ensures the pointer is non-null and that length is greater than zero and a multiple of 4 bytes (32-bit words), as SPIR-V is a stream of 32-bit words.
  • Context Verification: The runtime confirms that the associated cl_context supports intermediate language ingestion. In OpenCL 3.0, the runtime checks whether the device exposes CL_DEVICE_IL_VERSION; in OpenCL 2.1, core SPIR-V support is mandatory.

If these checks fail, the call returns an appropriate error code, such as CL_INVALID_VALUE.

Header Parsing

Before processing the instruction stream, the runtime parses the mandatory 5-word SPIR-V header:

  1. Magic Number (Word 0): Must be 0x07230203. The runtime uses this value to determine endianness. If the bytes are reversed, the runtime either swaps the endianness in-flight or rejects the binary.
  2. Version Number (Word 1): Encodes the SPIR-V specification version (major and minor). The runtime checks this against the highest version supported by the target OpenCL devices.
  3. Generator Magic Number (Word 2): Identifies the toolchain (e.g., Clang, SPIRV-LLVM-Translator) that generated the module. The runtime may use this to apply driver-specific workarounds for known compiler bugs.
  4. Bound (Word 3): Defines the upper bound for all <id> values used within the module.
  5. Reserved Schema (Word 4): Must be 0 according to the SPIR-V specification.

A mismatch in the magic number or an unsupported version returns CL_INVALID_BINARY.

Capability and Environment Checking

The runtime scans the instruction stream for required module-level configuration:

  • Execution Model: OpenCL environments require the Kernel execution model declared via OpCapability Kernel. If graphics capabilities (e.g., Shader) are declared without OpenCL-specific extensions, validation fails.
  • Memory Model: The module must contain an OpMemoryModel instruction specifying the OpenCL memory model and either Physical32 or Physical64 addressing, which must match the device's pointer size architecture.
  • Optional Capabilities: The runtime compares instructions like OpCapability Addresses, OpCapability Int64, OpCapability Float16, or subgroup features against the target hardware's reported capabilities (via clGetDeviceInfo).

Structural and Semantic Validation

Many production OpenCL runtimes integrate the Khronos spirv-val validation engine or an equivalent internal parser to enforce the SPIR-V specification rules:

  • Opcode and Length Consistency: Every instruction begins with a word encoding the opcode and the total word count. The runtime ensures the stream cleanly segments into valid instructions without buffer overruns.
  • Static Single Assignment (SSA): Every result <id> must be uniquely defined and dominate its uses within local control flow.
  • Control Flow Graph (CFG) Rules: The runtime verifies that blocks end with proper terminators (OpBranch, OpBranchConditional, OpReturn, etc.) and adhere to structured control flow rules where applicable.
  • Type Safety and Linkage: Operand types must match instruction signatures, and entry points (OpEntryPoint) must match valid kernel function declarations.

Program Creation and Deferred Compilation

clCreateProgramWithIL does not compile the module to target-specific machine instructions. Instead, it completes the following:

  1. Allocates an internal cl_program object.
  2. Copies or references the validated SPIR-V byte stream.
  3. Extracts kernel metadata (kernel names, argument types, qualifiers) from OpEntryPoint and OpDecorate instructions to populate subsequent clGetProgramInfo queries.

Actual hardware code generation, register allocation, and application of specialization constants (via clSetProgramSpecializationConstant) are deferred until clBuildProgram or clCompileProgram is executed. If structural or validation errors are detected during the initial ingestion phase, clCreateProgramWithIL fails immediately and returns CL_INVALID_BINARY.
