High-Throughput Philox PRNG in OpenCL

High-throughput pseudo-random number generation is essential for parallel workloads such as Monte Carlo simulations, statistical modeling, and machine learning running on modern GPUs. Counter-based pseudo-random number generators (CBPRNGs), particularly the Philox family, are ideal for OpenCL because they generate random values directly from a counter and an encryption-like key rather than updating a persistent sequential state. This article details the mathematical principles of Philox, explains how to implement the Philox4x32 algorithm in OpenCL C, and covers optimization strategies to achieve peak parallel throughput without memory bottlenecks.

Why Counter-Based PRNGs Suit OpenCL

Traditional PRNGs like Linear Congruential Generators (LCGs) or the Mersenne Twister rely on sequential internal states. In a massively parallel OpenCL environment, stateful generators require each work-item to either update global memory or maintain heavy state structures in private registers, causing memory latency or high register pressure.

Philox operates as a keyed, counter-based bijection:

\[\text{Output} = f_K(\text{Counter})\]

Because each random vector depends solely on an arbitrary counter value and a user-defined key, work-items can calculate outputs independently. A unique counter can be derived simply from the OpenCL global ID and a loop step counter:

\[\text{Counter} = (\text{get\_global\_id}(0), \text{loop\_iteration})\]

This completely eliminates inter-thread communication, synchronization barriers, and memory access dependencies.

Anatomy of the Philox4x32 Algorithm

The most widely adopted variant is Philox4x32-10, which processes a 128-bit counter (stored as four 32-bit unsigned integers: \(R_0, R_1, R_2, R_3\)) through 10 rounds of substitution-permutation operations using two 32-bit keys (\(K_0, K_1\)).

In each round:

  1. Two non-linear multiplications are performed using high-multiplier constants:
    • \(M_0 = \text{0xD2511F53}\)
    • \(M_1 = \text{0xCD9E8D57}\)
  2. Each 32-bit multiplication produces a 64-bit result, which is split into high and low 32-bit halves.
  3. The halves are XORed with the alternate values and swapped.
  4. Keys are incremented using Weyl constants (\(W_0 = \text{0x9E3779B9}\), \(W_1 = \text{0xBB67AE85}\)) to avoid periodic correlations.

OpenCL Implementation

OpenCL provides native vector types (uint4, uint2) and native 32-bit integer arithmetic functions like mul_hi, making Philox highly efficient.

#define PHILOX_M0 0xD2511F53U
#define PHILOX_M1 0xCD9E8D57U
#define PHILOX_W0 0x9E3779B9U
#define PHILOX_W1 0xBB67AE85U
#define ROUNDS 10

// Single Philox4x32 round function
inline uint4 philox4x32_round(uint4 ctr, uint2 key) {
    uint hi0 = mul_hi(ctr.x, PHILOX_M0);
    uint lo0 = ctr.x * PHILOX_M0;
    
    uint hi1 = mul_hi(ctr.z, PHILOX_M1);
    uint lo1 = ctr.z * PHILOX_M1;
    
    uint4 next_ctr;
    next_ctr.x = hi1 ^ ctr.y ^ key.x;
    next_ctr.y = lo1;
    next_ctr.z = hi0 ^ ctr.w ^ key.y;
    next_ctr.w = lo0;
    
    return next_ctr;
}

// Full evaluation generating 4 uniform floats in [0, 1)
inline float4 philox4x32(uint4 ctr, uint2 key) {
    #pragma unroll
    for (int i = 0; i < ROUNDS; ++i) {
        ctr = philox4x32_round(ctr, key);
        key.x += PHILOX_W0;
        key.y += PHILOX_W1;
    }
    
    // Scale 32-bit unsigned integers to single-precision float [0, 1)
    const float factor = 2.3283064365386963e-10f; // 1.0 / 2^32
    return convert_float4(ctr) * factor;
}

__kernel void generate_random_numbers(__global float4* output, 
                                      uint2 base_key, 
                                      uint steps_per_thread) {
    size_t gid = get_global_id(0);
    
    for (uint step = 0; step < steps_per_thread; ++step) {
        // Unique counter for every thread and step
        uint4 counter = (uint4)(gid, step, 0, 0);
        
        float4 random_vals = philox4x32(counter, base_key);
        
        output[gid * steps_per_thread + step] = random_vals;
    }
}

Key Optimizations for Maximum Throughput

  1. Leveraging mul_hi: Using OpenCL's built-in mul_hi() directly maps to the underlying hardware instruction (such as MUL.HI on NVIDIA GPUs or V_MUL_HI_U32 on AMD architectures), preventing expensive 64-bit emulation.
  2. Loop Unrolling: Apply #pragma unroll to the main transformation loop. Because the number of rounds (7 or 10) is static, unrolling enables the OpenCL compiler to schedule instructions across registers efficiently and eliminate branch overhead.
  3. Register Budget Management: Keep the counter representation inside registers (uint4). Avoid spilling registers to local memory (__local) or global memory (__global) within the inner loop, as Philox achieves maximum arithmetic intensity when completely self-contained in registers.
