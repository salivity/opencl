Mapping OpenCL Work-Items to GPU Threads

This article explains how OpenCL's abstract execution model translates directly to the physical silicon of modern Graphics Processing Units (GPUs). It breaks down the hierarchy of OpenCL work-items, sub-groups, and work-groups, detailing how they align with physical hardware components such as SIMD lanes, warps or wavefronts, and compute units across major GPU architectures.

The OpenCL Hierarchy vs. GPU Hardware

OpenCL uses an abstract execution hierarchy designed to scale across different types of processors. Modern GPUs execute these abstractions using massively parallel Single Instruction, Multiple Data (SIMD) or Single Instruction, Multiple Threads (SIMT) architectures.

The structural relationship maps as follows:

1. Work-Item to Physical SIMD Lane

A work-item represents a single invocation of a kernel. Physically, a work-item does not correspond to an independent CPU-like core with its own instruction fetch, decode, and control units. Instead, it corresponds to a single SIMD lane (an Arithmetic Logic Unit, or ALU) executing within a broader vector processing unit.

Each work-item maintains its own private state, which the hardware allocates out of a shared physical register file.

2. Lockstep Execution: Warps and Wavefronts

GPUs do not schedule individual work-items. Instead, the hardware bundles a fixed number of adjacent work-items into lockstep execution groups:

  • NVIDIA bundles 32 work-items into a Warp.
  • AMD bundles 32 or 64 work-items into a Wavefront.

All work-items in a warp or wavefront share a single instruction pointer and execute the exact same instruction simultaneously across parallel SIMD lanes.

  • Branch Divergence: If work-items within the same hardware group diverge at a conditional branch (if/else), the physical unit must execute each branch path sequentially, masking out (disabling) the lanes that do not participate in that path. This reduces overall hardware throughput.

3. Work-Group to Compute Unit (SM/CU)

An OpenCL work-group consists of multiple work-items that can synchronize execution using barriers and share high-speed data. Modern GPU hardware maps an entire work-group to a single physical Compute Unit (AMD) or Streaming Multiprocessor (NVIDIA).

  • Atomicity of Allocation: A work-group cannot be split across multiple physical compute units. All warps/wavefronts that comprise that work-group must execute on the same compute unit to guarantee synchronization and memory consistency.
  • Shared/Local Memory: OpenCL __local memory physically resides in on-chip SRAM located directly inside the compute unit (known as Shared Memory on NVIDIA, Local Data Share on AMD). Because local memory is physically tied to the compute unit, work-items within the work-group access this memory with extremely low latency.
  • Occupancy: A single physical compute unit can host multiple work-groups concurrently, provided it has enough physical registers, shared memory, and scheduling slots available.

4. NDRange and Hardware Schedulers

The global collection of all work-items is the NDRange. When a kernel is enqueued:

  1. The GPU’s global hardware scheduler receives the complete grid of work-groups.
  2. The scheduler distributes work-groups across available Compute Units / SMs until all physical capacity is occupied.
  3. As work-groups complete their execution, the global scheduler assigns new work-groups to the newly freed compute units until the NDRange is fully executed.

Latency Hiding in Hardware

Because modern GPUs have thousands of physical registers per compute unit, switching between warps or wavefronts incurs zero cycle overhead. When one set of work-items stalls on a high-latency operation (such as loading data from off-chip global VRAM), the on-chip warp/wavefront scheduler instantly switches the physical execution lanes to another group of work-items that is ready to compute. This mechanism, known as latency hiding, ensures physical hardware execution units maintain maximum utilization.
