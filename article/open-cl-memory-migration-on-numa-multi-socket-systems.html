OpenCL Memory Migration on NUMA Multi-Socket Systems

In multi-socket Non-Uniform Memory Access (NUMA) systems, OpenCL memory migration dictates how data buffers and Shared Virtual Memory (SVM) regions move between distinct physical memory domains and compute devices. Because memory access latency and throughput vary significantly depending on whether a CPU socket or PCIe accelerator accesses local or remote RAM, OpenCL memory migration relies on explicit runtime directives, operating system page-fault handling, and underlying interconnects to ensure high-performance execution.

NUMA Topologies and the OpenCL Memory Model

A multi-socket system features distinct CPU sockets, each directly linked to its own physical memory channels (a NUMA node). Sockets communicate over high-speed coherent interconnects, such as Intel Ultra Path Interconnect (UPI) or AMD Infinity Fabric.

When OpenCL operates on such a platform, compute devices generally fall into two categories:

  1. CPU Devices: OpenCL exposes host CPU cores as compute units. Kernels execute directly on the host processor across one or multiple sockets.
  2. Discrete Accelerators (GPUs, FPGAs): Devices attach via PCIe lanes physically routed to the PCIe controller of a specific CPU socket (the "local" NUMA node for that peripheral).

The behavior of memory migration depends on whether buffers are traditional discrete memory objects (cl_mem) or Shared Virtual Memory (SVM).

Explicit Buffer Migration via clEnqueueMigrateMemObjects

The primary OpenCL API mechanism for controlling memory placement is clEnqueueMigrateMemObjects. This command provides a hint or explicit instruction to the OpenCL runtime to migrate memory objects to the device associated with an OpenCL command queue prior to kernel execution.

  • Between Host and Discrete Devices: When migrating a buffer to a discrete accelerator, the runtime initiates direct memory access (DMA) transfers. If the buffer currently resides in the memory of the remote CPU socket, the DMA transfer must traverse the inter-socket interconnect to reach the PCIe controller attached to the GPU. This consumes inter-socket bandwidth and increases transfer latency compared to transfers originating from local NUMA memory.
  • Between CPU NUMA Nodes: If multiple OpenCL sub-devices represent different CPU sockets, issuing an explicit migration command signals the runtime to shift the backing host pages to the target socket’s local memory pool.

Shared Virtual Memory (SVM) and Page Migration

OpenCL 2.0 and later support Shared Virtual Memory, which enables host and devices to share a unified address space. SVM migration behavior differs based on the granularity supported:

  • Coarse-Grained Buffer SVM: Pointers are shared, but updates require explicit synchronization via clEnqueueMapBuffer and clEnqueueUnmapMemObject (or explicit migration calls). Data does not dynamically shift between NUMA nodes; it remains anchored to the allocating socket’s memory unless explicitly moved by the driver.
  • Fine-Grained Buffer/System SVM: Host threads and OpenCL devices can read and write to the same memory concurrently without manual synchronization markers. In platforms supporting hardware cache coherency and Heterogeneous Memory Management (HMM), page migration can happen on demand. When a compute thread on Socket 1 writes to a page physically hosted on Socket 0, the operating system kernel and OpenCL driver intercept the page fault and either service the request over the inter-socket link or migrate the physical page directly to Socket 1.

Impact of the OS "First-Touch" Policy

Most operating systems (such as Linux) implement a "First-Touch" allocation policy for host memory. When an application allocates host memory via clCreateBuffer with CL_MEM_ALLOC_HOST_PTR or standard system allocators, physical pages are not allocated until the memory is first accessed.

  • If the host setup thread initializes the buffer on Socket 0, all physical pages map to Socket 0's NUMA node.
  • If an OpenCL CPU queue subsequently executes the workload on compute units mapped to Socket 1, all memory read/write requests must cross the CPU interconnect.
  • Without explicit page migration, this cross-socket access introduces substantial latency and degrades throughput.

PCIe Device Affinity and Peer-to-Peer Traversal

For discrete devices, every PCIe slot is wired to a specific host socket. When migrating memory to an accelerator:

  1. Local Node Transfer: If the OpenCL buffer resides on the NUMA node directly controlling the device's PCIe root complex, data moves straight through the local memory bus into PCIe lanes at peak line rate.
  2. Remote Node Transfer: If data resides on a remote NUMA node, transfers must first cross the inter-socket link to reach the host socket hosting the PCIe root complex. This path can introduce transfer bottlenecks, especially when multiple accelerators simultaneously pull data from remote nodes.

Performance Considerations

Optimizing OpenCL memory migration on NUMA architectures requires mitigating inter-socket overhead through deliberate placement:

  • NUMA Binding: Pin OpenCL host threads to the NUMA node topologically closest to the target device or PCIe controller using OS utilities (e.g., numactl) or thread-affinity APIs.
  • Proactive Migration: Use clEnqueueMigrateMemObjects early in the execution pipeline to overlap page transfer with ongoing computation, preventing on-demand page faults during kernel execution.
  • Partitioning: When targeting multi-socket CPUs via OpenCL, partition the device into sub-devices per socket (CL_DEVICE_PARTITION_BY_AFFINITY_DOMAIN) and manage separate, locally allocated memory pools for each partition.
