OpenCL In-Order vs Out-of-Order Command Queues

This article provides an overview of the differences between in-order and out-of-order command queues in OpenCL. It explores how each execution model schedules commands, how dependencies and synchronization are handled, and the performance trade-offs developers face when choosing between deterministic execution and hardware-level parallelism.

Understanding OpenCL Command Queues

In OpenCL, the host application interacts with target devices (such as GPUs or CPUs) through command queues. A command queue receives commands—such as kernel execution requests, memory reads, writes, and copies—and dispatches them to the device for execution. By default, an OpenCL command queue operates in an in-order fashion, but it can be configured as an out-of-order queue using the CL_QUEUE_OUT_OF_ORDER_EXEC_MODE_ENABLE property during queue creation.

In-Order Command Queues

An in-order command queue guarantees that commands are executed sequentially in the exact order they are submitted by the host.

  • Execution Flow: A command will not begin execution until the immediately preceding command has fully completed.
  • Implicit Synchronization: Because execution is strictly serial, there is no need to manually coordinate dependencies between commands. For example, if you enqueue a memory write followed by a kernel that reads that data, the kernel will naturally wait until the write operation finishes.
  • Simplicity: In-order queues reduce programming complexity and eliminate data race hazards between sequential commands.
  • Limitation: The strict sequential requirement can underutilize device hardware. Independent operations—such as transferring data while running a separate kernel—cannot overlap automatically, potentially introducing idle hardware cycles.

Out-of-Order Command Queues

An out-of-order command queue allows commands to be executed as soon as device resources become available, regardless of submission order.

  • Execution Flow: Commands can begin, run concurrently, and finish in any order. The device scheduler decides the order based on available compute units and memory bandwidth.
  • Explicit Synchronization: Because commands do not wait for one another automatically, the developer must explicitly define execution dependencies. This is achieved using OpenCL events (cl_event), event wait lists, markers (clEnqueueMarkerWithWaitList), and barriers (clEnqueueBarrierWithWaitList). A command provided with an event wait list will hold execution until all specified prerequisite events are satisfied.
  • Performance Advantage: Out-of-order execution enables simultaneous execution of independent kernels and concurrent memory transfers with compute operations, maximizing device utilization.
  • Complexity: Failure to properly specify dependencies leads to race conditions, data corruption, or undefined behavior.

Summary of Key Differences

Feature In-Order Queue Out-of-Order Queue
Default Status Yes (default behavior) No (requires explicit flag)
Execution Order Strictly follows submission order Non-deterministic, resource-driven
Synchronization Implicitly handled by the queue Explicitly handled via events and barriers
Development Effort Low; minimal synchronization logic needed High; developer must manage dependency graphs
Hardware Utilization Can introduce idle time between independent tasks High; facilitates overlap of compute and data transfers

When to Use Each

Use an in-order queue when computational workflows are fundamentally linear, when prototyping, or when the overhead of managing complex event graphs outweighs the performance gains.

Use an out-of-order queue when an application has independent tasks that can run in parallel, such as heterogeneous workloads with overlapping PCIe transfers and kernel executions, and maximum hardware saturation is required.
