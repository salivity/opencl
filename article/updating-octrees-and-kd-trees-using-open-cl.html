Updating Octrees and KD-Trees Using OpenCL

Maintaining dynamic spatial partitioning structures like octrees and kd-trees on the GPU requires adapting hierarchical data to massive parallel architectures that lack dynamic memory allocation and deep call stacks. This article details practical methods for maintaining and updating these structures using OpenCL, focusing on linear tree representations, Morton code sorting, bottom-up refitting via atomic barriers, and evaluating the trade-offs between incremental structural updates and fast full parallel rebuilds.

Flattening Tree Hierarchies for OpenCL

Standard pointer-based tree structures are inefficient on GPUs due to dynamic memory management constraints and divergent branch execution. To maintain an octree or kd-tree in OpenCL, the tree must be linearized into pre-allocated, contiguous cl_mem buffers.

  • Index-Based Arrays: Nodes are stored in flat arrays where parent-child relationships are tracked via integer offsets rather than memory pointers. A typical node structure contains an axis-aligned bounding box (AABB), a child index offset, and metadata flags packed into vector types (e.g., float4, int4) to optimize memory coalescing.
  • Linear Octrees (Morton Codes): Instead of explicit hierarchy pointers, primitives are sorted along a space-filling curve (Z-order curve) by calculating their 30-bit or 63-bit Morton codes. In this structure, the hierarchy is implicit, enabling parallel binary searches to locate parent-child relationships.

Fast Dynamic Updates: Refitting vs. Rebuilding

When geometry moves, the spatial partitioning structure must reflect the changes. Depending on the extent of deformation or movement, two primary update paths exist:

1. Bottom-Up AABB Refitting

If primitives move continuously without drastically altering the overall spatial topology, refitting existing nodes is significantly faster than rebuilding the entire tree.

  1. Leaf Update Kernel: A parallel OpenCL kernel assigns one work-item per leaf node. The kernel recalculates the bounding box of the leaf based on the updated positions of its contained primitives.
  2. Bottom-Up Propagation: Propagating bounding volumes up to the root cannot use recursion. Instead, OpenCL uses atomic counters. Each parent node maintains an atomic flag initialized to zero. When a child finishes computing its AABB, it executes an atomic_inc on its parent's counter:
    • If the child is not the last to complete (the returned value is less than the child count minus one), the work-item terminates.
    • The final child to finish (the one that advances the counter to the child count) processes the parent node, aggregates the bounding boxes of all children, and moves up to the next hierarchical level.

This synchronization pattern ensures that work-items do not stall in busy-wait loops, maintaining high compute utilization.

2. Full Parallel Rebuild via Sort-and-Extract

When primitives experience large, discontinuous transformations, the existing tree topology degrades, resulting in overlapping bounding boxes and poor spatial culling. In OpenCL, rebuilding a linear tree from scratch is frequently faster than restructuring an unbalanced tree.

  1. Generate Keys: Compute the centroid and Morton code for each moving primitive in parallel using a mapping kernel.
  2. Parallel Radix Sort: Sort the primitive indices using their Morton codes. An OpenCL parallel radix sort implementation (using local memory for histogram calculation and prefix-sums/scans) reorders primitives efficiently.
  3. Hierarchy Construction (Karras Algorithm): Octrees and bounding volume hierarchies can be generated concurrently in a single pass over the sorted array. A kernel assigns one work-item to each split between elements. By determining the common prefix length between adjacent Morton codes, the kernel establishes internal node split positions and child ranges without global synchronization.

Handling KD-Tree Maintenance

KD-trees partition space using splitting planes (alternating axes or Surface Area Heuristic [SAH]) rather than regular cubic subdivisions, making maintenance more complex than octrees.

  • Refitting Limits: Because kd-tree split planes are static, moving primitives can violate plane boundaries, rendering pure AABB refitting invalid if an object crosses into a neighboring spatial cell.
  • Median-Split Fast Rebuild: For dynamic kd-trees, maintaining strict SAH splits at runtime is cost-prohibitive. Instead, implement a GPU-friendly spatial median split. Use the OpenCL kernel to calculate the spatial midpoint of the bounding box at the current tree depth, partition primitives using parallel compaction (cl_mem stream compaction), and proceed down to the maximum allowed depth.
  • Loose Bounds: Alternatively, implement a "loose" kd-tree structure where leaf boundaries are extended by an overlap margin. Small primitive movements within this margin do not require tree updates, reducing the update frequency to only when primitives breach the margin boundaries.

OpenCL Memory and Execution Considerations

  • Avoiding Buffer Reallocation: Pre-allocate maximum node bounds at initialization using CL_MEM_READ_WRITE. Rebuilding or updating trees in-place avoids the latency of host-side memory allocations and clSetKernelArg updates.
  • Work-Group Local Memory: During radix sorting and leaf node reduction, cache bounding boxes in __local memory to avoid high-latency global memory round trips.
  • Divergence Mitigation: When traversing or updating kd-trees and octrees, structure kernels to minimize warp/wavefront divergence by ensuring neighboring work-items in a work-group operate on spatially adjacent nodes.
