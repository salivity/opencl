AMD Wavefronts in OpenCL Work-Group Execution

In heterogeneous computing, mapping abstract software abstractions to physical hardware is essential for achieving optimal performance. In OpenCL, parallel computation is structured hierarchically into an NDRange containing work-groups, which in turn consist of individual work-items. AMD hardware bridges this software model to physical silicon through a construct known as a wavefront. This article explains how AMD's wavefront functions as the hardware execution slice of an OpenCL work-group, detailing how work-items are grouped, scheduled, and executed across SIMD units.

The OpenCL Hierarchy vs. AMD Hardware

OpenCL defines a vendor-agnostic software model:

  • Work-item: The smallest unit of execution (a single thread).
  • Work-group: A collection of work-items that execute concurrently, share a common local memory space, and synchronize via barriers.

AMD hardware does not execute an entire work-group as a single monolithic block. Instead, the hardware scheduler breaks down each work-group into discrete, fixed-size execution slices called wavefronts. A wavefront consists of a fixed number of work-items—historically 64 in Graphics Core Next (GCN) architectures, and either 32 or 64 in RDNA architectures (Wave32 and Wave64 modes).

Wavefronts as Work-Group Slices

When an OpenCL kernel is queued for execution, the runtime assigns each work-group to a specific AMD Compute Unit (CU) or Workgroup Processor (WGP). Within that compute unit, the work-group is partitioned linearly along its local dimensions into wavefronts.

For example, if an OpenCL work-group is configured with a size of 256 work-items on a GPU using Wave64:

  1. The hardware runtime divides the 256 work-items into four discrete wavefronts of 64 work-items each.
  2. Each wavefront is assigned a set of vector registers and execution slots on the Compute Unit's SIMD units.
  3. These four wavefronts represent the actual execution slices of the parent work-group.

The wavefront is the fundamental unit of scheduling. The hardware's instruction issue logic tracks the program counter and state at the wavefront level, rather than tracking individual work-items.

SIMT Execution and Lockstep Processing

Wavefronts execute using a Single Instruction, Multiple Threads (SIMT) model. All work-items within a single wavefront execute the identical instruction simultaneously on physical vector ALUs.

If code within a wavefront encounters divergent branching (such as an if/else condition where some work-items evaluate to true and others to false), the hardware does not execute branches in parallel. Instead, it serializes the execution paths. It executes the if block with a bitmask disabling the inactive lanes, and then executes the else block with an inverted bitmask. Because execution is tied to the wavefront slice, branching divergence inside a single wavefront reduces throughput, whereas divergence between separate wavefronts carries no performance penalty.

Memory and Synchronization Boundaries

While the wavefront is the execution slice, the OpenCL work-group remains the boundary for memory and synchronization:

  • Local Memory (LDS): Local Data Share memory is allocated per work-group, allowing all constituent wavefronts within that work-group to exchange data.
  • Barriers: When an OpenCL kernel invokes barrier(CLK_LOCAL_MEM_FENCE), execution pauses for each wavefront in the work-group until all wavefronts within that work-group reach the same synchronization point.

Within a single wavefront, synchronization is implicit because work-items execute in lockstep. However, communication between different wavefronts inside the same work-group requires explicit barriers and local memory operations.

Performance Implications

Understanding the relationship between work-groups and wavefronts is critical for optimizing OpenCL performance on AMD GPUs:

  • Sizing Multiples: Work-group sizes should always be integer multiples of the target architecture's wavefront size (32 or 64). If a work-group contains 70 work-items on a Wave64 architecture, the hardware must allocate two full wavefronts (128 lanes), leaving 58 lanes inactive in the second wavefront, which wastes execution resources.
  • Occupancy: Compute units have limits on the total number of wavefronts they can track concurrently. Sizing work-groups to balance register usage and shared memory allocation allows the scheduler to interleave multiple wavefronts, hiding memory latency through hardware multithreading.
