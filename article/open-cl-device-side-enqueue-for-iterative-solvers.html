OpenCL Device-Side Enqueue for Iterative Solvers

Device-side enqueue, introduced in OpenCL 2.0, allows compute devices to launch kernels directly without host CPU intervention, fundamentally changing how iterative numerical solvers manage execution. In traditional pipelines, each solver iteration requires synchronization with the CPU to assess convergence and determine the next dispatch parameters, introducing severe latency bottlenecks. By offloading scheduling logic directly to the device, iterative solvers can dynamically adapt their execution grids, prune converged sub-domains, and distribute irregular computational workloads in real time with minimal overhead.

In an iterative solver, such as a Conjugate Gradient, Jacobi, or Adaptive Mesh Refinement (AMR) system, computational density often shifts across domains as the simulation progresses. When using device-side enqueue, a parent kernel executes an iteration step or a coarse-grained evaluation phase. Instead of returning control to the host to check residual errors, the parent kernel reads the device memory directly to identify areas requiring further computation. Based on local error metrics or convergence criteria, the parent kernel calls enqueue_kernel to spawn specialized child kernels targeted specifically at unresolved regions.

This autonomous dispatch mechanism dynamically adjusts work distribution in three primary ways:

1. Dynamic Grid Sizing and Sub-Domain Pruning
Traditional static implementations must dispatch over the entire problem space for every iteration, wasting execution resources on threads that simply exit early because their local data has already converged. With device-side enqueue, parent threads evaluate local residual thresholds and dynamically compute the precise dimensions (ndrange_t) for the next iteration. Child kernels are only launched for active, unconverged cells or blocks, effectively concentrating the device's compute units where work is actually needed.

2. Hierarchical Load Balancing
Iterative algorithms often encounter load imbalances when localized phenomena (such as shock fronts, crack propagation, or fluid turbulence) require higher precision or smaller time steps than the rest of the domain. Device-side enqueue enables a nested parallelism model. A high-level parent kernel processes macro-blocks, dynamically enqueuing fine-grained child kernels with variable local and global work-group sizes depending on the local complexity of each block. This prevents underutilization of compute units by dynamically matching the hardware dispatch size to the data complexity.

3. Elimination of Host-Device Latency
In standard OpenCL architectures, issuing thousands of small, adaptive iterations incurs substantial PCIe transit and driver execution overhead. Device-side enqueue routes execution queues directly within device memory and internal scheduling hardware. The GPU or accelerator schedules child kernels as soon as execution resources become available, maintaining high occupancy on compute units and eliminating the latency tail that typically degrades performance in iterative solvers.

By coupling execution decisions directly to data evaluation on the hardware, device-side enqueue transforms iterative OpenCL solvers from rigid, host-bound dispatch loops into adaptive, self-governing computational graphs.
