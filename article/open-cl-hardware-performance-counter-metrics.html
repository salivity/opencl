OpenCL Hardware Performance Counter Metrics

OpenCL tools interface directly with underlying GPU and accelerator performance counters to provide deep visibility into compute kernel execution. By querying these hardware registers, profiling tools can capture essential performance metrics across execution timing, compute utilization, memory subsystem throughput, and pipeline stall conditions. Understanding these metrics enables developers to locate computational bottlenecks, minimize memory latency, and maximize hardware occupancy across heterogeneous platforms.

Execution and Event Timing Metrics

At the API level, OpenCL exposes hardware execution metrics via its built-in event profiling mechanism (clGetEventProfilingInfo). These provide baseline wall-clock timings:

  • Queue-to-Submit Latency (CL_PROFILING_COMMAND_QUEUED to CL_PROFILING_COMMAND_SUBMIT): Measures the driver overhead required to transfer a command to the device queue.
  • Submit-to-Start Latency (CL_PROFILING_COMMAND_SUBMIT to CL_PROFILING_COMMAND_START): Captures the host-to-device synchronization latency before kernel execution actually begins.
  • Kernel Execution Time (CL_PROFILING_COMMAND_START to CL_PROFILING_COMMAND_END): The exact duration the compute device spent executing the kernel code on its compute units.

Compute Core and Instruction Metrics

Low-level vendor profiling tools (such as Intel VTune, AMD ROCm Profiler/Omnitrace, and legacy NVIDIA Profilers) capture hardware counters that reflect ALU pipeline utilization and instruction retirement:

  • Active Compute Units / SMs: The percentage of available compute units actively scheduling and processing work.
  • ALU Utilization and Instruction Mix: The count of executed instructions broken down by type:
    • Single-precision (FP32), double-precision (FP64), and half-precision (FP16) floating-point operations.
    • Integer arithmetic operations (INT32, INT64).
    • Special function operations (transcendental instructions like sine, cosine, square root).
  • SIMD / Wavefront Occupancy: The ratio of active threads (work-items) participating in execution masks compared to the maximum SIMD width (e.g., 32 for NVIDIA warps, 32 or 64 for AMD wavefronts).
  • Branch Divergence: The number of divergent execution paths encountered within a work-group, reflecting wasted cycles where lanes are masked off due to conditional branching.

Memory Hierarchy and Bandwidth Metrics

Memory operations often form the primary bottleneck in compute kernels. Hardware performance counters monitor throughput across every cache tier:

  • Global Memory Bandwidth: Aggregate read and write volume over time between compute units and external VRAM/DRAM, compared against the device's peak theoretical bandwidth.
  • Memory Access Coalescing: The ratio of requested memory bytes to the actual bytes transferred across the memory bus. Non-coalesced access patterns trigger redundant memory transactions.
  • Cache Hit and Miss Rates:
    • L1 Data Cache: Transaction counts, hit rates, and evictions per compute unit.
    • L2 Cache: Read/write request counts, miss rates, and crossbar interconnect traffic.
  • Local Memory (LDS / Shared Memory) Efficiency: Tracks local memory load/store operations, read/write throughput, and the count of bank conflicts, which force parallel accesses to serialize.
  • Constant Cache Hit Rates: Efficiency metrics for constant memory reads broadcast across work-items.

Pipeline Stalls and Resource Limits

Profiling tools track execution bubbles to reveal why hardware execution units remain idle:

  • Memory Dependency Stalls: Cycles spent waiting for data to return from global memory or cache lines before an instruction can issue.
  • Execution / Register Dependency Stalls: Cycles lost waiting for the results of previous ALU operations.
  • Barrier Synchronization Overhead: Cycles lost while work-items wait at barrier(CLK_LOCAL_MEM_FENCE) or global sync points.
  • Register and Shared Memory Allocation: The number of vector and scalar registers consumed per work-item, along with allocated local memory per work-group. High resource consumption reduces theoretical occupancy by limiting the number of in-flight work-groups the hardware can schedule concurrently.
