Understanding clCreatePipe in OpenCL 2.0

In OpenCL 2.0, the clCreatePipe function creates a specialized FIFO (first-in, first-out) memory object that enables direct kernel-to-kernel communication on a computing device. This mechanism allows a producer kernel to stream data directly to a consumer kernel without synchronizing through the host application or writing intermediate arrays to standard global memory buffers. This article explains the role of clCreatePipe, its syntax and key parameters, and how it facilitates low-latency data exchange in OpenCL 2.0 pipeline architectures.

The Role of clCreatePipe

Traditionally, sharing data between two OpenCL kernels required the producer kernel to write results into a global memory buffer (cl_mem), wait for completion via an event or barrier, and then launch the consumer kernel to read the buffer. clCreatePipe replaces this disjointed process by allocating a pipe object.

A pipe stores organized packets in a FIFO queue. Kernels can read from and write to this queue concurrently, facilitating streaming and producer-consumer workflows. Because the runtime and device manage synchronization internally, kernels can overlap execution, significantly reducing memory bandwidth usage and end-to-end latency.

Function Signature and Parameters

The host creates a pipe using the following OpenCL API signature:

cl_mem clCreatePipe(cl_context context,
                    cl_mem_flags flags,
                    cl_uint pipe_packet_size,
                    cl_uint pipe_max_packets,
                    const cl_pipe_properties *properties,
                    cl_int *errcode_ret);
  • context: A valid OpenCL context in which the pipe is created.
  • flags: Memory allocation flags specifying access properties. Pipes typically use CL_MEM_READ_WRITE and often CL_MEM_HOST_NO_ACCESS, as pipes are generally intended strictly for device-side execution and are inaccessible from the host.
  • pipe_packet_size: The size, in bytes, of a single data element (packet) stored within the pipe.
  • pipe_max_packets: The maximum capacity of the pipe, defined as the total number of packets it can hold at any given time.
  • properties: Reserved for future extensions in OpenCL 2.0; typically set to NULL.
  • errcode_ret: Returns an error code indicating success (CL_SUCCESS) or specific failure states (such as CL_INVALID_PIPE_SIZE).

Setting Up Kernel-to-Kernel Communication

Establishing kernel-to-kernel communication using clCreatePipe involves three primary phases:

  1. Host Allocation: The host calls clCreatePipe to specify the structural boundaries of the pipe—namely the size of each packet and the buffer depth.
  2. Kernel Argument Binding: The host passes the resulting cl_mem handle as an argument to both the producer kernel and the consumer kernel using clSetKernelArg.
  3. Device-Side Operation:
    • In OpenCL C device code, the argument is typed as pipe <type>.
    • The producer kernel uses the built-in function write_pipe() to push packets into the pipe.
    • The consumer kernel uses read_pipe() to extract packets from the pipe.
    • Both built-in functions return status codes indicating whether the reservation or transfer succeeded, allowing kernels to handle full or empty conditions dynamically without stalling the entire compute unit.

Benefits of Pipe-Based Communication

  • Decoupled Work-Groups: Work-items in the consumer kernel do not need to wait for the producer kernel to finish execution completely before they begin processing data.
  • Memory Bandwidth Conservation: On architectures that support on-chip pipe storage (such as FPGAs or specialized GPUs), data passing through a pipe can stay inside fast local SRAM or registers rather than traversing external DRAM.
  • Thread Safety: Read and write operations to pipes are thread-safe at the packet level, abstracting away the low-level synchronization barriers required when manually implementing circular ring buffers in standard global memory.
