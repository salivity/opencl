OpenCL get_local_id Work-Group Indexing Explained

In OpenCL, parallel execution is organized hierarchically into an NDRange, work-groups, and individual work-items. This article explains how the built-in function get_local_id provides relative coordinate indexing within a localized work-group. Readers will learn the mechanics of work-item positioning, dimensional indexing across up to three dimensions, and how these local coordinates are used for shared local memory access and intra-work-group collaboration.

The OpenCL Execution Hierarchy

OpenCL divides computational tasks across an N-dimensional space known as the NDRange (1D, 2D, or 3D). The entire NDRange is split into multiple independent subsets called work-groups, each containing an identical number of work-items (threads).

While every work-item possesses a unique global coordinate within the overall NDRange (retrieved via get_global_id), it also possesses a local coordinate relative only to the specific work-group to which it belongs. The get_local_id function provides access to this relative coordinate.

Syntax and Dimensional Indexing

The function signature for get_local_id is defined as:

size_t get_local_id(uint dimindx);

The parameter dimindx represents the dimension for which the coordinate index is requested:

  • dimindx = 0: Corresponds to the X dimension.
  • dimindx = 1: Corresponds to the Y dimension.
  • dimindx = 2: Corresponds to the Z dimension.

For any given dimension, the index returned by get_local_id(dimindx) starts at 0 and increments sequentially up to get_local_size(dimindx) - 1. Regardless of where a work-group is situated in the broader NDRange, the first work-item in that work-group always receives a local ID of 0 along each active axis.

Coordinate Mapping and Linearization

Work-groups frequently process multi-dimensional data, such as images or matrices. Within these structures, get_local_id acts as an offset within the local execution block.

When accessing one-dimensional storage arrays (such as linear allocations in __local memory) using multi-dimensional coordinates, get_local_id is used to calculate a unique 1D linear index:

// 2D to 1D Linearization
size_t local_x = get_local_id(0);
size_t local_y = get_local_id(1);
size_t local_width = get_local_size(0);

size_t local_index = local_y * local_width + local_x;

This mapping guarantees that each work-item within the work-group is assigned a unique slot in the local buffer without overlapping with other items in the same group.

Primary Use Cases

1. Local Memory Staging (Tiling)

High-performance kernels often stage data from high-latency global memory into low-latency __local memory. Work-items use get_global_id to determine which data point to fetch from global RAM, but use get_local_id to determine where to store that data within the group's shared memory cache.

__kernel void matrix_tile_example(__global float *input, __local float *tile) {
    size_t gx = get_global_id(0);
    size_t gy = get_global_id(1);
    size_t lx = get_local_id(0);
    size_t ly = get_local_id(1);
    size_t local_w = get_local_size(0);
    size_t global_w = get_global_size(0);

    // Read from global, write to local
    tile[ly * local_w + lx] = input[gy * global_w + gx];

    barrier(CLK_LOCAL_MEM_FENCE);
    // Computation on shared tile follows...
}

2. Intra-Group Reductions

Parallel reduction operations (such as finding a sum, minimum, or maximum across an array) rely on tree-based algorithms executed inside a work-group. get_local_id(0) is used conditionally to deactivate half of the active threads at each step of the reduction tree:

for (unsigned int stride = get_local_size(0) / 2; stride > 0; stride >>= 1) {
    barrier(CLK_LOCAL_MEM_FENCE);
    if (get_local_id(0) < stride) {
        tile[get_local_id(0)] += tile[get_local_id(0) + stride];
    }
}

By providing a stable, zero-based coordinate space for each work-group, get_local_id enables predictable memory access patterns, safe thread-level synchronization, and efficient data reuse across hardware compute units.
