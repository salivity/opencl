OpenCL __local Qualifier Scope and Lifetime

The __local (or local) address space qualifier in OpenCL designates variables that reside in a device's high-speed, on-chip shared memory. Applying this qualifier alters standard C storage behavior, binding the variable's memory and state to a specific work-group rather than an individual thread or the entire compute device. This article details how the __local qualifier dictates variable visibility (scope), persistence (lifetime), allocation constraints, and synchronization requirements during kernel execution.

Variable Scope with __local

In OpenCL, the scope of a __local variable defines where that identifier can be referenced in code and which threads have access to its underlying data:

  • Syntactic Scope: When declared inside a kernel function, a __local variable follows standard C block scoping rules. The identifier is only visible within the block or function in which it is declared. It cannot be declared at the global program scope outside of kernel functions.
  • Execution Scope: Even though the variable's name may be restricted to a specific block, the underlying memory is shared across all work-items within the same work-group. Any work-item in that work-group can read from or write to that memory location, provided it has access to the variable or a pointer referencing it.
  • Kernel Argument Scope: When __local is applied to a pointer argument of a kernel function (e.g., __local float *shared_data), the variable points to a block of local memory allocated dynamically by the host. In this scenario, the variable is visible throughout the entire kernel body to all work-items in the work-group.

Variable Lifetime with __local

The lifetime of a __local variable is strictly tied to the life cycle of the work-group executing the kernel:

  • Creation: Memory for a __local variable is allocated when a work-group begins executing on a compute unit.
  • Persistence: The data stored in __local variables persists for the duration of that specific work-group's execution. Multiple work-items within the group can repeatedly read and write to this shared storage during the kernel run.
  • Destruction: The memory is released as soon as all work-items in the work-group finish execution. Data does not persist across successive work-groups, nor does it persist across different kernel executions.

Declaration Rules and Restrictions

Using the __local qualifier introduces specific compiler and runtime restrictions:

  1. No Direct Initialization: Local variables declared inside a kernel cannot be initialized at the point of declaration (e.g., __local int counter = 0; is invalid). Initialization must occur dynamically through explicit code executed by one or more work-items.
  2. Dynamic vs. Static Allocation:
    • Static allocation: Declared inside the kernel body with a fixed size known at compile time (e.g., __local float buffer[256];).
    • Dynamic allocation: Declared as a kernel parameter and allocated from the host application using clSetKernelArg with a NULL pointer and the desired byte size.

Synchronization and Memory Consistency

Because the lifetime and scope of __local variables span an entire work-group, concurrent read and write operations by multiple work-items can cause race conditions. OpenCL does not guarantee automatic cache coherency or execution order among work-items.

To safely use __local data across work-items, you must use work-group barriers:

barrier(CLK_LOCAL_MEM_FENCE);

This barrier ensures that all work-items within the work-group reach the same point in execution and that all reads and writes to local memory are visible to all work-items before execution proceeds.
