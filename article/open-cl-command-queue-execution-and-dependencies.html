OpenCL Command Queue Execution and Dependencies

OpenCL command queues manage task scheduling and device synchronization by directing commands from the host application to compute devices. Depending on whether a queue is configured for in-order or out-of-order execution, the runtime determines when tasks begin, while event objects, wait-lists, and synchronization barriers provide precise control over data dependencies across single or multiple devices.

Queue Execution Modes

When an OpenCL command queue is created, its execution model is defined by its properties.

  • In-Order Execution: By default, command queues execute commands sequentially. A command will only start execution after the preceding command in the queue has completely finished. This ensures strict ordering without requiring manual synchronization, making it ideal for simple, linear pipelines. However, in-order queues can underutilize hardware by preventing the simultaneous execution of independent tasks or the overlap of data transfers with compute kernels.
  • Out-of-Order Execution: When configured with the CL_QUEUE_OUT_OF_ORDER_EXEC_MODE_ENABLE property, commands are dispatched as soon as device resources become available. There is no guarantee regarding the order in which commands start or finish. This mode maximizes throughput by overlapping kernel executions and asynchronous memory operations, but it places the responsibility of managing dependencies entirely on the developer.

Dependency Tracking Using Events

In out-of-order execution, or when coordinating tasks across multiple queues, OpenCL relies on cl_event objects to track execution state and resolve dependencies.

Most OpenCL enqueue functions (such as clEnqueueNDRangeKernel, clEnqueueReadBuffer, or clEnqueueCopyBuffer) accept two parameters related to events:

  1. An event wait-list (event_wait_list): An array of events that must reach the CL_COMPLETE state before the current command can begin execution.
  2. An output event pointer (event): Returns a handle to a new event representing the newly enqueued command.

When a command is submitted with an event wait-list, the OpenCL runtime places the command in a CL_SUBMITTED state. The runtime monitors the dependencies, and only when every event in the wait-list transitions to CL_COMPLETE does the command transition to CL_QUEUED and then CL_RUNNING.

Queue Barriers and Markers

OpenCL provides specific enqueue commands to implement synchronization points directly within the command stream without requiring explicit event arrays on every single operation:

  • clEnqueueBarrierWithWaitList: Acts as an execution fence. It prevents any subsequently enqueued commands in that specific queue from executing until all commands in the barrier's event wait-list (or all previously enqueued commands, if no list is provided) have fully completed.
  • clEnqueueMarkerWithWaitList: Enqueues a marker command that does not execute hardware work, but produces an event that signals completion once all events in its wait-list have completed. This provides a lightweight mechanism to group multiple operations into a single completion event.

Cross-Queue and Host-Device Synchronization

Because cl_event objects belong to an OpenCL context rather than a specific queue, they can resolve dependencies across different queues and devices. An event generated by a data transfer on a copy queue can be placed into the wait-list of a compute kernel on an execution queue, enabling cross-queue pipelines.

For host-side synchronization, the host program can block execution until specific events finish using clWaitForEvents. Alternatively, non-blocking execution can be maintained using clSetEventCallback, which triggers a host function callback when an event reaches a specified execution status, such as completion or an error state.
