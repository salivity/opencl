How to Avoid OpenCL Local Memory Bank Conflicts

OpenCL local memory provides high-bandwidth, low-latency data sharing among work-items within the same work-group. However, because local memory is divided into equally sized, independent memory banks, simultaneous access by multiple work-items to different addresses within the same bank causes memory serialization known as a bank conflict. This article outlines the architecture behind local memory banks and provides actionable strategies—including memory padding, optimized access strides, and broadcast utilization—to eliminate bank conflicts and maximize kernel throughput.

Understanding Local Memory Banks

On modern GPU architectures, local memory (often called shared memory) is physically divided into a fixed number of banks, typically 32 banks of 4-byte (32-bit) words.

Bank assignment is interleaved at the word level:

  • Bank Index = (Address / 4 bytes) % Number of Banks

When work-items in a warp or wavefront execute a load or store instruction:

  • No conflict: Each work-item accesses an address mapped to a unique bank. All requests are served in a single cycle.
  • Broadcast/Multicast: Multiple work-items read the exact same address within the same bank. The hardware serves the data simultaneously in a single transaction without serialization.
  • Bank Conflict: Two or more work-items access different addresses residing in the same bank. The memory controller must serialize these accesses, increasing latency proportionally to the degree of the conflict (e.g., a 2-way conflict doubles execution time for that memory transaction).

Key Strategies to Eliminate Bank Conflicts

1. Add Memory Padding to Multi-Dimensional Allocations

The most common cause of bank conflicts occurs when work-items read or write columns of a 2D matrix stored in local memory.

If a 2D tile has a width that is a multiple of the bank count (such as 32 words wide):

  • Work-item 0 accesses matrix[0][0] (Bank 0)
  • Work-item 1 accesses matrix[1][0] (Address offset by 32 words \(\rightarrow\) Bank 0)
  • All 32 work-items hit Bank 0, creating a catastrophic 32-way bank conflict.

Solution: Pad the row dimension by one element (or an odd number of words) so that successive rows start in staggered banks.

#define TILE_DIM 32
#define PADDED_DIM (TILE_DIM + 1) // Breaks the stride alignment

__kernel void matrixTranspose(__global float* output, __global float* input) {
    __local float tile[TILE_DIM][PADDED_DIM];

    int lx = get_local_id(0);
    int ly = get_local_id(1);

    // Staggered layout prevents bank conflicts during transposed writes/reads
    tile[ly][lx] = input[...];
    barrier(CLK_LOCAL_MEM_FENCE);

    output[...] = tile[lx][ly];
}

2. Maintain a Unit Stride (Stride-1) Access Pattern

Bank conflicts naturally disappear when consecutive work-items access consecutive memory addresses.

  • Good (Stride 1): Work-item \(i\) accesses index \(i\). Work-items 0 to 31 access Banks 0 to 31 simultaneously.
  • Bad (Non-Unit Stride): Work-item \(i\) accesses index \(i \times 2\). Work-items 0 to 15 access Banks 0, 2, 4, ..., 30, while work-items 16 to 31 also access Banks 0, 2, 4, ..., 30, resulting in a 2-way conflict.

When writing reduction kernels or parallel scans, restructure algorithms to use contiguous blocks rather than strided access patterns:

// Prone to bank conflicts: strided indexing
for (int stride = 1; stride < group_size; stride *= 2) {
    int index = 2 * stride * tid;
    if (index < group_size) {
        shared_data[index] += shared_data[index + stride];
    }
    barrier(CLK_LOCAL_MEM_FENCE);
}

// Conflict-free: contiguous indexing
for (int stride = group_size / 2; stride > 0; stride >>= 1) {
    if (tid < stride) {
        shared_data[tid] += shared_data[tid + stride];
    }
    barrier(CLK_LOCAL_MEM_FENCE);
}

3. Exploit the Hardware Broadcast Mechanism

When all work-items in a wavefront read from the exact same local memory address, the hardware routes the value to all requesting threads via a single broadcast transaction. If an algorithm requires a shared configuration value, lookup parameter, or pivot element, reading it directly from a single local address avoids serialization entirely. Note that broadcast only applies to reads; simultaneous writes to the exact same address cause undefined behavior or race conditions.

4. Align Vector Data Types Appropriately

Using OpenCL vector data types like float4 (16 bytes) in local memory requires understanding bank allocation. A single float4 spans four consecutive 32-bit banks.

  • If work-item 0 reads local_ptr[0] (occupying Banks 0–3) and work-item 1 reads local_ptr[1] (occupying Banks 4–7), the hardware executes this in multiple cycles because each bank handles only one request per cycle.
  • On some architectures, wider vector accesses can induce internal serialization if memory interfaces are 32-bit. In performance-critical kernels, profiling scalar types (float) versus vector types (float4) in local memory reveals whether vector operations are introducing hidden bank constraints.

5. Reorganize Thread-to-Data Mapping

When data cannot be padded easily, remap how work-items map to memory coordinates using XOR swizzling or index transformation.

By using bitwise operations on work-item IDs:

int bank_conflict_free_index = lx ^ ly;

Swizzling breaks power-of-two memory access patterns without requiring additional memory allocation, effectively distributing concurrent requests across distinct banks.
