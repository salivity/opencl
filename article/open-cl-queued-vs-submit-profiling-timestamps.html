OpenCL Queued vs Submit Profiling Timestamps

OpenCL provides built-in event profiling capabilities to analyze performance bottlenecks across the host and compute devices. When profiling is enabled on a command queue, the API tracks commands as they progress through different states: queued, submitted, started, and ended. This article explains the exact roles of the CL_PROFILING_COMMAND_QUEUED and CL_PROFILING_COMMAND_SUBMIT timestamps, what stages of execution they measure, and how developers can use the difference between them to evaluate host and driver overhead.

OpenCL Profiling Overview

To capture timing data for OpenCL commands (such as kernel executions or memory transfers), the command queue must be created with the CL_QUEUE_PROFILING_ENABLE flag. Developers can then query specific stages of an associated event using the clGetEventProfilingInfo function.

Profiling timestamps are returned as 64-bit unsigned integers (cl_ulong) representing time in nanoseconds. These timestamps are synchronized to a single device clock, allowing direct subtraction between execution stages.

What is CL_PROFILING_COMMAND_QUEUED?

The CL_PROFILING_COMMAND_QUEUED timestamp records the moment a command is initially enqueued into a command queue on the host.

  • Trigger Point: It marks the completion of the host-side enqueue function (such as clEnqueueNDRangeKernel or clEnqueueReadBuffer).
  • State: At this stage, the command exists within the host software queue. It has not yet been processed by the OpenCL runtime driver or dispatched to the physical device.

What is CL_PROFILING_COMMAND_SUBMIT?

The CL_PROFILING_COMMAND_SUBMIT timestamp records the moment the command is submitted by the OpenCL runtime driver to the target hardware device.

  • Trigger Point: It marks when the host driver flushes the command queue and hands the task off to the underlying hardware interface or command processor.
  • State: The command has left the host queue and is now in the device-level queue, ready to begin execution as soon as device compute units become available and any dependent events are resolved.

What the Difference Between the Two Timestamps Measures

Calculating the difference between these two points (SUBMIT - QUEUED) measures the queue latency on the host:

\[\text{Host/Driver Overhead} = \text{CL\_PROFILING\_COMMAND\_SUBMIT} - \text{CL\_PROFILING\_COMMAND\_QUEUED}\]

This duration reveals:

  1. Driver Overhead: The time the OpenCL runtime takes to serialize, validate, and prepare the command for the target architecture.
  2. Queue Buffering: In an in-order queue, commands may sit queued while waiting for previous commands to be submitted.
  3. Flush Latency: Commands may remain unsubmitted until the runtime's internal buffer fills, or until an explicit call to clFlush or clFinish forces submission to the device.

A large gap between QUEUED and SUBMIT indicates CPU-side or driver-side delays rather than slow execution on the GPU or accelerator.

Summary in the Context of the Complete Lifecycle

To understand these two timestamps within the full OpenCL command lifecycle, consider the sequence of all four profiling states:

  1. CL_PROFILING_COMMAND_QUEUED: The host registers the command in the queue.
  2. CL_PROFILING_COMMAND_SUBMIT: The driver submits the command to the hardware.
  3. CL_PROFILING_COMMAND_START: The device actively begins executing the command.
  4. CL_PROFILING_COMMAND_END: The device finishes execution.

While START and END isolate device compute time, QUEUED and SUBMIT isolate host-to-device scheduling efficiency.
