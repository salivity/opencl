OpenCL Double Buffering for Streaming Pipelines

Double-buffering in OpenCL is a vital design pattern for streaming data pipelines that maximizes hardware throughput by hiding PCIe memory transfer latencies. By maintaining two sets of memory allocations and overlapping data transfers with kernel execution, the host and compute device can operate simultaneously rather than sequentially. This article outlines the recommended architecture, queue structures, and event-based synchronization required to build an efficient double-buffering pipeline in OpenCL.

Architecture Overview

The standard approach uses two distinct sets of memory buffers (Buffer Set A and Buffer Set B) and separates operations into compute tasks and memory transfer tasks. While the compute device executes a kernel on Buffer Set A, the host concurrently transfers the next batch of input data into Buffer Set B and reads the previous results from Buffer Set A back to host memory.

To enable this overlap, the recommended design pattern employs two separate in-order command queues (or alternatively, a single out-of-order queue, though multiple in-order queues offer greater portability across diverse OpenCL runtimes):

  1. Transfer Queue (queue_transfer): Dedicated to host-to-device (clEnqueueWriteBuffer) and device-to-host (clEnqueueReadBuffer) memory operations.
  2. Compute Queue (queue_compute): Dedicated to kernel dispatch (clEnqueueNDRangeKernel).

Synchronization with OpenCL Events

Because the queues operate asynchronously, synchronization between the transfer and compute stages must be managed using OpenCL events (cl_event).

For each iteration \(i\):

  1. Input Transfer: clEnqueueWriteBuffer is enqueued into queue_transfer targeting the current input buffer, generating an event_write.
  2. Kernel Execution: clEnqueueNDRangeKernel is enqueued into queue_compute. It is passed event_write in its event wait list so that execution begins only after the transfer completes. This yields an event_kernel.
  3. Output Transfer: clEnqueueReadBuffer is enqueued into queue_transfer. It is passed event_kernel in its event wait list to guarantee that the kernel has finished writing output data before the transfer to the host begins.

The Streaming Loop Structure

The double-buffering execution loop alternates between the two buffer sets:

Iteration N:
- Queue_Transfer: Read Output (N-1 from Set B) [waits on Kernel N-1]
- Queue_Transfer: Write Input (N+1 to Set B)
- Queue_Compute:  Execute Kernel (N on Set A)   [waits on Write N]

Iteration N+1:
- Queue_Transfer: Read Output (N from Set A)   [waits on Kernel N]
- Queue_Transfer: Write Input (N+2 to Set A)
- Queue_Compute:  Execute Kernel (N+1 on Set B) [waits on Write N+1]

Before entering the loop, an initial write is enqueued to prime the pipeline (prologue). Inside the loop, events from the previous iteration must be tracked and passed to the wait lists of the current iteration. After the final data chunk is processed, remaining outputs are read back, and the pipeline drains (epilogue).

Pinned Memory Optimization

To achieve true asynchronous memory transfers and saturate PCIe bandwidth, standard host-allocated buffers should be replaced with pinned host memory.

Create OpenCL buffers using the CL_MEM_ALLOC_HOST_PTR flag, or map page-locked memory directly using clEnqueueMapBuffer. Non-pinned memory typically requires the OpenCL driver to copy data into an intermediate pinned buffer before initiating direct memory access (DMA), which introduces CPU overhead and can prevent transfers from running concurrently with compute workloads.

Cleanup and Resource Reuse

Reusing cl_event objects without proper lifecycle management causes memory leaks. Ensure that every event generated by transfers or kernel launches is released via clReleaseEvent once its corresponding dependent operations have been enqueued and the event is no longer needed in subsequent wait lists.
