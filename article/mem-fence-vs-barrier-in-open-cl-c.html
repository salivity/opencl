mem_fence vs barrier in OpenCL C

In OpenCL C, both mem_fence and barrier are synchronization primitives used to manage concurrency, but they serve fundamentally different purposes. While mem_fence enforces memory ordering constraints for the calling work-item without pausing its execution relative to its peers, barrier provides both memory ordering and execution synchronization, forcing every work-item in a work-group to wait until all have reached the same point in code. Understanding this distinction is critical for writing correct, deadlock-free, and high-performance kernel code.

Execution Synchronization

The most significant difference lies in execution control:

  • barrier: Halts execution. When a work-item reaches a barrier, it suspends execution until every work-item in the same work-group arrives at the barrier. Only after all work-items arrive does execution resume.
  • mem_fence: Does not halt execution. A work-item executing mem_fence continues running without waiting for any other work-item in the work-group.

Memory Ordering

Both functions accept memory flags (CLK_LOCAL_MEM_FENCE, CLK_GLOBAL_MEM_FENCE, or a combination of both via bitwise OR) to define which memory spaces are affected:

  • mem_fence: Guarantees that all memory loads and stores issued by the calling work-item prior to the fence are committed to memory before any loads or stores issued after the fence. It enforces a strict ordering pipeline to prevent compiler or hardware reordering across the fence boundary.
  • barrier: Implies an automatic mem_fence using the specified flags. In addition to synchronizing execution, it ensures that all memory transactions initiated by all work-items in the work-group before the barrier are globally or locally committed before any work-item proceeds past the barrier.

Control Flow and Deadlock Risks

Because barrier coordinates execution across the entire work-group, it is subject to strict convergence rules:

  • barrier: Must be encountered by all work-items in a work-group executing the same dynamic path. If a barrier is placed inside a divergent conditional branch (e.g., an if statement where only some work-items enter), the behavior is undefined and typically results in a GPU kernel hang or deadlock.
  • mem_fence: Can safely be used inside conditional code or loops with divergent execution. Because it only affects the ordering of the executing work-item's own memory operations, divergent branches do not risk deadlock.

Practical Use Cases

  • Use barrier when work-items need to share data safely. The standard pattern involves work-items collaboratively loading data from global memory into __local memory, calling barrier(CLK_LOCAL_MEM_FENCE) to ensure the shared memory is fully written, and then reading each other's data without data races.
  • Use mem_fence when implementing lock-free data structures, custom atomic synchronization protocols, or producer-consumer patterns between work-items across groups where waiting for an entire work-group is either impossible or unnecessary. It ensures writes to flag variables are committed only after the payload data is safely written to memory.
