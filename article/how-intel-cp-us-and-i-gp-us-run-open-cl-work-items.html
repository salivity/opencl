How Intel CPUs and iGPUs Run OpenCL Work-Items

This article explores how Intel processors achieve concurrent OpenCL work-item execution across multi-core central processing units (CPUs) and integrated graphics processing units (iGPUs). It covers the creation of heterogeneous OpenCL contexts, the hardware-level translation of work-items into CPU vector instructions and GPU execution units, the role of shared system memory in minimizing data transfer overhead, and the mechanisms used to balance workloads simultaneously across both compute engines.

Heterogeneous OpenCL Setup and Command Queues

To execute work-items concurrently on an Intel CPU and an integrated GPU, an OpenCL host program creates a single cl_context containing both device types (CL_DEVICE_TYPE_CPU and CL_DEVICE_TYPE_GPU). The application then establishes independent, asynchronous command queues (cl_command_queue) for each device.

Because OpenCL command queues operate independently, the host thread can enqueue non-blocking kernels (clEnqueueNDRangeKernel) to both devices back-to-back. The underlying Intel OpenCL runtime routes the commands to separate driver stacks: the CPU runtime and the Intel Graphics Compute Runtime. Once submitted, both devices process their respective queues in parallel without blocking each other.

Work-Item Execution on the Intel CPU

Intel CPUs process OpenCL workloads by mapping work-groups and work-items onto existing operating system threads and SIMD (Single Instruction, Multiple Data) vector units:

  • Work-Groups to OS Threads: The OpenCL runtime uses an internal task scheduler (typically based on Intel oneAPI Threading Building Blocks) to assign OpenCL work-groups to worker threads running across available physical and logical CPU cores.
  • Work-Items to SIMD Vectors: Rather than assigning one CPU core per work-item, the OpenCL compiler vectorizes the kernel code. Multiple work-items within a work-group are packed into vector lanes (such as AVX-256 or AVX-512). For example, an AVX-512 register can process 16 single-precision floating-point work-items in a single instruction cycle.
  • Execution: Hardware prefetchers, out-of-order execution engines, and large L3 caches allow the CPU to execute work-items requiring heavy branch prediction and complex sequential operations efficiently.

Work-Item Execution on the Intel Integrated GPU

Intel iGPUs (such as Intel Iris Xe or UHD Graphics) utilize a massively parallel architecture based on Execution Units (EUs) or Xe Vector Engines (XVEs):

  • Sub-Groups and SIMD Compilation: The graphics compiler groups work-items into hardware execution units known as sub-groups, typically operating at SIMD widths of 8, 16, or 32.
  • Hardware Multithreading: Each EU/XVE features dedicated hardware thread contexts. When one thread stalls waiting for a memory fetch from the system RAM or LLC (Last-Level Cache), the EU automatically switches to another runnable thread with zero cycle overhead.
  • Work-Group Dispatch: Work-groups are assigned to Sub-slices (or Dual Sub-slices). Each sub-slice contains dedicated Shared Local Memory (SLM), thread dispatchers, and samplers. The work-items inside a work-group execute synchronously on the execution units within the same sub-slice.

Unified Memory and Low-Overhead Concurrency

A major advantage of concurrent execution on Intel hardware is the shared physical silicon architecture. Both the CPU cores and the iGPU share the same physical system RAM and access to the shared Last-Level Cache (LLC) via a coherent system fabric or ring interconnect.

  • Zero-Copy Memory Access: Unlike discrete GPUs that require data copies across the PCIe bus, Intel CPUs and iGPUs can share data buffers using zero-copy allocations (CL_MEM_ALLOC_HOST_PTR or CL_MEM_USE_HOST_PTR) and OpenCL Shared Virtual Memory (SVM).
  • Concurrent Memory Access: Both devices can read from and write to the same physical memory space during execution. Fine-grained SVM, available on modern Intel platforms, allows atomic operations across both the CPU and iGPU, enabling lock-free data structures shared between concurrently executing work-items on different devices.

Workload Synchronization and Load Balancing

True concurrent execution requires deliberate load balancing and event management from the host application:

  1. NDRange Splitting: Applications divide the overall problem domain (NDRange) into proportional slices based on the compute characteristics of each device. Workloads dominated by arithmetic density are typically allocated to the iGPU, while latency-sensitive tasks or operations with irregular branching are routed to the CPU.
  2. Synchronization via Events: The host coordinates dependencies using OpenCL event objects (cl_event). When a kernel running on the GPU requires output from the CPU (or vice versa), an event passed to clEnqueueNDRangeKernel or clEnqueueWaitForEvents forces execution barriers only when necessary, allowing both devices to operate independently for the remainder of the application lifecycle.
