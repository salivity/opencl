Dividing OpenCL NDRange Across Asymmetric Devices

Coordinating heterogeneous compute platforms, such as systems pairing integrated GPUs, discrete GPUs, and multicore CPUs, requires specialized load-balancing strategies to prevent bottlenecks. When dividing a global OpenCL NDRange across asymmetric devices, disparities in compute density, memory bandwidth, and architectural topologies mean uniform splitting will cause faster devices to stall while slower units finish processing. This article details the primary strategies for managing asymmetric workload distribution in OpenCL, covering static ratio-based partitioning, dynamic work-stealing queues, event-driven adaptive feedback, and memory topology management.

Static Proportional Partitioning

Static proportional partitioning calculates a fixed ratio of the global NDRange to assign to each device before execution begins. This split is typically derived from theoretical performance metrics—such as single-precision FLOPS and peak memory bandwidth—or from offline benchmarking runs using identical kernel data.

To execute this strategy, the application decomposes the global domain into non-overlapping sub-NDRanges using clEnqueueNDRangeKernel, setting custom global work offsets (global_work_offset) and dimensions (global_work_size) for each device context. While this method imposes practically zero runtime scheduling overhead, it assumes linear scaling and uniform execution time per work-item. It is fragile against data-dependent branching, runtime thermal throttling, or OS background activity that alters device performance dynamically.

Dynamic Chunk-Based Scheduling

Dynamic scheduling divides the global NDRange into numerous smaller discrete chunks and enqueues them onto a shared, centralized task scheduler. Instead of receiving a massive monolithic partition, each device requests and executes a small block of work-items. As soon as a device finishes its current sub-NDRange, it signals the host to dispatch the next available chunk.

This approach inherently balances the load: faster processors naturally complete and consume more chunks, while slower hardware processes fewer chunks without stalling the global pipeline. To prevent scheduling overhead from overshadowing computation, chunk sizes must be carefully calibrated. Common variations include:

  • Fixed-size Chunking: Assigning uniformly sized blocks throughout execution.
  • Guided Self-Scheduling: Starting with large chunk sizes to minimize initial dispatch overhead, then geometrically decreasing the chunk size toward the end of the NDRange to smooth out tail-end latency.

Event-Driven Adaptive Feedback

For iterative algorithms or frame-based computational pipelines, adaptive feedback monitors real-time execution speeds to continuously adjust partition boundaries. OpenCL provides non-intrusive runtime tracking via event profiling:

  1. Enable profiling on each device command queue using CL_QUEUE_PROFILING_ENABLE.
  2. Attach cl_event objects to each clEnqueueNDRangeKernel call.
  3. Query timestamps with clGetEventProfilingInfo using CL_PROFILING_COMMAND_START and CL_PROFILING_COMMAND_END.
  4. Calculate the effective processing rate (work-items per millisecond) for each device.
  5. Reallocate the proportional NDRange boundaries for the subsequent iteration based on measured performance.

Adaptive feedback automatically accounts for dynamic frequency scaling, operating system interruptions, and changing computational density across algorithmic stages.

Memory Hierarchy and Transfer Latency Mitigation

Workload distribution is heavily bounded by data migration costs. In asymmetric systems, a discrete GPU typically connects via PCIe, introducing significant latency, while an integrated GPU or CPU may utilize shared physical memory (Zero-Copy).

Effective distribution strategies must account for these transfer penalties:

  • Overlap Computation with Transfers: Utilize asynchronous memory operations (clEnqueueWriteBuffer and clEnqueueReadBuffer non-blocking calls) and double-buffering. A discrete GPU should execute its current sub-NDRange while the host transfers inputs for the next iteration.
  • Non-Uniform Splitting based on Data Locality: Bias larger workload partitions toward devices where the data already resides, reducing total traffic across the interconnect bus.

Device-Specific Work-Group Optimization

Work-group sizing cannot be treated uniformly across asymmetric architectures. While global work offsets divide the broader problem, the local work-group dimensions must be tailored per device:

  • CPUs: Small work-group sizes (often 1 or small multiples of SIMD vector widths) maximize cache utilization and prevent thread migration overhead.
  • GPUs: Larger work-group sizes (typically multiples of 32 or 64 to match hardware wave/warp architectures) are required to hide memory latency through massively parallel thread switching.

Applications must pass distinct local_work_size pointers to each respective device’s kernel enqueue call to ensure peak architectural efficiency across the asymmetric cluster.
