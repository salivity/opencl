Limitations of LLVM-Based SPIR Before SPIR-V

Before the introduction of SPIR-V, the Khronos Group utilized the Standard Portable Intermediate Representation (SPIR) to facilitate cross-vendor compilation in OpenCL. While original SPIR versions—primarily SPIR 1.2 and SPIR 2.0—aimed to decouple OpenCL compilation into a frontend and a backend, they relied directly on LLVM intermediate representation (IR) bitcode. This reliance created severe technical and practical bottlenecks, including tight coupling to specific LLVM versions, target-specific data leakage, driver bloat, and an inability to unify compute with modern graphics pipelines. These deficiencies ultimately necessitated the clean-slate redesign that resulted in SPIR-V.

Direct Coupling to LLVM Versions

The foremost limitation of original SPIR was its direct dependence on specific LLVM releases. SPIR 1.2 was bound to LLVM 3.2, and SPIR 2.0 was tied to LLVM 3.4. By design, the LLVM project does not guarantee backward or forward compatibility for its binary bitcode across major versions. Because the SPIR specification was defined as a subset and extension of a particular LLVM version's IR, any update to a hardware vendor's internal LLVM compiler chain risked breaking compatibility with existing SPIR binaries. Vendors were forced either to maintain legacy, outdated LLVM parser infrastructure inside their runtime drivers or to implement complex translation layers.

Target Machine and Layout Leakage

LLVM IR was designed as an internal representation for general-purpose CPU compilers, meaning it assumes low-level target machine specifics earlier in the pipeline than is ideal for heterogeneous computing. When compiling an OpenCL C kernel into LLVM bitcode, target-dependent information—such as data layout, endianness, pointer sizes, and struct alignment—often became baked directly into the IR. This "leaky abstraction" compromised true binary portability across diverse GPU architectures, embedded accelerators, and heterogeneous hardware that possessed fundamentally different memory hierarchies and register structures.

Driver Bloat and Compilation Overhead

Because original SPIR was essentially serialized LLVM bitcode, hardware vendors had to embed large portions of the LLVM infrastructure directly into their graphics and compute drivers to parse, validate, and optimize incoming SPIR modules. For resource-constrained environments, such as mobile and embedded platforms, shipping heavyweight LLVM backends inside consumer-facing drivers led to massive binary footprints, high memory consumption, and increased kernel compilation latency at runtime.

Inability to Unify Graphics and Compute

Original SPIR was built specifically around OpenCL C semantics and compute workloads. As the Khronos Group developed modern low-overhead APIs like Vulkan, the industry demanded a single intermediate language capable of representing both general compute and the complete graphics pipeline (including vertex, tessellation, geometry, and fragment shading). Original LLVM-based SPIR lacked standard constructs to handle graphics-specific concepts—such as multi-stage pipeline inputs/outputs, descriptors, image sampling states, and built-in graphics operations—making it unsuitable as a unified cross-API intermediate format.

Weak Governance and Validation Constraints

Because original SPIR inherited the full expressiveness and complexity of LLVM IR, writing standalone specification compliance tests and robust validators was extremely difficult. In practice, code generation behavior was largely defined by how a specific version of Clang and the LLVM libraries behaved rather than by an independent, formal specification. SPIR-V solved this by discarding LLVM bitcode entirely, establishing an independent, strictly versioned, 32-bit-word binary format tailored specifically for heterogeneous compute and graphics architectures.
