OpenCL and DirectX Interop for Textures and Buffers

Interoperating OpenCL with DirectX on Windows enables high-performance computing pipelines by allowing OpenCL kernels to directly read from and write to Direct3D graphics resources—such as textures and vertex buffers—without transferring data back to host memory. This article explains the architectural mechanism of this interoperability, the extensions involved, context creation, and the process of acquiring, manipulating, and releasing shared resources between the two APIs.

Core Interoperability Extensions

DirectX-OpenCL interoperability is achieved through Khronos extensions, predominantly cl_khr_d3d11_sharing for Direct3D 11 and cl_khr_d3d10_sharing for Direct3D 10. These extensions provide the function pointers required to bridge Direct3D resources to OpenCL memory objects (cl_mem). Because these functions are extension-based, they must be loaded at runtime using clGetExtensionFunctionAddressForPlatform.

Context Creation and Device Query

Before sharing resources, the OpenCL context must be bound to the existing Direct3D device. This ensures both APIs operate on the same physical GPU and share the same virtual address space.

  1. Query Matching Devices: The function clGetDeviceIDsFromD3D11KHR queries the OpenCL device corresponding to an existing ID3D11Device.
  2. Initialize the Context: When calling clCreateContext, the cl_context_properties array must include CL_CONTEXT_D3D11_DEVICE_KHR mapped to the pointer of the Direct3D 11 device, alongside the CL_CONTEXT_PLATFORM property.

Creating Shared Memory Objects

Once the context is established, Direct3D resources can be wrapped into OpenCL cl_mem handles. The resources must be created in DirectX with appropriate flags (typically D3D11_USAGE_DEFAULT) to permit GPU-side sharing.

  • Vertex Buffers: An ID3D11Buffer representing vertex data is wrapped using clCreateFromD3D11BufferKHR. This returns a standard OpenCL 1D buffer object. Inside the OpenCL kernel, this data can be modified as an array of primitives, structs, or vectors.
  • Textures: A 2D texture (ID3D11Texture2D) is wrapped using clCreateFromD3D11Texture2DKHR, while 3D textures use clCreateFromD3D11Texture3DKHR. OpenCL treats these as native image objects (image2d_t or image3d_t), enabling hardware-accelerated sampling, filtering, and normalized coordinate addressing.

Synchronization Pipeline

Because Direct3D and OpenCL use separate command queues and internal execution states, explicit synchronization is required to prevent race conditions. The data never leaves device VRAM; synchronization merely transfers execution ownership between the graphics and compute pipelines.

  1. Flush Direct3D: The Direct3D pipeline must flush its pending commands using ID3D11DeviceContext::Flush to ensure rendering operations on the target resources are completed.
  2. Acquire Objects in OpenCL: The application calls clEnqueueAcquireD3D11ObjectsKHR, passing the target cl_mem handles. This creates an execution barrier, locking the resources for OpenCL usage.
  3. Execute Kernels: Compute kernels are queued via clEnqueueNDRangeKernel to process or generate the vertex or texture data.
  4. Release Objects to Direct3D: After compute operations are queued, clEnqueueReleaseD3D11ObjectsKHR is called to release ownership back to Direct3D.
  5. Direct3D Rendering: Once the OpenCL command queue completes (or signals an event), Direct3D can bind the vertex buffer to the Input Assembler stage or the texture to a Pixel Shader for rendering.
