Matrix Transpose Memory Stride Issues in OpenCL

Transposing large matrices on GPU architectures using OpenCL introduces severe performance bottlenecks primarily driven by unfavorable memory access strides. Because a transposition inherently converts row-major data into column-major structures, at least one stage of the operation forces threads to access memory across large strides rather than contiguously. This article examines the core memory stride issues that emerge during OpenCL matrix transposition—including uncoalesced global memory transactions, DRAM page thrashing, and local memory bank conflicts—along with the standard architectural remedies used to eliminate them.

The Inherent Asymmetry of Transposition

In standard C-based OpenCL representations, a matrix of dimension \(N \times M\) is laid out linearly in row-major order: adjacent elements along a row occupy contiguous memory addresses, while adjacent elements along a column are separated by a stride equal to the row width (\(M\)).

A naive transposition maps each OpenCL work-item (thread) to a specific element:

  • If reads are contiguous: work-item \((x, y)\) reads input[y * M + x]. Consecutive work-items across the work-group load adjacent memory addresses.
  • Writes become strided: work-item \((x, y)\) must write to output[x * N + y]. Consecutive work-items across the work-group now write to addresses separated by a stride of \(N\).

Swapping the access order simply inverts the problem, leaving one side of the pipeline severely decoupled from the underlying hardware requirements.

Non-Coalesced Global Memory Access

Modern GPUs execute work-items in lockstep groups (known as wavefronts on AMD or warps on NVIDIA). When threads in a wavefront request data from global memory, the memory controller attempts to merge these individual requests into the minimum possible number of memory transactions—a process known as memory coalescing.

  • Coalesced Access: When adjacent threads read or write adjacent addresses, a 32- or 64-thread wavefront can fulfill its entire request with a single or double 128-byte transaction.
  • Strided Access: When threads write with a stride of \(N\) (the row width of the destination matrix), the target addresses cross distinct cache lines. If \(N\) is sufficiently large, virtually every work-item in the wavefront hits a different cache line.

This drops memory throughput dramatically. Instead of a single 128-byte transaction supplying data to 32 threads, the memory controller must issue 32 distinct transactions, wasting massive amounts of bus bandwidth by discarding up to 96% of the fetched cache line data.

Cache Thrashing and DRAM Row Buffer Conflicts

For very large matrices that exceed the GPU's L1 and L2 cache capacities, high-stride memory access degrades the lower levels of the memory hierarchy:

  1. Cache Evictions: Large strides cause rapid cache line turnover. As the GPU traverses rows to read or write columns, previously cached data is evicted before it can be reused, nullifying the benefits of the cache hierarchy.
  2. DRAM Page Thrashing: Device memory is organized into banks, rows, and columns. Accessing memory within an already active row buffer is fast. When work-items access memory with large strides, they continually activate different rows across different memory banks. This constant opening and closing of DRAM row buffers adds substantial memory latency.

Shared/Local Memory Bank Conflicts

The established optimization for matrix transposition in OpenCL is tiling: work-groups load a 2D tile from global memory into high-speed __local memory coalesced, synchronize via barrier(CLK_LOCAL_MEM_FENCE), and write the transposed tile back to global memory in a coalesced fashion.

While this technique resolves the global memory stride issue, it exposes an internal stride issue within OpenCL local memory known as bank conflicts:

  • Local memory is divided into independent, equal-sized memory modules called banks (typically 32 banks, 4 bytes wide).
  • If consecutive work-items access addresses assigned to different banks, requests are handled simultaneously.
  • During the transposed read from local memory, threads access a column of the local tile. If the tile width is a multiple of the bank count (e.g., a \(32 \times 32\) tile on a 32-bank architecture), every work-item in the wavefront accesses the exact same memory bank.

This creates a 32-way bank conflict. The hardware must serialize the 32 accesses sequentially, negating the high-throughput benefits of using local memory.

Resolving Stride-Induced Bottlenecks

To overcome these access stride penalties, OpenCL implementations apply two primary architectural optimizations:

  1. Local Memory Padding: By allocating local tiles with an extra dummy column (e.g., __local float tile[32][33]), the stride between successive rows in local memory shifts by one element. This offset ensures that when threads read down a column, their target addresses map to unique local memory banks, eliminating bank conflicts entirely.
  2. Work-Group Swizzling: To mitigate DRAM page conflicts at the global level, work-group execution order can be swizzled (e.g., diagonal or Hilbert curve scheduling) rather than executed in simple raster order. This preserves spatial locality in DRAM row buffers across the entire device during massive parallel transpositions.
