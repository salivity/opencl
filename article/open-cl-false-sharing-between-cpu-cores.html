OpenCL False Sharing Between CPU Cores

False sharing in OpenCL CPU runtimes occurs when work-items running on different CPU cores concurrently modify distinct variables that reside on the same hardware cache line. While the program remains logically correct, the underlying CPU architecture wastes significant cycles maintaining cache coherency, resulting in severe performance bottlenecks. This article examines the hardware mechanics behind false sharing in OpenCL, how it manifests during execution, and practical techniques to eliminate it.

The Underlying Mechanism in CPU Runtimes

CPUs do not track memory access at the byte level; instead, they operate on fixed-size blocks called cache lines, which are typically 64 bytes in modern architectures. When executing an OpenCL kernel on a CPU device, the runtime scheduler distributes work-groups and work-items across available host cores using OS threads or a thread pool.

If Work-Item A on Core 0 writes to byte 0, and Work-Item B on Core 1 writes to byte 4, both cores must operate on the exact same 64-byte cache line. Even though the two work-items are accessing completely separate variables, the CPU cache coherency protocol (such as MESI or MOESI) treats the entire line as contested. Core 0 must invalidate Core 1's copy of the cache line before writing, and Core 1 must re-fetch it to perform its write, forcing the cache line to continually bounce between L1/L2 caches.

Observable Manifestations of False Sharing

When false sharing occurs in an OpenCL kernel running on a multi-core CPU, it typically reveals itself through several distinct symptoms:

  1. Negative Scaling (Slowdown as Cores Increase)
    The most prominent symptom is that increasing the number of compute units or expanding the global work size causes the kernel to run slower rather than faster. A single-threaded or low-core run often outperforms an execution that utilizes all physical and logical cores, as more cores simply generate more coherency invalidations.

  2. Inflated Cycles Per Instruction (CPI)
    Hardware profiling tools reveal a high CPI ratio. The CPU cores report near 100% utilization, but the instructions executed per cycle drop sharply. The execution pipelines spend the vast majority of their time stalled waiting for memory operations to complete.

  3. Massive L1/L2 Cache Misses and Inter-Core Bus Traffic
    Performance counters (via tools like Linux perf, Intel VTune, or AMD uProf) display an anomalous spike in L1 Data Cache misses, L2 invalidations, and High-Bandwidth Interconnect (UPI/Infinity Fabric) traffic. These misses occur even when the dataset is small enough to fit comfortably in the CPU's last-level cache.

Common OpenCL Patterns Causing False Sharing

A standard pattern that triggers false sharing on CPUs is direct indexing into a global array using global work-item IDs:

__kernel void accumulate(__global int* output, __global const int* input) {
    int gid = get_global_id(0);
    output[gid] = compute(input[gid]);
}

If the runtime assigns consecutive global IDs across different CPU threads, or if a reduction loop aggregates results into adjacent array indices (histogram[bin]++), multiple threads write to the same 64-byte boundary simultaneously. For standard 32-bit integers, up to 16 adjacent elements share a single 64-byte line, creating contention among up to 16 work-items.

How to Mitigate False Sharing in OpenCL

  • Local Aggregation: Accumulate results in private variables or work-item registers first, writing to global memory only once per work-item or work-group.
  • Array Padding: When work-items must write to separate tracking locations (such as per-thread partial sums), pad data structures so that each entry spans a full 64 bytes (e.g., using alignas(64) in host buffers or reserving 16 integers per thread slot).
  • Chunked Work Scheduling: Structure kernels so that each work-item or work-group processes a contiguous stride of memory that aligns with CPU cache boundaries, ensuring that neighboring work-items do not straddle shared cache lines concurrently.
