Hardware Support for OpenCL Convert Macros

OpenCL provides built-in conversion functions—commonly termed convert macros—such as convert_int4_sat, to handle type casting, vectorization, saturation, and rounding between primitive types. This article breaks down the native hardware conversion operations supported by these macros, explaining how modern GPU, CPU, and DSP architectures translate these OpenCL primitives into native instruction set architecture (ISA) operations.

Anatomy of the Conversion Function

OpenCL type conversions follow the naming convention convert_<dest_type><N>[_sat][_roundingMode]. For example, convert_int4_sat translates a 4-component vector from a source data type (such as float4 or short4) into signed 32-bit integers (int4) with saturation arithmetic enabled.

Hardware support for these operations maps to several discrete processor execution units:

1. Integer Saturation (_sat)

When integer destinations specify _sat, out-of-range values are clamped to the destination type's minimum or maximum representable value rather than overflowing or wrapping modulo.

  • Narrowing Conversions: When converting from wider integers (e.g., long to int or int to short), hardware uses native packing and saturation instructions:
    • x86 (SSE/AVX): Instructions like PACKSSDW (Pack Signed Doubleword to Word with Saturation) or PACKUSWB (Pack Signed Word to Unsigned Byte with Saturation).
    • ARM (NEON): Vector saturating narrowing instructions, such as VQMOVN (Vector Saturating Move and Narrow).
    • GPU Architectures (NVIDIA PTX / AMD GCN/RDNA): Handled via conversion instructions with saturation modifiers (e.g., PTX cvt.sat.s32 or AMD v_cvt_pk_i16_i32).
  • Unsigned to Signed / Signed to Unsigned: Hardware clamps negative inputs to zero for unsigned targets, or values exceeding \(2^{n-1}-1\) to the maximum positive signed limit.

2. Float-to-Integer Conversions

Converting floating-point values to integers via functions like convert_int4_sat uses dedicated Floating-Point Unit (FPU) to Integer conversion pipelines:

  • Truncation and Rounding: By default, float-to-integer conversion in OpenCL uses truncation toward zero (_rtz). If explicit modifiers are supplied (_rte, _rtp, _rtn), native hardware rounding controls are asserted directly in the instruction opcodes (e.g., PTX cvt.rni for round to nearest even, cvt.rmi for round toward negative infinity).
  • NaN and Infinity Handling with Saturation: Standard hardware float-to-int conversion typically produces an invalid operation exception or returns an architecture-specific indefinite value when encountering NaN or infinity. When _sat is present, native hardware clamp paths force NaN to 0, \(+\infty\) to INT_MAX, and \(-\infty\) to INT_MIN.

3. Floating-Point Precision Conversions

Hardware conversion units directly support cross-precision floating-point conversions between IEEE 754 formats:

  • Half-Precision (FP16) \(\leftrightarrow\) Single-Precision (FP32): Mapped to instructions such as x86 VCVTPH2PS / VCVTPS2PH, or GPU FP16 conversion opcodes (v_cvt_f32_f16).
  • Single-Precision (FP32) \(\leftrightarrow\) Double-Precision (FP64): Mapped to single-instruction float extension or demotion (cvt.f64.f32, cvt.f32.f64, or x86 CVTPS2PD / CVTPD2PS).

4. Vectorized Execution Units

The <N> component (such as the 4 in convert_int4_sat) dictates SIMD or SIMT mapping:

  • CPUs and Vector DSPs: Vector conversions are mapped to 128-bit, 256-bit, or 512-bit wide SIMD registers (e.g., SSE, AVX2, AVX-512, NEON), processing the 4 components simultaneously in a single vector execution cycle.
  • GPUs (SIMT Execution): On GPUs, vector conversions like convert_int4_sat are unpacked into four separate scalar conversion operations across individual register lanes, or executed via packed dual/quad instructions if the microarchitecture supports sub-word or packed execution (such as packed 16-bit math instructions).
