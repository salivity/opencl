OpenCL Dispatch Across Multi-Vendor Devices

OpenCL cannot natively dispatch compute workloads directly across heterogeneous multi-vendor devices within a single command stream or context. Because hardware vendors supply proprietary platform layers that isolate their own devices, OpenCL runtimes do not automatically load balance or schedule tasks across competing hardware. To execute workloads across mixed-vendor environments, such as combining an NVIDIA GPU, an AMD GPU, and an Intel CPU, developers must manually orchestrate execution and data transfers at the application host level.

The Platform Architecture Barrier

The primary limitation stems from the OpenCL execution hierarchy, which begins with the platform layer (cl_platform_id). Hardware vendors provide their own Installable Client Driver (ICD) that implements the OpenCL specification for their specific architecture.

A compute context (cl_context) is the boundary within which memory objects, programs, and command queues exist. In standard OpenCL implementations, a single context can only contain devices (cl_device_id) that belong to the exact same platform. Because you cannot create a unified cl_context encompassing an NVIDIA GPU and an AMD GPU, the native runtime cannot route commands, share memory buffers, or dispatch kernel events directly between them.

Manual Host Orchestration

To utilize multi-vendor hardware concurrently, the host application must explicitly manage each vendor stack:

  1. Platform Discovery: Query the host system for all available platforms using clGetPlatformIDs.
  2. Context Creation: Initialize a separate cl_context for each distinct vendor platform.
  3. Queue Initialization: Build individual cl_command_queue instances for the target devices within their respective contexts.
  4. Workload Partitioning: Manually divide the global problem domain (NDRange) into discrete sub-problems tailored to each device's compute capabilities.
  5. Memory Synchronization: Allocate separate buffers for each context. Since memory cannot be shared directly across platforms via OpenCL pointers, intermediate data must be copied back to host memory (system RAM) before being transferred to another vendor's device.

Open-Source Runtime Exceptions

While proprietary vendor drivers enforce platform isolation, open-source implementations such as PoCL (Portable Computing Language) offer alternatives. PoCL can aggregate multiple heterogeneous compute backends—including standard CPUs, CUDA-enabled NVIDIA GPUs, and custom accelerators—under a single unified platform. In such specialized environments, OpenCL can create a single context spanning disparate hardware, though workload distribution across devices still requires explicit command queue management by the developer rather than automated load balancing.
