How OpenCL ICD Loader Resolves Symbols Across Runtimes

The OpenCL Installable Client Driver (ICD) loader acts as an intermediary layer between an OpenCL application and the hardware-specific OpenCL runtime libraries installed on a system. This article explains how the ICD loader discovers multiple vendor runtimes, extracts their dispatch tables, and dynamically routes API symbols to the appropriate vendor implementation at runtime using object-based dispatching.

Runtime Discovery and Enumeration

The ICD loader does not contain any compute execution logic. Instead, when an application initializes OpenCL by calling clGetPlatformIDs, the loader scans the host operating system to discover installed vendor runtimes:

  • Linux and POSIX Systems: The loader reads text files located in /etc/OpenCL/vendors/. Each .icd file contains the path to a vendor's dynamic shared library (for example, libnvidia-opencl.so.1 or libamdocl64.so).
  • Windows Systems: The loader checks the system registry under HKEY_LOCAL_MACHINE\SOFTWARE\Khronos\OpenCL\Vendors. Each entry contains a path to a vendor's dynamically linked library (.dll) along with a DWORD value indicating its activation state.

For each entry found, the loader loads the shared library into memory using platform-native calls (dlopen on Linux or LoadLibrary on Windows).

Dispatch Table Negotiation

To establish communication with each loaded library, the ICD loader checks whether the vendor runtime complies with the OpenCL ICD specification.

  1. Querying the ICD Entry Point: The loader queries the library for an exported entry function, primarily clIcdGetPlatformIDsKHR or clGetExtensionFunctionAddress.
  2. Retrieving Platforms: The loader invokes clIcdGetPlatformIDsKHR on the vendor library. The vendor library populates an array of cl_platform_id handles corresponding to the hardware devices it supports.
  3. Dispatch Table Attachment: Each returned cl_platform_id is an opaque pointer that internally points to a data structure whose first member is a pointer to a cl_icd_dispatch structure. This table consists of function pointers pointing directly to the vendor's concrete implementations of the standard OpenCL API functions.

Routing Function Calls via Dynamic Dispatch

Once platforms are enumerated, the ICD loader resolves symbols using a two-tier mechanism:

1. Loader-Implemented Entry Points

Functions that do not belong to a specific vendor platform or are required to aggregate multiple platforms—such as clGetPlatformIDs and clUnloadCompiler—are directly implemented within the ICD loader itself. When the application calls clGetPlatformIDs, the loader aggregates the platform IDs returned by all discovered vendor runtimes and presents them to the application as a single, unified list.

2. Object-Based Dispatching

For API calls associated with specific resources (such as clCreateContext, clEnqueueNDRangeKernel, or clReleaseMemObject), the application passes an OpenCL handle (cl_platform_id, cl_context, cl_command_queue, etc.) as an argument.

The OpenCL ICD specification mandates that every vendor-allocated handle must mirror a C++ virtual method table (vtable) structure: the first pointer inside the object structure must point to that vendor's cl_icd_dispatch table.

When an API function is called:

  1. The application links against the ICD loader and invokes the exported stub for the function (e.g., clFinish(cl_command_queue queue)).
  2. The ICD loader stub dereferences the first parameter passed to it: 
    struct _cl_icd_dispatch *dispatch = *(struct _cl_icd_dispatch **)queue;
  3. The loader calls the matching function pointer inside that vendor’s table: 
    return dispatch->clFinish(queue);

Because each object contains a pointer to the dispatch table belonging to the vendor that created it, subsequent operations are automatically routed to the correct vendor library without requiring conditional branching or runtime string lookups.

Extension Symbol Resolution

When an application needs to access platform-specific or device-specific extensions, it calls clGetExtensionFunctionAddressForPlatform. The ICD loader delegates this query to the specific platform’s dispatch table. The vendor library returns a function pointer directly from its own driver code, allowing the application to bypass the loader entirely for proprietary or non-standard extension functions.
