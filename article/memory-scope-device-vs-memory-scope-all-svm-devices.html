memory_scope_device vs memory_scope_all_svm_devices

In OpenCL 2.0 and later, memory scopes define the boundary within which atomic operations and memory orderings apply. The difference between memory_scope_device and memory_scope_all_svm_devices centers on the visibility boundary of these operations: memory_scope_device restricts memory synchronization strictly to work-items running on the same individual OpenCL device, while memory_scope_all_svm_devices extends synchronization across all OpenCL devices sharing a virtual memory space, including the host CPU.

Understanding memory_scope_device

When an atomic operation or memory fence uses memory_scope_device, the synchronization guarantees are confined to a single OpenCL device.

  • Visibility: All work-items across all work-groups executing on that specific device can see the changes according to the specified memory ordering (e.g., memory_order_seq_cst, memory_order_acq_rel).
  • Hardware Boundary: It typically targets device-level hardware primitives, such as GPU L2 caches or on-chip coherence fabrics.
  • Exclusions: The host processor and any secondary devices connected to the same OpenCL context will not be synchronized by this operation.
  • Performance: Because it does not require bus transactions or cache-coherency protocols across PCI Express (or other system interconnects), memory_scope_device has lower latency and higher throughput compared to broader scopes.

Understanding memory_scope_all_svm_devices

The memory_scope_all_svm_devices scope is designed for heterogeneous computing environments utilizing Shared Virtual Memory (SVM), particularly fine-grained system SVM.

  • Visibility: Memory operations synchronized with this scope are visible to all work-items on the current device, work-items on other SVM-capable devices in the same context, and the host CPU threads.
  • Hardware Boundary: This scope transcends individual device boundaries, utilizing system-wide cache coherency protocols or software-driven flush-and-invalidate cycles across system buses.
  • Requirements: Using this scope requires hardware and driver support for fine-grained system or fine-grained buffer SVM with atomic capabilities.
  • Performance: Synchronization at this level introduces significantly higher latency due to cross-device interconnect traffic, system cache invalidation, and broader memory stalls.

Key Differences Summary

  • Scope of Synchronization: memory_scope_device synchronizes only work-items on the local device. memory_scope_all_svm_devices synchronizes the local device, other discrete/integrated OpenCL devices in the context, and the host CPU.
  • Use Case: Use memory_scope_device for global communication within a single kernel running on a single accelerator (such as multi-work-group reductions). Use memory_scope_all_svm_devices when implementing lock-free data structures or signaling mechanisms shared concurrently between the host and device, or between multiple peer devices.
  • Cost: memory_scope_device is localized and fast. memory_scope_all_svm_devices carries heavy synchronization overhead across system interconnects.
